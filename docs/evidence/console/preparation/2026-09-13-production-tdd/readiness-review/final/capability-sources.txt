# Console capability preservation and usability evidence

The primary sources support a whole-product capability-family map and explicit dependency preservation before first-slice implementation. They do not justify completing every future feature, adopting Palantir's storage architecture, or calling a designed or partially tested Console slice equivalent to Foundry. The most consequential missing distinction is between a structurally valid object model, an executable workflow, and a workflow people can discover and complete.

## Source scope and dates

This bounded review inspected official Palantir documentation, W3C guidance and the GOV.UK Service Manual for an as-of date of 13 September 2026. The bundle retains 29 retrievals: 25 usable documents and four failed page candidates. `source-inventory.json` records exact requested URLs, titles, dates when stated, response status chains, file paths and raw SHA256 hashes. Current Palantir overview pages are undated; their copyright year is not treated as publication date. The release index contains individually dated June–September 2026 entries in its embedded page data, preserved in `release-2026-data.json` and `release-selected.json`. It initially renders only “loading”; no date is inferred from that display.

The official application reference is a useful family inventory, not proof of exhaustive leaf coverage or universal availability. Marketing descriptions such as secure, scalable, robust and comprehensive are not accepted as measured guarantees. Release notes describe bounded vendor changes; they are neither independent audits nor a recent industry consensus. Older W3C and GOV.UK guidance remains relevant for methods but is not presented as 2026 research.

## Capability families and the first slice's preservation obligations

The following dependency implications are analytical recommendations for Console. They are not claims that Palantir requires Console's implementation or that Console already satisfies them. “Additive” means plausibly additive if the stated contracts hold; it is not a migration-free guarantee.

| Capability family | Primary product evidence | Preserve in the first slice | Later adoption and decision trigger |
|---|---|---|---|
| Data connectivity, batch/stream integration, transformation and orchestration | Application reference lists Data Connection, Pipeline Builder, Code Repositories, Data Health, Scheduler and Data Lineage [1]; the integration overview describes the broader data plane [2]. | Source identity, owner identity, typed/versioned data and source lineage; distinguish business commands from imported/source facts. | Connectors and transforms can be additional adapters if ownership/provenance stays intact. Making native facts indistinguishable from imported snapshots requires conversion and reconciliation. Design actual connectors before their implementation. |
| Ontology semantics: objects, properties, links and interfaces | Ontology overview explicitly names semantic objects/properties/links and interface polymorphism [3]. | Stable identities, property/item addressing, units, relationship meaning/cardinality, schema versions, current policy context and provenance. | Additional types/links are plausibly additive. Changed identity or property meaning needs migration; “generic JSON” alone does not ensure compatibility. |
| Actions, functions, automations and decisions | Action definitions contain edits and side-effect behavior; shared logic/validation is reusable across applications [4]. Application reference includes Automate notifications and Actions [1]. | Canonical command/receipt identity, expected revisions, owner dispatch, submission authority, preflight semantics and effects distinct from notification delivery. | New registered actions can reuse owners; reinterpreting old commands or replacing historical receipt semantics requires explicit versioning/migration. |

API compatibility, tenant extensions and untrusted execution need separate admission; no requirement to copy Palantir microservices. |

Record each family with a stable capability ID, current-authority reference, accountable owner, phase, intended acceptance outcome, dependencies, current evidence/status and preserved contracts. For later features, record additive/migration/unknown plus the assumption that would invalidate that classification. The complete versioned leaf map remains necessary before a full-suite equivalence claim. Family-level closure cannot be counted as leaf acceptance.

## Primary-source findings that challenge easy equivalence claims

**Foundry contains more than an Ontology and an Actions API.** The application reference states that its analytical applications include “Contour, Quiver, Code Workbook, Notepad, and Fusion,” and separately inventories data integration, models, developer tools, use-case development, delivery, governance and management [1]. Its overview navigation also includes observability. The source supports explicit breadth tracking; it does not require every family to be fully specified or implemented before a coherent payroll slice.

**“Action transaction” does not establish atomic external delivery or comprehensive information-flow safety.** The Actions overview says an action is “a single transaction that changes the properties of one or more objects” [4]. The permissions page separately states: “These controls do not extend to the action's write,” referring to row/column controls on reads; markings or Classification-based Access Control must protect downstream flow. It also says: “If notifications fail to send for whatever reason, edits may still succeed” [10]. Console therefore needs its own explicit write authority, propagation and external-effect contracts. The vendor's noun does not prove those properties.

**Fusion's “Actions” are not automatically Ontology Actions.** The Fusion formulas page demonstrates `action.copy_range`, `action.submit_to_region`, `action.toast`, serial and parallel formulas. It separately requires target-sheet edit permission and dataset edit permission for the latest changes to build [9]. Its overview advises using Ontology Actions when adding data to the Ontology [8]. A capability map should distinguish sheet-local operations, dataset sync and governed object mutation rather than merging similarly named concepts.

**Sharing a sheet is not necessarily partial-field access.** Fusion's update/history page says recipients lacking read access to referenced datasets “will not be able to open the document” [6]. That source describes a specific permission model, not evidence of arbitrary granular collaboration. Console's intended current resource/field/action projection model must be verified independently.

**Schema flexibility is not migration-free.** Current schema documentation lists changed primary keys, input datasources, property types/IDs and deletion of edited properties/struct fields as breaking changes. It requires an explicit migration before saving relevant changes; a replacement pipeline must complete before the new version becomes queryable. It also states that the framework does not support migration instructions on object primary keys and permits at most 500 migrations at once [5]. Some available migration choices discard edits. Console must preserve its stronger historical-evidence requirements instead of copying a destructive option.

**Historical inspection is bounded by retention and loaded history.** The 23 July 2026 Time Travel release states that Bisect only searches loaded versions and inspection is possible only where data remains available under retention; the feature is beta [15]. A timeline, hash, or version number does not prove original data is still recoverable.

## Observable usability and accessibility acceptance

Palantir's current “Ontology design: Validation” page states: “A structural review confirms that an Ontology is semantically coherent and technically correct. It cannot confirm that anyone can use it.” It recommends questions drawn from recurring real decisions, participants who did not build the model, unassisted attempts before coaching, and recording correctness, investigation time, confusion, searched terms, paths and assistance [13]. It warns that building questions from existing model coverage systematically excludes missing concepts and relationships. Keep important questions that the current model cannot answer; a failure is evidence.

This gives two complementary checks for Console. Evaluate the first workflow through its actual application, including safe submission and recovery. Separately, at the appropriate shared-object acceptance stage, test whether users can discover and traverse the underlying business model through general authorized views. Palantir excludes purpose-built dashboards for its model-specific drills because those can mask weak semantics; that restriction should not be misapplied to ordinary application usability tests. Its suggested AI comparison is optional and does not override Console's Intelligence boundary. The page explicitly says an AI-only run cannot substitute for people.

W3C's “Involving Users in Evaluating Web Accessibility” states that involving disabled and older users reveals usability problems conformance checks miss, while user evaluation alone cannot determine accessibility. It recommends combining user involvement with WCAG conformance and cautions against generalizing from a couple of participants [14]. Formal task timing and high-interaction accessibility investigations answer different questions; facilitator assistance must be recorded rather than counted as unassisted success.

For the first slice, define task start/completion points and observations before implementation; iterate early using prototypes when useful; execute on real owner-backed flows before slice acceptance. Suggested tasks are: resume a saved draft in its original Company after a context switch; identify missing evidence and request permitted repair; review only the authorized portion without mistaking it for whole-run completion; reconcile an interrupted submission without creating new intent; transfer selected work without inheriting a prior actor's authority; read a historical own publication and initiate a correction without needing a future correction receipt. These are proposed Console evaluations, not externally established universal tasks.

For each task record participant context and assistive technology, intended outcome, correct completion, incorrect/unsafe completion, abandonments, errors, time, assistance, decision information encountered and recovery path. Retain unsuccessful attempts in the denominator. Distinguish task completion, downstream business outcome and user satisfaction. GOV.UK defines completion as completed transactions divided by all starts, including partial or failed transactions, and requires save-and-return starts to be matched to later completions [16]. Its specific start-page and monthly publication requirements concern UK government services and should not be copied into Console: Console deep links remain legitimate entry points.

GOV.UK moderated-testing guidance asks for believable goals that do not give away the answer, neutral instructions and observation before assistance [17]. Its dummy-data guidance says synthetic scenarios remain useful but may reveal fewer contextual issues. Synthetic fixtures are appropriate for Console preparation; they should not be misrepresented as actual user validation.

WCAG 2.2 is the explicit accessibility reference, using the dated 12 December 2024 Recommendation [18]. Relevant checks include keyboard operation, focus visibility/obscuring, labels and error identification, status messages, reflow, target size, redundant entry and accessible authentication. The Understanding pages explain status announcements and the minimum target-size criterion [19,20]. Automated checks, keyboard walkthroughs and assistive-technology evaluation should complement observed task performance. WCAG conformance is not a legal conclusion, and satisfying it does not by itself establish intuitive use.

Numerical usability thresholds should remain stated hypotheses until evaluated. A tiny convenience sample may expose blockers but does not establish population-level success rates. Define unacceptable outcome classes now—for example mistaking a pending result for completed work or submitting in the wrong Company—then evaluate the actual surfaced workflow. Schedule later capabilities' own usability checks at their acceptance gates rather than certifying unimplemented screens.
