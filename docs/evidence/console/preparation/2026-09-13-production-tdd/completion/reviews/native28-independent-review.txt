## F2 — Existing Principal cannot identify the authenticated session being validated

owner-interface-refinement.md:11-22 supplies only PgPool, platform-authz Principal and immutable RequestIdentity. Two caller sessions with different revocation/context states can therefore present identical proposed entry inputs. A DB lookup cannot identify which session authenticated this call; choosing any live session would substitute authority.

Add a separate nonserialized request authentication binding issued only by the existing owning auth/session resolver. It must identify the actual authenticated Account and session plus selected context/scope and token-carried generations needed for exact current revalidation. It is separate from retained RequestIdentity/normalized command bytes and never a boolean permission grant. No public constructor, Deserialize, From<Principal> or test-only bypass may mint this binding. Tests obtain it through the same real authentication owner. Worker calls require the separately authenticated actual worker identity; a human Principal flag is insufficient.

An alternative is to accept verified transport authentication material and invoke the real authentication resolver inside the owning entry before beginning finalization. In either design, explicitly specify how correlation data reaches fixed participants and remains transaction-scoped. Pure ontology/application can own data/codec types; it must not acquire SQLx, and payroll/domain must not depend on ontology/application. Owner-local private contexts remain constructible only inside their actual issuer path. Neither a private struct declaration nor a caller-created Principal supplies proof of session authentication.
