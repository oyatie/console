This explains run4 and withdraws the author's original contrary inference.

`syncrep.c:288-308` explicitly handles `ProcDiePending`: the transaction is already committed locally but might not be replicated; PostgreSQL emits a warning, sets `whereToSendOutput = DestNone`, cancels the synchronous wait, and lets the process die **after commit cleanup**. This supports using an exact backend termination to create an uncertain client outcome plus a now-visible primary-local commit while standby replay remains paused. It does not prove the corrected application behavior before execution.

Do not substitute `pg_cancel_backend`: the adjacent `QueryCancelPending` branch cancels the wait with a warning and has different client-output semantics. Do not SIGKILL PostgreSQL: abrupt backend death introduces crash-recovery behavior and wider blast radius.
