Repeatedly materializing2000 event/day packages can read84,000MiB before other evidence. Chosen candidate strategy: an owner-sealed immutable dependency inventory for an already admitted retained unit can be reused through17 registered owner adapter. It binds exact source revision/semantic digest, decoder/owner build, exhaustive typed child identities, purpose edges, conservative node/edge/byte counters and every original row and package required by19. It is custody evidence, not current source eligibility. New effect still re-resolves current source semantics under family guards; semantically stale or untrusted inventory must be rebuilt through explicit preparation or refused. It must never silently treat a control->receipt->snapshot backedge as another evidence root.
A reusable inventory must carry a protected acyclic closure: edges only to existing immutable earlier inventories or direct exact retained units; max depth8, children8192 and transitive caps in budgets.json. New inventory construction verifies no self/back edge; immutable membership prevents future cycle injection. Each root's downstream purpose/obligation must prevent deletion of every required reachable leaf even if upstream adoption/private pin/retention obligation expires. Do not rely on historic ADOPTED boolean, an expiring upstream pin, a cached closure hash, or merely a root content pin. Parent purpose can be added only when all referenced contents are still admitted and protected. A quarantined/disposed child prohibits new positive adoption; failure preserves acknowledged input.
Required lifecycle contract: destructive child mutation resolves all current reverse memberships/purpose protections under the same unit/family guard discipline, using an exhaustive indexed membership relation maintained by the custody owner. Adding a root purpose cannot race deleting a child: it must have pre-established a live protection reservation covering the exact immutable closure, or lock/check all leaves itself within budgets. Preparation of that reservation is an explicit guarded owner action over bounded pieces with durable progress, not fake atomic source publication. During preparation provisional pins retain the successfully protected subset; failed/cancelled preparation releases them only after conclusive terminal/no-unknown reconciliation. Completion is exposed only after all members are protected and a final version-bound closure check; private pin release cannot shorten it. Reservation-to-domain-purpose transfer is atomic at final publication and preserves the same full closure; retries use exact receipts. Pending/UNKNOWN reservations remain protective. No asynchronous best-effort propagation after publication is allowed.
This is a selected capability requirement over17 existing owner, not a deployed seal/reservation schema. Concrete membership/reservation storage, purpose/obligation DTOs, counted canonical inventory format and SQL transition bodies are explicitly open F01/F03. Until those enforce the invariant, only full direct expansion/protection within budgets is eligible; sealed-inventory fast path remains unadmitted. Do not assert pilot readiness from a proposed shortcut. Direct per-leaf pins are simpler for small commands and remain the reference behavior; reusable inventories pay complexity only where measured amplification demands it.
