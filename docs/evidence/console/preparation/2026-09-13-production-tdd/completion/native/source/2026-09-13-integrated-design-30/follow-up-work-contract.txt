DC30 — Initiate or link accountable work without requiring its future result
This refinement replaces DC29/IC28 case response references where they conflict. All other29 contracts remain selected. AR29-F01 was confirmed; AR29-Q01 was an unspecified creation/reuse condition, not a proven inevitable deadlock. This is a design-only candidate with no user approval or executed product/SQL/Verus/load proof.

1. One response input and one workflow owner
CORRECTION_PENDING carries nullable correction_receipt and FollowUpWorkIntent. Null means no completed correction result is being claimed; it is valid on the first correction need when the handler has no source-write permission. Nonnull must resolve an actual authorized correction effect whose subject/source/lineage matches this case item; inquiry, task-creation, transfer, generic success or preparation receipts are not correction proof. Both forms remain pending. CORRECTED still requires actual matching correction receipt AND the corrected approved publication accessible to the subject under current policy. Pending work never substitutes for either result.
FollowUpWorkIntent is a closed CREATE(definition_revision,target:ObjectRef) or LINK(definition_revision,task:TaskRef). The definition is the existing governed WorkDefinition revision/owning process, not a new free-text process or callback. CREATE carries no future task ID/assignment/receipt. LINK explicitly chooses a permitted existing task at its expected epoch/control. OUTSIDE_SUPPORTED_PROCESS uses the same intent plus its subject-readable explanation; it remains pending with no implied legal/source correctness. No new reason-specific action, workflow interpreter or public task-creation service is added.
The handler's existing response composer defaults a valid work definition and target from the current typed case/item/source relations. It shows the proposed work and permitted target; the handler can explicitly choose another allowed definition/target or an existing compatible task. Draft/preflight perform no task creation. User never creates a task elsewhere merely to complete this form. Registered configuration must supply a bounded definition/coverage and actual supervised repair route before this case capability enrolls; configuration revoked or unavailable afterward preserves draft and exposes that existing repair path, never fabricates a definition. Choosing work does not confer authority to execute its domain action.
CREATE target is an exact existing Company ObjectRef. A fixed resolver registered with the existing work definition validates its admitted target type, same historical subject and actual source/publication lineage or exact case object for a case-targeted process. Issue prose is not a source selector. Target must already exist and be permitted for this request; source/parent refs are never allocated speculatively from a comment. Candidate scope includes only existing admitted definitions/owners; unsupported modules are not activated by selecting a work request.
LINK validates current nonterminal task, exact immutable definition/target, expected control/assignment and current link permission. Its work criterion and target must cover the case item's requested remaining obligation. The original inquiry task may be reused ONLY if it already has that same admitted definition/target and remaining criterion; no implicit conversion from inquiry handling to source correction or broader access. An unrelated task, terminal task, wrong Company/subject/lineage or broader scope without link authority is rejected with preserved input and permitted repair. Several responses/cases can link a compatible task; this creates associations, not new assignments/charges. A transfer later changes current assignment without rewriting historical response evidence.

2. Constructive transaction, authority, concurrency and result
The existing payroll.review.respond owner validates current handler, distinct human, case/item/task expectations and complete disposition coverage; normalizes and seals exactly the typed original input through the existing common owner. Allocate actual response identity and, for each CREATE item, an actual task identity once under original command ownership before obtaining the full protection plan. These reserved IDs are private owner results, absent from sealed input/fingerprint. After receipt-first replay, derive the complete bounded plan for response content, work creation/link, task/assignment facts, Group capacity/routing/availability and retained evidence. Include all new real unit/task IDs and all lock modes before acquisition in existing total order; restart bounded discovery if earlier resources are found, never upgrade/lock a new earlier resource late.
workflow.resolve_response_work(Conn,Ctx,target:action-types::CaseResponseWorkTarget,intent:action-types::FollowUpWorkIntent,ProtectedPlan) -> control-types::FollowUpWorkBinding
This is a fixed borrowed participant using the existing workflow task creation/link/assignment owner and WC16 routing/capacity helpers. Only payroll.review.respond is admitted as this caller in this slice. Caller cannot pass allowed=true, SQL, arbitrary executor, chosen output task ID, assignee grant or a fabricated actor. No pool/commit/network/detached job.

It validates finite definition/obligation/coverage and current eligible candidate plus capacity. Current assignment-conditioned policy changes take earlier Company authority EXCLUSIVE as WC16 requires. LINK takes the expected task's current owner guards and validates compatibility as section1. It does not change assignee, task definition/target, epoch, counter or business outcome. Retain exact admitted task/control/assignment evidence and append the response association. Reuse or later transfer never transfers another person's sealed command or private draft. Receiving work gives only permissions already derived by current Cedar; source correction/publication still requires its own policy, inputs, gates and receipt.
Return FollowUpWorkBinding(actual TaskRef,actual definition_revision,actual target) only after the underlying rows and link exist. Follow-up source work may finish while the case still awaits publication; no task terminal receipt alone resolves the case.

3. Physical ownership, retention and projection
workflow_response_work_links is one native workflow-owned association projection with key(org_id,origin_command_id,item_id), unique(org_id,response_id,item_id), actual case/response/issue revision, task and admitted assignment/control revision, and CREATE/LINK discriminator. It stores no narrative, policy copy or second mutable task. Same-Company FKs to task/control and deferred exact response membership apply. CREATE correlates task origin to this same command/item; LINK proves actual existing task from sealed intent. Definition/target resolve through immutable task control and must equal resolved common response content. Current task revision may later advance; stored admitted revisions remain historical facts, never a permanent equality-to-current constraint.
Deferred bidirectional closure checks every resolved pending/outside content item has exactly one link and every link has that actual item/response/content/common provenance and final command receipt. LINK input expected task equals the admitted snapshot; CREATE definition/target equals actual created work. No extra item, orphan link, orphan newly created task or incomplete assignment/charge closure can commit. task creation origin and all matching initial assignment/receipt fields use actual command identities, not a future receipt hash. Fixed decoder and independent native owner constraints enforce exact enums/types/tuple equality; application credentials cannot raw-write around them.
ProtectionPlan includes actual WorkDefinition/coverage/target facts required by the selected work criterion, task/assignment evidence, link and case response content; Use existing DRAFT_CHAIN for exact common definition/coverage/response revision chains, OWNER_SUBMISSION for original command bytes, and the existing closed selectors for any required native domain source. Task, assignment, charge and association identity/provenance rows are nondisposable native integrity metadata with same-Company noncascading references; no payload-removal procedure may delete them or the actual referenced native receipt history. This correction adds no WORK_EVENT selector or untyped retention class. Immutable association metadata survives as lineage. Active case/work, unknown attempts and independent correction obligations block release of required payload; inquiry withdrawal cannot release an independent pending correction obligation. All reserved late evidence is filled and adopted before commit under existing26/28 lifecycle protocol. No total recursive graph expansion or metadata-only pin substitutes for the actual required originals.
All work refs/bindings and resolved content are internal. PublicOutcome/AuthorizedScreen reproject current requester/handler permissions: permitted pending explanation and related work link only, never hidden assignee, capacity, routing candidate, source wage, private task input or internal expected epoch by direct serialization. Unknown/denied links produce permitted pending information without hidden placeholders. Replayed historical response binding cannot grant current task access. Manual CREATE/LINK uses the same owner, validation, gates, concurrency and projection as automated defaults.

4. Positive traces, versioning and verification boundary
First correction: handler without wage-write permission selects permitted correction definition/target; correction_receipt=null, CREATE intent seals; workflow creates ACTIVE or supervised UNASSIGNED work; response content records actual binding and case stays pending. Qualified source owner later executes its normal action under its own current authority. A later response may LINK that existing compatible task or a publication task and attach actual correction receipt; only corrected approved publication permits CORRECTED. No fabricated prior receipt.
Existing work: handler LINKs current compatible work; expected-task/current policy mismatch preserves input, otherwise association commits with no new task/charge. Shared corrective work can cover several cases only when exact subject/source criterion and link rights validate for each. Outside process: CREATE a permitted case-targeted follow-up or LINK compatible work; original inquiry task is reusable under section1, not automatically. No candidate leaves visible accountable UNASSIGNED work. Fault after task creation but before common content/receipt rolls everything back; ACK loss reconciles original command before retry. All64 mixed item dispositions bind exact generated work, with no silent partial response.
