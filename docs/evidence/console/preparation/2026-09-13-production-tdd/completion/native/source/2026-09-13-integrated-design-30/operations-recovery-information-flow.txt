OR28 — Operational, recovery and information-flow contract
Proposal for integrated review. This file refines17 RR/RM and21 IF. It does not certify deployment, legal retention rules, storage-provider conformance or Verus proof.

A. Explicit process and credential ownership
Existing console-app authentication constructs request principal; public HTTP/SSR never accepts authoritative actor, Group ownership, policy verdict or issuer credential from payload. Account identity persists independent of Employment and Company lifecycle. Existing application/domain use cases own command dispatch; domain adapter owns the one Company transaction; supporting owners borrow that transaction and never checkout/commit another connection. RLS cell remains Company, tenant remains Group. Group control queries require owner-only narrow access and never arm app.current_org with Group. Group-level batches issue Company child commands with distinct receipts and expose authorized aggregate progress, not cross-Company atomic payroll.
Serving roles are console_rt for approved reads and console_ontology_cmd for validated command dispatch; NOLOGIN console_owner_commit_writer owns fixed SECURITY DEFINER functions with pg_catalog-only search_path and qualified names. No raw writable pool reaches untrusted HTTP handlers, background script or browser. Every process that holds console_ontology_cmd is explicitly a trusted executor and appears in deployment enrollment. SQL validates structural/current-state/source/receipt constraints independently but does not claim to execute Cedar through an allowed boolean. A compromised authenticated execution service is outside the verified projection theorem and is contained by DB privileges, egress and operational monitoring, not waved away.
Selected destructive-issuance design: sole credential-holding issuer, NOT provider generation support presumed from S3. Extend existing storage version methods through an issuer process using existing Console worker/dependency deployment patterns; ordinary app, cleanup planner and retry workers have no provider DELETE capability. Provider exact-version deletion and exact-version HEAD/list semantics must pass conformance before enrollment. Independent journal holder extends the existing external audit custody service boundary with append/head operations; it is not the existing sign API and cannot be considered installed. Holder uses a separately operated transactional PostgreSQL store for stream head+immutable entries (native transaction atomicity and UNIQUE, no custom consensus), independent append-only backup and pinned signer keys; deployment must prove a separate failure/administrative domain from restored Console. Missing holder leaves physical cleanup disabled; preserve safe business operations that do not depend on missing current authority. No user data payload is exported to this journal.

B. Issuance and late stop semantics
ProviderStep={org_id,unit_id,copy_id,provider_binding_id,bucket_object_identity,nonnull_version_id,expected_sha256,expected_bytes,job_id,step_id,manifest_sha256,serving_generation,cancel_generation,authorization_receipt}. All IDs resolve same Company/exact immutable registered location; arbitrary URL/bucket/key from a job cannot select a new target. Length/codec constraints use inherited19/24 identity framing. Issuer receipt fields are {step_id,dispatch_sequence,generations,target_digest,state,provider_request_id?,evidence_digest?,journal_head}. Null provider request identity is allowed only if provider never issued one; null is not no-effect evidence.
Per step states: PREPARED (no issue authority), AUTHORIZED (durably registered potential issue), ISSUED_UNKNOWN, CONFIRMED_RETAINED, CONFIRMED_REMOVED, IDENTITY_MISMATCH, NOT_ISSUED. Authorizing means the process may already have crossed its network send instruction, even if it crashes before recording ISSUED. Therefore AUTHORIZED is unresolved on restart until drain/readback proves otherwise. No time-based retry with a new identity. Same exact step request replays issuer state. CONFIRMED_RETAINED is terminal only with both trustworthy exact-version retention evidence AND proof every previous send capability/request is terminal or conclusively prevented. HEAD200 alone leaves the step unresolved because an earlier accepted DELETE can finish later. Retransmission requires a fresh explicitly authorized attempt under the same original step with current generation; never while an earlier request can still act. WORM/hold rejection retains material and records typed result; it never becomes removal.
Hold/cancel/fence first stops new authorizations at the sole issuer and advances its durable generation, then enumerates every AUTHORIZED/ISSUED_UNKNOWN older-generation step. Acknowledgment is STOP_PENDING until all prior send capabilities are conclusively disabled or each in-flight effect resolved. A paused old process cannot be assumed dead after lease expiry. Replacement requires operator/runtime credential revocation and network fencing with readback; otherwise no replacement issuer may claim exclusivity. Already accepted irreversible requests can complete after stop. UI distinguishes HOLD_RECORDED, STOP_PENDING, STOPPED_RETAINED and PARTIALLY_REMOVED; no claim a hold restored deleted bytes. A hold is not declined because deletion raced; it records preservation of the remainder and an incident.
Each external step sequence: local committed intent/quarantine -> independent INTENT acceptance and fresh readback -> sole issuer current eligibility/generation dispatch authorization -> provider request -> exact-version observation -> local typed outcome/ledger receipt -> independent outcome acceptance. No provider I/O inside Company transaction. At any lost reply keep exact identity, attempt and protections. Next batch cannot start until prior outcome is conclusively reconciled and journaled. Cancellation-before-any-issue uses17 two-stage terminal ACK; issued/unknown work cannot be reclassified as cancelled no-effect.

G. Current recovery source matrix and transitions
Selected ordinary-data recovery design for testing: PostgreSQL primary plus independently hosted synchronous durable replica for acknowledged Company commits, with WAL/timeline/LSN readback and independently fenced failover. No application success ACK before synchronous durability boundary. Standard PostgreSQL/managed HA semantics are reused; no invented distributed commit engine. Each acknowledged receipt and all same-transaction gate/work/pin/publication facts live on that durable timeline. The disaster class where every acknowledged replica is lost is outside zero-loss claim and blocks automatic readmission; separately archived backups may recover data but not prove missing newer outcomes absent. Deployment must demonstrate independent failure domains and credential separation, otherwise this selected durability boundary is not met.
Authority classes and sources: (1) Account credentials/security, Group topology/grants/identity bindings: independently current authenticated authority timeline+fence; if unavailable, supervised fresh identity/permission re-establishment by independently verified recovery operators, not restored passkeys. (2) Company command/attempt/gate/work/capacity/publication/protection: current acknowledged replica timeline with completeness LSN and exact schema; absence is conclusive only within proven complete interval. (3) Physical deletion/cancel/issuer generations: independent holder current head plus immutable scope manifests and exact provider readback. (4) Serving generation: independent holder fenced-generation event plus actual old process/network/credential fence evidence. (5) Source qualifications/retention policy: independently retained source identity and current revocations/validity evidence; unavailable qualification blocks new use, not historical receipt disclosure when otherwise authorized.
Each reconciliation record stores class, scope, source identity, timeline/generation, known-complete watermark, nonce/freshness evidence, mismatch set and decision. If no complete business timeline survives, affected attempts remain UNKNOWN and protected; never infer no effect from backup absence. Bound dependent scope through exact retained relations; if incomplete isolate whole affected Company/Group control plane. No automatic replay of historical queue contents. Trusted human recovery cannot assert arbitrary past no-effect without independent evidence; it may establish new forward authority with an auditable unresolved boundary and affected effects still isolated.
Transitions ISOLATED -> OLD_SERVING_FENCED -> CURRENT_SOURCES_ESTABLISHED -> RECONCILED -> ADMITTED are evidence-bound. Isolation disables customer reads/SSR/authenticated downloads/streams/jobs/notifications/cleanup; health/operator recovery only through separate restricted channel. Final admission receipt binds source image/schema, binary/codec/projection manifests, current authority and serving generation, journal applied/current heads, timeline/watermarks, retained/removed checks and excluded unknown scopes. Final catch-up must prevent a gap between verified watermark and admitted writer; either continuously follow current authoritative stream or keep writes fenced until handover completes. Partial Company admission requires proven dependency closure and safe Group aggregation; otherwise remain paused.
Recovery trial target<=4h from confirmed fencing for specified retained dataset; ordinary backup RPO<=5min is a separate hypothesis and cannot relax zero loss at declared acknowledged synchronous-commit boundary or lossless journal/fence facts. Missing source evidence may safely exceed RTO and means failed availability target. Backup retention35d is configuration evidence only, not proof of actual recoverable/erased horizon; inventory WAL/base backup/version copies. No claim crypto-erasure or statutory compliance follows from local deletion or signatures.

H. Dispatch ordering and current authority refinements
The independent holder is the SINGLE dispatch/stop ordering authority. Its transactional stream state has (org_id,serving_generation,cancel_generation,stop_state,current_head) and per-step immutable target+dispatch identity. authorize_dispatch(expected_head,expected_generations,step_id,exact_eligibility_receipt,manifest_ref) atomically verifies no effective stop and exact current generation, appends DISPATCH_AUTHORIZED and changes step from PREPARED to AUTHORIZED. stop_dispatch(expected_head,scope,stop_id) atomically advances generation, closes new authorizations and appends STOP_REQUESTED. Console DB rows are mirrors and cannot override the holder's order. Only the sole issuer with direct DELETE capability can act on authorization, and each authorization remains a potentially active capability until terminal proof. Holder state survives independently; losing holder state blocks dispatch and replacement.
Local hold/cancel/policy change first records REQUESTED and queues an exact idempotent stop to holder; pending state is displayed. Effective external stop is holder stop commit, confirmed to caller by fresh signed ACK. Every deletion-eligibility-invalidating transition follows this route before reporting external protection effective. Holder-stop-before-dispatch forbids dispatch; dispatch-before-stop joins the unresolved set to drain, even if local mirror ACK is missing. Local hold remains protective for SQL cleanup immediately under its own owner guard. Cross-resource protection completion waits for both sides; partial result never says all stopped. On restart reconstruct issuer mirrors from accepted holder entries and independently retained manifests, preserving AUTHORIZED uncertainty. Missed local mirror records are repaired; holder entries are never deleted to match an old database.
Eligibility receipt binds exact manifest/obligation revisions, issuer scope and bounded not-after dispatch time, as well as generations. Issuer checks time before any send and cannot reuse authority for another target. Time expiry stops future authorization but never proves prior issued effects absent. Holder does not evaluate arbitrary SQL policy: issuance enrollment requires all invalidating owners to join the stop protocol, private command credential separation and current policy receipts. Missing participant prevents physical deletion enrollment. Uncontrolled administrative provider deletion remains outside application guarantees and must be excluded by provider credentials/deployment controls.

I. Replica and recovery authority precision
Selected acknowledgment configuration for tests is PostgreSQL synchronous_commit=remote_apply with one specifically admitted independent synchronous standby; standbys, timeline and promotion eligibility are recorded in deployment admission. No asynchronous fallback, no unadmitted standby promotion and no success receipt through another local connection while a commit is waiting for remote application. Loss of eligible synchronous replication blocks new durable success; timeout becomes UNKNOWN. Before promotion, fence old-primary writes AND egress, replay through the independently confirmed promotion watermark, verify timeline ancestry and do not admit read traffic until recovery checks finish. Standard HA tooling must provide actual fencing readback; a leader lease alone is insufficient.
An acknowledged watermark does not prove absence of unacknowledged old-primary commits. Every known dispatched/in-flight command beyond complete captured timeline remains UNKNOWN; local-only receipt visibility is not a success at the declared durability boundary. Reconcile complete old-primary WAL and egress/dispatch journals where available. If loss hides the possible command set, isolate the wider affected Company rather than assuming none existed. External workers only consume effects after their transaction meets remote-apply durability and current dispatch admission. Unknown local work cannot create external effects through a legacy outbox reader. Read-after-write receipt endpoints use the same admitted timeline/durability checks.
Account/security, identity bindings, topology and policy/grant roots use the SAME protected synchronously durable authority database timeline with explicit complete LSN, not an unnamed provider. When a complete current authority timeline cannot be established, all affected sessions/credentials/grants are untrusted and ordinary service stays isolated. Forward re-establishment requires RecoveryRoot28:2-of-3 independently held Ed25519 operator keys pinned in the external holder's admission config (key IDs and revision bound in deployment manifest), with holder-recorded key revocations/current generation. Restored Console DB cannot choose or rotate these keys. Recovery proposal binds Group, Account identities to preserve, fresh identity verification receipts, exact new grants/credential enrollments, denied/unresolved scopes and expiry; two distinct currently admitted operator signatures authorize that exact proposal, and the holder appends it before Console applies new forward authority. Operators may not certify historical no-effect solely by signature. This is an explicit deployment trust-root proposal requiring separate provisioning/evidence, not job-title-derived tenant power. Missing valid keys/current holder cannot be bypassed with restored administrator login.
Projection validity: ordinary synchronous response/live event performs final current context+policy check at emission admission; per-session outbound sequence is fenced by security/context/serving generations. Completed revocation closes later emission admissions and stale subscriptions. Bytes already admitted/emitted can be in transit; no claim to retract them. Buffered work stores protected resource refs/intent, not reusable public DTO authority; each later event/download is reprojected under current policy before admission. Egress follows recipient-specific current admission and the above explicit in-flight semantics. Receipt replay grants no bypass to this final disclosure check.

K. Exact dispatch terminal evidence (supersedes J terminal shorthand)
Every authorization has DispatchRef(stream,step,dispatch_sequence,authorization_event_id,target_digest,serving_generation,cancel_generation). The holder checks authorization_event_id equals enclosing event ID, target digest resolves the immutable ProviderStep and generation equals the admitted current stream/step state. First sequence1; reauthorization increments exactly1 without wrap. Accepted authorization owns that exact step's current nonterminal dispatch. A terminal outcome must match every DispatchRef field under holder head/step CAS. Duplicate exact terminal event replays its old ACK; it cannot change a later dispatch's state. Cross-step, stale-sequence or conflicting bytes fail.
TerminalStepEvidence is a closed union: NOT_ISSUED requires conclusive NoFutureSendProof and no provider observation; all issued outcomes require exact dispatch-bound provider terminal proof and version observation. NEVER_SENT is accepted only from sole issuer's durable send-admission record when it proves no provider send occurred and permanently closes that dispatch capability. FENCED includes actual process/network/credential fence; it proves no future send but alone does not prove no earlier send. Consequently NOT_ISSUED additionally requires holder/issuer complete admission history showing no earlier send; an uncertain crash after admission is UNKNOWN, not NOT_ISSUED. Provider NO_REQUEST variant likewise requires proven NEVER_SENT, not mere fence. Fixed adapter validates terminal provider evidence against its admitted contract digest and exact request/version. Hash/ref presence is not proof validation.
CONFIRMED_RETAINED requires closed prior request with CANCELLED or FAILED_NO_EFFECT plus no future-send proof and exact PRESENT_MATCH observation. CONFIRMED_REMOVED requires REMOVED terminal plus exact ABSENT observation and closed retry capability. IDENTITY_MISMATCH quarantines; it cannot complete cancellation or deletion job. Unsupported/nonconclusive provider behavior remains UNKNOWN and blocks copy removal/reuse. No provider request is invented when provider is unavailable before send.
Reauthorization from CONFIRMED_RETAINED or NOT_ISSUED is a new DispatchRef for same immutable step, accepted only after prior terminal CAS, current lifecycle/hold/cancel eligibility and fresh owner receipt, current serving admission, unexpired new validity and no accepted job STOP. Previous send capability stays closed; reauthorization does not reopen it. A delayed retained proof from sequence1 cannot terminate sequence2. Stop orders against authorization at holder; already authorized sends remain potentially in flight until exact terminal reconciliation. Typed proof bodies may reference encrypted independent evidence artifacts; holder verifies actual artifacts/body correlations, size and hash under its admitted validator before accepting terminal CAS.

L. Routine dispatch closure
DISPATCH_CLOSED is the normal sole-issuer proof, distinct from full disaster fence. Each DispatchRef permits at most one durable send admission and one provider request; HTTP client automatic retries/redirect resends are disabled. Retry requires a fresh holder authorization/DispatchRef after conclusive previous terminal state. The issuer's durable per-dispatch row records accepted admission ID, exact provider request identity, current worker capability generation and terminal observation. A closure transaction CAS permanently closes that dispatch admission, verifies the one admitted request is terminal under the provider contract and records that no worker retains an uncompleted network-send capability. It binds the ledger head and the complete one-send terminal manifest into DISPATCH_CLOSED; holder checks those exact correlations and admitted issuer signature. This can complete a normal successful or conclusively failed request without rotating all issuer credentials.
An admission whose worker crashed, whose call may still be in flight, or whose capability return cannot be established cannot issue DISPATCH_CLOSED. It remains UNKNOWN until complete request reconciliation and capability closure, or the stronger FENCED procedure. Merely writing closed=true is insufficient while an authorized worker might still send. Fenced issuer code and OS/network/provider enforcement are explicit external assumptions beyond Verus application proof. NEVER_SENT proves zero sends and is required for NOT_ISSUED; DISPATCH_CLOSED binds exactly one admitted sent request and therefore cannot prove NOT_ISSUED. No hidden retry path can reuse a terminal capability.
