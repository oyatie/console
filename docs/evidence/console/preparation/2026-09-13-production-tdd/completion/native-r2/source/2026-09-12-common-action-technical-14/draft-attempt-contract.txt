DA1 — Common draft and execution participation

DA1.1 Four control tables, one editable history
schema-candidate.json specifies input schema revisions, immutable runtime bindings, draft controls and submission attempts. ont_instances/ont_instance_revisions remain the only editable payload history. DraftId is InstanceId. Control stores immutable Company/action/target/custody/intent-slot/creator and current lifecycle/editing epoch, plus active attempt; it does not have another input revision counter. Current input revision is the common head UUID/version. Immutable creation command and Company receipt make start retry-safe; partial unique active-intent binding prevents two tabs creating duplicate active drafts. Explicit new request requires new owner-issued intent slot, never randomizing on each GET.
Account custody references exact creator Account; Work custody references existing atomic WorkItem and its Company. No internal/external or title discriminator. Work start takes the current assignment fence before finding/creating its draft; all work starts and handovers share that fence. No task from a GET. Account-only users may own a Company-targeted request without Employment. No-target-Company forms remain outside this Company-scoped draft contract.
The editing token is random256bit opaque context nonce stored on control, issued only by current authorized start/resume. It is continuation evidence, not a bearer grant. Current Account/custody/WorkItem assignment generation and control epoch must still match under locks. Same-epoch resume returns the same nonce to support multiple tabs. Every seal/unseal/handover/terminal transition advances epoch and rotates nonce; A->B->A never validates A's old token. No customer-supplied epoch can renew it. A fresh login may resume the same still-authorized editing context; session IDs are not immutable command identity.

DA1.2 Save and common instance helper
Consolidate CAS/replay from ontology/rest::instance_revision_writeback into the common ontology owning application/adapter boundary, reusing its existing helpers. Convert reusable in-tx mechanics to borrowed PgConnection as needed; existing Transaction wrappers delegate. Preserve one owner and existing business tests. Pure schema/patch/normalization lives in ontology/application; SQL/locks in ontology/adapter-postgres. REST and Leptos server functions are sibling adapters. No SQLx in the pure domain/application and no adapter-to-adapter dependency.
Save first parses a bounded exact patch, fences current authority/work/custody, and rechecks its same-command receipt under the common order. Proven prior success returns a current-disclosure-filtered historical ACK without restoring the old head. Only proven absence enforces new save eligibility, context, exact expected common revision and current property write rights. Reconstruct from locked authoritative head, apply allowed field patches, validate partial schema and source/provenance shape, then append a full common revision and minimal receipt atomically. Stale expected head fails before no-op handling. Equality includes schema/provenance/basis, not just displayed values. Accepted equal input returns ACK with no new revision. Save does not consume a gate or change domain/work completion.
Selected two-tab rebase is FD1's bounded deterministic field-group merge: authoritative retained base, current permitted base/server/local projection, no overlap in coupled groups, same epoch, max2 rebase retries. Hidden conflict is not permission to overwrite. Restore and schema upgrade use the same guarded append: at most2pinned revisions compared; authorized selected fields only, no Company/action/target/custody retargeting. Unsupported schema/base loss/integrity failure blocks auto-merge/seal and provides authorized recovery. Browser save ACK/offline/leave behavior remains candidate11; no raw draft in persistent browser storage.

DA1.3 Seal and immutable attempt
Seal requires acknowledged current revision+context, exact current schema/owner codec, valid required source/evidence and normalized complete business input. In the same Company transaction allocate attempt_id and fresh domain_command_id, persist ONE immutable normalized submission snapshot, pin source revision/evidence, set attempt READY, set control SEALED/active_attempt and rotate epoch. The snapshot is necessary to prevent later default/source changes from rewriting the command; it is not another editable history. normalized_input and its canonical digest are retention-governed payload, never copied into generic audits or ACK receipts. Snapshot size has its own64KiB cap; server-derived population manifests stay owner reference objects, not thousands of duplicated rows in the form.
When policy requires an execution gate, an explicitly requested seal allocates attempt_id/domain_command_id and the governance request ID/payload revision first, then computes the final command fingerprint including that fixed gate reference. The governance owner creates the pending exact request in the same seal transaction, binding that fingerprint. Approval/revocation changes separate decision state; the request payload revision and IDs stay immutable. No hash includes its own stored digest or a future approval result, so there is no circular fingerprint. A pre-existing gate can be reused only when its exact immutable command binding already matches; otherwise cancel/reseal through a newly authorized request. Seal can succeed with pending approval while execute remains blocked. It does not itself approve or decide payroll.
The immutable attempt binds original Account, CompanyActor, registered action/type/schema/codec, target/create scope, expected business/source refs, normalized input/reason, original custody and assignment generation, sealed source revision/epoch, domain command, and required exact gate request if present. Gate approval is never a saved boolean. Current gate policy may reject a no-gate old attempt; it cannot silently attach a new gate or edit the old payload. Repair conclusively cancels and reseals as a new attempt. Create target IDs are server allocated before sealing and retained in the normalized target; retries never mint a new target.
Mutable attempt state is only READY, SUCCEEDED, REJECTED_NO_EFFECT or CANCELLED with monotonic state_revision and typed receipt/result refs. No separate committed RUNNING phase for this one-DB atomic slice. An HTTP/worker observation UNKNOWN is not a fifth trustworthy business state; a locked/inaccessible attempt may be READY in a stale read while another transaction commits. No expiry/lease timer changes UNKNOWN into no effect. READY and unknown attempts stay pinned.

DA1.4 Exact order and borrowed participants
Use TX1 order1..6 for Group, Account/session, Company authority, routing/capacity, coverage/HandoverPlan/WorkItem and Group-operation parent. Refine TX1 class7 as: sorted stable intent-slot fences when starting -> sorted draft controls -> sorted attempt rows -> Company command advisory fence(s); then common instance heads/open revisions. Workflow and domain/source locks follow TX1 classes8..9; exact governance consumption stays last at10. This supersedes FD1.14's earlier command-before-control order for enrolled drafts. Every involved caller must adopt this order before enrollment; no lock upgrades. Multi-draft handover enumerates while holding assignment fence, locks sorted controls then attempts; it does not discover another draft after taking command/head locks. Cancellation of a HandoverPlan takes its own earlier EXCLUSIVE as WA2 requires, not a late upgrade.
Before seal reserves a fresh domain_command_id, take that future command fence as well as the seal command fence and authoritatively prove no existing attempt/receipt owns it. A collision aborts that reservation; never overwrite a direct command or another attempt. Cancellation similarly fences its own cancel command and bound domain command. Predeclare all participating common-namespace command IDs before locking; acquire distinct advisory lock i64 values in ascending signed order (deduplicate collisions), not discovery order. No new earlier-class command/control resource may be acquired from a late participant.
Command advisory key is first64bits of SHA256 over UTF8 domain tag console.command-lock.v1 plus NUL plus canonical lower-case Company UUID plus NUL plus canonical command UUID, interpreted signed big-endian i64. Full (org,command) key remains receipt uniqueness and equality authority. Hash collision only causes extra serialization, never identity equality. Same-command aliases use same fence, including direct domain commands with no draft. No receiver opens a second transaction. No code acquires another draft/assignment guard after the command fence.
Draft-only mutation transaction is owned by the common instance adapter. A business execute transaction stays owned by the actual domain adapter (PgPayRunPort etc.). Consumer-declared borrowed participant methods are wired in console-app, following existing EmploymentTransferPort/PayRunParticipants; app forwards to actual owners and adds no SQL. Required methods in boundary-ports.json are concrete responsibilities, not an arbitrary callback registry. Preparation loads facts without accepting old preview permissions; current checks repeat under execution guards.

DA1.5 Receipt race, execution and cancellation
Optimistic receipt lookup may avoid work but absence is not proof. Domain transaction fences/collects current authority facts without prematurely rejecting new-effect permission, takes exact control/attempt/command fences, then authoritatively reads receipt/attempt. Existing success is historical: match immutable command/actor/action/target/protocol binding and project result with current discovery/field/history rights, regardless of lost current execute/assignment rights. An undisclosable receipt is404, not a claim of no effect. Never require a fresh active task merely to disclose retained successful evidence. Retained control/tombstone/fence identity permits safe historical reconciliation after exit/disposal.
For every enrolled command, including PERMITTED direct execution, resolve server-owned (Company,domain_command_id)->attempt provenance before choosing the lock path, regardless of a supplied or omitted attempt_ref. A bound ID requires its exact immutable attempt; omitted/mismatched binding is uniformly refused within discovery rights, never normalized as a new direct command. Under the command fence recheck provenance as well as receipt. If a binding appeared that needs earlier control/attempt locks, roll back/release and restart from the correct control->attempt->command order (bounded TX1 retries); never acquire those locks late or continue as direct. Seal reservations share this same command fence, so authoritative absence cannot race an unguarded binding insertion. READY, CANCELLED, REJECTED_NO_EFFECT and SUCCEEDED bindings all remain authoritative after scope/permission changes and until the accepted replay/recovery horizon. Missing successful receipt is not absence of command provenance.
Only proven receipt absence and (for a bound command) READY allow new-effect authorization, current custody, source/CAS/SoD/assurance/gates. Verify that immutable attempt input and canonical digest match registered normalization; reconstruct no defaults from live data into the immutable command. Then exact governance consume + domain effect + immutable owner receipt/audit + attempt SUCCEEDED/control CONSUMED + applicable task/capacity finalization commit together. Common owner finalizes only its controls; workflow/source/domain owners retain their SQL. Post-commit UI/audit-projection repair cannot authorize another effect. Direct route on draft-required registration must present the exact attempt and use this same executor or refuse.
Cancel takes the same fences and checks authoritative outcome. READY plus proven no concurrent/out-of-protocol effect permits terminal CANCELLED and editable unseal with a new epoch. Execute winning first yields SUCCEEDED and an authorized business correction route. Rejection may persist REJECTED_NO_EFFECT only with established zero effect under those fences; a real transaction rollback normally leaves READY. Unknown commit, uncontactable owner or stale restored database remains unresolved and pinned. No cancellation based only on an empty ordinary SELECT. Same-command retries retain binding; max3 established no-effect transaction-conflict retries per TX1, then pause/reconcile. Terminal attempts never execute after permission restoration. SUCCEEDED clears active_attempt and makes control CONSUMED; conclusive cancellation/rejection clears it and returns the permitted draft to EDITABLE with a fresh epoch, unless a separately authorized discard/expiry makes it terminal. Old sealed_editing_epoch records original input authorization; execute compares the current SEALED control/active attempt and current assignment, not the invalidated pre-seal editor nonce.
Work handover cancels/reconciles old READY attempts conclusively before assignment transition; successor reviews allowed input and seals a new attempt/command under their own identity. Never rewrite old attempt actor. Private Account custody is not transferred. New effect with stale source can fail while old successful receipt remains valid historical fact. Business state awaiting separate review is not confused with a draft's SEALED state.

DA1.6 History, payload custody and adoption
Draft audit/receipts carry only IDs, acknowledged revision, registered action/status and authorized timestamps; no values, raw digest, user narrative title/reason, field-name deltas or complete InstanceState. New draft title is registered generic metadata; editable display content lives in policy-governed cells. Both generic instance audit and Action writeback full-snapshot paths must be bypassed through the same draft-aware owner, not merely filtered at the UI. Existing immutable receipts/hashes are never rewritten to hide prior leakage.
History uses FD1 whole-chain metadata permission and bounded50-entry keyset pages, current field projection and PA1 query/cursor rules. Receipt result refs are reprojected through owners; hashes and normalized inputs stay server-side. A pinned submitted revision does not grant private editor timeline access. Restore appends a new head, never executes business action or resurrects terminal attempt.
RR1 owns disposal, independent journal and restore fencing. Its inventory must include the normalized attempt snapshot as a distinct payload artifact. Domain adoption atomically retains complete normalized input/evidence and minimal source identity under the domain's retention/disclosure contract before releasing source payload pins. Retained lineage is not an unconditional FK to deletable revision payload. controls retain Company/draft/tombstone identity; attempts keep original revision UUID/version/digest plus verified adoption receipt, while optional payload FK/pin is released only by guarded adoption/disposal. Missing original payload later is explicitly unavailable, never reconstructed from current values. No general runtime NULL/DELETE/update of immutable input; narrowly reviewed retention functions alone may erase eligible unadopted payload, with tombstone/manifest proof and unchanged command fingerprint. Physical deletion/adoption schema/ACL and recovery harness remain W04b-05 requirements, not done by14.
