2. Retention policy without invented legal durations
Purpose, policy and obligation are typed Company common-object revisions with exact object_type/instance/revision/version/row_hash bindings. Native binding projection enforces this tuple and admitted compiled type; common JSON shape alone grants no authority. Policy's selected evaluator MAX_HORIZON_V1 has finite inputs: exact obligation, currently admitted policy for same purpose, qualified basis and current qualification, immutable trigger facts, current time, exact active holds, unresolved attempts and other required dependencies. Unknown qualifier/trigger/current policy returns UNRESOLVED and retains material. No free-form expression or evaluator plugin identifier executes tenant code.
Policy duration is explicit FIXED_SECONDS or CALENDAR_MONTHS in Asia/Seoul; no default statutory value. Fixed duration adds checked seconds to exact trigger instant. Calendar months adds months to trigger's KST local calendar date/time, clamps missing day to last day of target month, converts through admitted timezone database build; arithmetic overflow/unrepresentable date refuses. PERIOD_END trigger is midnight KST immediately after inclusive end date, preserving established source-period semantics. OWNER_TERMINAL/GOVERNED_CASE_CLOSED use exact recorded terminal instant. Closed case receipt cannot be invented from current status. Deployment chooses qualified retention basis/duration through governed approval before policy admission; algorithm correctness does not certify legal adequacy.
For one obligation release eligibility requires now>=not_before, terminal trigger valid, zero active holds and zero open/unknown dependencies requiring that obligation. Current policy extensions increase horizon; a shorter successor cannot shorten an already recorded minimum without explicit governed reduction authority and exact evidence. Evaluate maximum applicable historical minimum/current extension and all independent obligations. A result RELEASE_ELIGIBLE authorizes only the named pin transition under same current guard; other pins remain. No automatic pin expiry/TTL. Store immutable evaluation receipt with revisions, trigger, checked horizon, current hold/dependency witnesses and outcome; digest or old ALLOW never substitutes for reevaluation. Missing qualified policy is an explicit enrollment blocker for release, while acquisition/retention remains safe. A suspended policy cannot make protected content disappear.

5. Inventory needed by large native inputs
Direct evidence expansion remains reference behavior where26 bounds fit. For inherited2,000-person extreme,8,194,000 event rows and~82GiB event/day packages cannot fit fresh128MiB/65,536node plan; per-person decoding alone does not solve retention. Select a narrow immutable protected inventory for that use: no mutable graph queries, reference counters or inferred edges. Each inventory unit has immutable plan metadata and ordinal slots, each filled slot owns a real independent child content_pin with exact purpose/obligation. Child inventory must already be SEALED before being pinned; leaf has immutable owner selector. Depth<=8 and children<=8192, conservative covered counters include repeated descendants and metadata; reused digest is not free storage.
States BUILDING->SEALED->RETIRING->RETIRED; BUILDING may retire after conclusive cancellation. While BUILDING/SEALED outgoing member pins cannot release. Any active incoming pin/hold/owner requirement prevents retirement. Therefore protecting a root protects every descendant through stable direct pins, without recursive ancestor liveness query. Leaf removal tests direct incoming pins under lifecycle exclusion. Finalization cannot use RETIRING/RETIRED inventory. SEALED means complete retained closure, not current source suitability.
Create immutable plan under preparation receipt with canonical slots ordered by exact child identity, purpose/obligation and materialization kind. Allocate real late Submission/GateDecision/GateConsumption units before seal; no future content digest. Fill chunks<=256 through registered child owners after exact admission and evidence checks; complete count/digest checks are not substitute for owner's semantic completeness extraction. Finish root seal only when all declared slots filled, all member pins live and counters valid. Existing immutability and incoming pins stabilize child content protection, so root seal need not reacquire every leaf. Final domain transaction fills real late evidence, seals inventory, creates result adoption and its own root domain pin BEFORE releasing preparation root pin.25 slot1 still points to actual submitted unit, not replaced by root inventory.
Retirement atomically closes admission and verifies absence of incoming protections. Release outgoing pins only in RETIRING under current parent hold/policy and exact parent/child correlation,<=256 per receipted batch. Late hold pauses remaining release; never reopens root or claims released descendants restored. RETIRED means outgoing protections conclusively released, not physical bytes deleted. Physical disposal follows OR28 independent issuer/journal and exact location inventory. No generic pin-release endpoint bypasses parent lifecycle or releases another purpose.

6. Concurrency selection for the review candidate
The selected FIRST TEST TARGET uses existing PostgreSQL owning transactions because current single-writer domain/receipt/gate/RLS atomicity already lives there. This is a bounded integration choice, not evidence that MVCC is inherently best or scales to1m. Business history is explicit immutable revisions; storage versioning alone is not draft history. A replacement engine remains valid when equivalent owner invariants and measured migration/operational cost justify it; complete systems are compared viaCP28.
Replace27 automatic EXCLUSIVE-every-pin choice with shared unit ADMISSION versus exclusive LIFECYCLE barrier in reference target. Independent incoming-pin acquire/release uses shared admission plus exact pin row CAS; begin retirement/delete and identity/location enrollment closure uses exclusive unit barrier. Fresh protection absence read AFTER exclusion on same READ COMMITTED connection prevents phantom pin insertion. Inventory slot mutation/seal/retirement additionally locks only its exact root header; independent users pinning a sealed root share admission and do not write header/refcount. All target keys/predeclared modes sorted by20 total class+Company+canonical ID order; exclusive wins before acquisition, no upgrades. A discovered earlier resource restarts bounded plan, never late lock.
Barriers use native row-level SHARE/UPDATE locks on stable unit admission rows or transaction advisory shared/exclusive exact hashed keys where equivalent mapping is proven. Reference implementation choice is stable native admission rows; measure row overhead/fairness. Hash collisions are not relied on for identity and would only add false contention. Unit creation establishes row before exposure; missing row refuses, never creates unlocked default during disposal. Lifetime read/absence predicate remains complete across all owner aliases/triggers. Default PostgreSQL row locks do not enforce Cedar or current policy by themselves.
For source/population/current-authority predicates, retain complete registered source-family shared-reader/exclusive-writer admission as conservative comparison baseline, but record actual scope and false contention. Do not claim per-row CAS catches absence or whole-roster changes. Compare smaller invariant partitions, serializable transaction validation and ordered owners against sameCP28 histories before widening accepted envelope; coarse baseline may fail performance while remain a correctness reference. No global Company mutex added to every edit/clock event. Draft scalar/semantic-group expected revisions and current workflow/gate predicates remain exact. Data-layer replacement or changed conflict semantics is a material design revision requiring review; failure never weakens safety to meet target.

Barrier refinement: a finalizer that changes a STAGED unit/location to LIVE or fills/seals its own inventory predeclares that unit LIFECYCLE-exclusive before acquisition. Reusing an already SEALED inventory only creates independent incoming pins under shared admission. No shared-to-exclusive row-lock upgrade is permitted mid-transaction. Inventory slot deduplication is child+purpose+obligation; materialization labels cannot create a second pin for the same pinner tuple.
