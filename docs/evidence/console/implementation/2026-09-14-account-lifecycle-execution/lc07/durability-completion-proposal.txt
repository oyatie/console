# Independent receipt durability completion proposal

Read-only design review; no application modifications or runtime proof in this turn.
Original task base d03166244500aed5d3e1d058bef723a0c3d678e4; integration observed at ebea26a790b2ee363e2924ca76c5085e4c4e1ee6. This is a proposal, not an admitted implementation lane or final-head approval.
Lenses: Cartesian doubt, Systems Thinking, Red Team, Operability, Zero-trust.

## Decision
Use an opt-in shared durable transaction-completion primitive. Confirm an immutable post-commit WAL upper bound against an explicitly admitted replica policy before returning success. A successful SQL COMMIT, including a FOR KEY SHARE transaction, does not itself prove remote apply: PostgreSQL 18.6 SyncRep cancellation warns then returns locally committed success; SQLx 0.9 notices are logged, not returned as errors. Clearing synchronous_standby_names also releases waiters. Row-lock replay introduces WAL/MultiXact/privilege work while retaining these failure modes. Driver warning capture plus immutable topology safeguards is possible but larger and more brittle than explicit confirmation.

Use the existing platform/db layer, preserving caller-owned composition. Do not introduce a generic event bus, replication topology parser, or independent domain transaction. Do not modify with_org_conn globally.

## Smallest correct mechanism
1. Explicit startup/config admission distinguishes locally durable development from required remote-replay production policy. Missing/invalid required policy is failure, never inferred async fallback. A fixed admitted replica fixture is sufficient to implement the first experiment; it is not arbitrary CNPG quorum certification.
2. Acquire PgConnection, then begin its borrowed transaction; retaining the same connection after COMMIT binds capture to the transaction's server. Fresh writes and replay both use this completion boundary. Existing pool.begin() consumes its pool connection at commit, so adjust ownership at the outer owner.
3. After successful local COMMIT, obtain one pg_current_wal_insert_lsn() upper bound on the same connection and bind to trusted cluster identity, timeline, admitted primary epoch. Capture after COMMIT is necessary to cover its commit WAL. Never refresh the target in the wait loop.
4. Independently observe admitted standby replay at or past the bound on the same WAL ancestry. Use a narrowly privileged fixed observation function or a separately credentialed observation connection; runtime must not get broad pg_monitor/admin rights. A definer function must have fixed search_path, no caller-selected SQL/server identities, restricted EXECUTE, explicit output fields, and admission checks. An application_name string or numeric LSN alone is not replica identity or ancestry proof. Primary-side pg_stat_replication can supply walsender replay progress only after the replica/session identity and epoch have been admitted.
5. Bound observation time and resources; mismatch, cancellation, unavailable observer, topology change, or deadline returns typed durability-unknown. Preserve command identifier for same-ID reconciliation. Never imply rollback of already committed data or auto-reissue with a new identifier.
6. No observer can replace promotion fencing. Old-primary writes and response/egress must be fenced; promoted replicas must satisfy ancestry and watermark admission. Identity checks before/after polling detect observed changes but cannot close a subsequent failover/response race without the operational fencing protocol. Keep this explicit as an exposure gate.

A replay-only experiment can establish the regression mechanism, but cannot claim complete durable mutation completion while fresh COMMIT still trusts cancellable SyncRep. No independent tx helper may certify a receipt produced in its still-uncommitted outer transaction.

## Required experiments/tests before success claim
1. Paused admitted standby, receipt visible on primary, original writer terminated: replay cannot succeed until confirmed replay watermark; unpause succeeds with byte-identical receipt and exactly one real effect.
2. Query cancel while initial COMMIT waits: SQL WARNING does not permit fresh durable success until explicit replay confirmation. Test ordinary pg_cancel_backend separately from transport termination.
3. Clear synchronous_standby_names while waiting: release local COMMIT but explicit observer continues withholding durable success.
4. Wrong application_name peer, wrong cluster/system identity, incompatible timeline, stale admission epoch, no observer privilege, dropped observation connection: typed UNKNOWN or admission refusal, no success.
5. Capture fixed bound after outer COMMIT; continuous unrelated WAL generation cannot continually move the bound. A borrowed inner writer cannot certify its own uncommitted receipt.
6. Concurrent receipt replays produce no second business effect and no lock-induced receipt tuple mutation; bounded waiter/pool occupancy and cancellation cleanup under hot command load.
7. Lost success response reconciles using exact original command ID. No automatic different-ID retry after UNKNOWN.
8. Person employee-create and recruiting atomic composition, employment transfer effectuate/archive, InstanceRevision zero-audit replay, all six standalone owners reach the common completion helper.
9. Runtime-role tests prove least-privilege observation grants and fail-closed behavior. Local/dev explicit policy has separate acceptance and no production guarantee.
10. Independent review of observer progress witness, request count/history completeness, positive controls, and failure injection. Existing recovery test's SyncRep wait_event witness is strategy-specific; change it only via reviewed receipt to an explicit observer-wait witness that proves the request reached the new boundary. A 300ms nonreturn alone is not evidence of progress.

## Existing harness
backend/crates/payroll/adapter-postgres/tests/recovery.rs contains replay_cannot_acknowledge_a_locally_visible_receipt_before_remote_apply and lost_commit_transport_reply_replays_one_real_payroll_effect. Use real fsync-enabled two-node recovery harness, not regular tests whose server has fsync off. Root owns execution. Production topology has unresolved durability admission/fencing evidence; this design does not certify it.
