# Bounded frontend architecture comparison

Read-only comparison requested by root after the owner asked about Leptos SSR (+ Tauri 2), WASM SPA and Dioxus. No replacement decision, dependency change, new prototype or product code. Primary framework documentation was queried through Context7 on 2026-09-22; references below identify the underlying official sources. Documentation capability is not Console integration evidence.

## Finding

Leptos SSR does not require a page of textboxes or prohibit a rich persistent workspace. Current Console implements a very small subset: `payroll/ui/Cargo.toml` pins Leptos 0.9.0-beta, SSR/islands default and separate hydration; `ui/src/lib.rs:283` has one authorized payroll status-filter island; `:755` hydrates islands. There is no leptos_router dependency in the current lockfile, no persistent routed workspace state, and native Company detail currently renders its own Account page. `/organization` is a server document with JSON detail links and no native entity-create workflow. These are current implementation/product architecture gaps, not demonstrated renderer limits.

Oyatie source has entity hierarchy, contextual inspector, persistent communications and proposed-versus-committed states; HRPeople source has scoped people/employment context and task-oriented table information. Achieving those interactions requires a real route/state/command model and carefully designed layout. Switching `view!` to `rsx!` or adding a desktop webview would not supply missing workflows, typed owner bridges or spatial design. Conversely, insisting every workspace transition reload the entire document solely to minimize hydration would work against the persistent inspector/conversation requirement.

## Options and actual consequences

| Option | Rich/persistent UI capability | Console delivery consequences |
|---|---|---|
| Leptos SSR with targeted hydration | Server-rendered first document, client signals/resources for interactions, nested routed layouts can keep parent context mounted. Islands can remain for isolated interactions; official islands router uses server-page fetch/diff for navigation. | Reuses current Rust views, backend HTTP/owner contracts and Buck-native WASM/SSR work. Must deliberately implement route/state ownership; current islands-only composition does not already provide it. |
| Leptos WASM CSR/SPA | Client owns routing and mounted workspace; can preserve open inspectors, filters and conversations naturally. | Same Leptos component model, but larger client rendering surface, boot/loading/failure behavior and API client integration. Every query/action still needs current server authorization; SSR-only server projection cannot simply be imported into client memory. Full CSR-only ordinary pages conflicts with current SSR acceptance contract unless explicitly amended. |
| Tauri 2 with Leptos | Desktop shell around HTML/CSS/JS/WASM; useful for windows, OS file dialogs, menus and notifications. | Tauri is not an SSR rendering server. Standard packaging hosts static assets/SPA; a hosted HTTPS app can be loaded remotely with separate trust considerations. Adds signed installers/updates, OS/webview matrix, permissions, auth deep links and session/origin qualification. Does not improve the webpage's layout by itself. |
| Dioxus web/fullstack | Supports web UI, SSR/hydration and client routing; Rust signals/components. | Viable alternative in principle. Rewrites Leptos view/component/island integration and generated bundles; requires a new Buck-native dependency/build/hydration path and broad browser acceptance reruns. Existing domain/application owners can remain. No measured blocker currently justifies that migration cost. |
| Dioxus desktop/native | Desktop renderer uses Wry webviews with Rust UI logic; newer Dioxus Native uses a separate Blitz/GPU rendering stack. | Desktop webview and GPU-native paths are different products with different compatibility proof. Do not assume GPU-native gives browser-equivalent CSS, Korean IME, accessibility or office-editor behavior; qualify those on exact renderer/version/platform before selecting it. |

SSR and SPA are not mutually exclusive product architectures: SSR can supply the initial route and hydrated routing can handle subsequent navigation. WASM is an execution artifact, not a guarantee of SPA UX, offline operation, authorization or better visual polish.

## Maintainable candidate direction, without authorizing a replacement

Continue Leptos for the working product and choose routing/hydration at the workspace boundary from measured workflow needs. Authentication, legal/terms and ordinary resource documents retain SSR and direct persistent URLs. The actual sustained workspace needs one retained Company context and explicit owners for active entity, inspector, open conversation and draft/checkpoint identity. Parent layout plus child routes is a documented Leptos capability; important state also belongs in URLs and durable owners so reload/reconnect and a second device work. Client memory alone is not preserved progress.

A parent workspace can keep communications mounted while People/Employment/Organization/Payroll/Approval child routes change. Each selected entity links to a real owner-backed route. Cross-module state must be cleared or revalidated when Company, Account or authority changes; cached sensitive payloads and late asynchronous responses cannot outlive revoked access. Focus moves, route announcements, keyboard navigation and browser Back/Forward are part of implementation, not benefits that a router supplies automatically. Long-running work needs real pending/unknown/confirmed receipts and recovery, regardless of framework.

The current contract says hydrate only interactions needing browser state. A persistent routed workspace is such an interaction if required by the workflow; this does not justify hydrating unrelated static collections. Compare ordinary nested Leptos routing with the official islands-router approach on one actual supported journey before broad rollout. The islands-router docs describe an example, not evidence that this pinned 0.9.0-beta/Buck bundle already supports it; API/build compatibility and state-preservation behavior must be demonstrated. No generic screen generator is needed.

Tauri should be selected when a concrete desktop requirement makes it useful, not as the explanation for a rich UI. Keep server business authority in the same owners. Default remote web content must receive no broad filesystem/shell/native IPC capability; grant narrowly scoped capabilities only for explicit OS features. Existing HTTPS WebAuthn RP/origin, SameSite cookies, CSRF and document admission are not automatically compatible with a bundled custom-protocol origin. Validate the actual browser/system-login and return/deep-link design; do not weaken allowed origins or expose authentication/payroll database credentials to the desktop process. An offline payroll action requires its own durable conflict/reconciliation contract, which a desktop wrapper does not provide.

Dioxus warrants a bounded comparison only if concrete requirements fail in the Leptos path or deployment targets materially favor its native runtime. Use the same owner-backed workflow and acceptance criteria; do not count a polished disconnected example as evidence against the working integration. Required measured comparison: initial useful render, route latency, retained inspector/conversation state, interruption/reopen, bundle bytes, accessible focus/IME/320px/zoom behavior, live policy revocation, browser/webview target coverage, and Buck-native build/release maintenance. No performance or maturity ranking is claimed without those measurements.

## Primary references read

- Leptos [nested routing](https://github.com/leptos-rs/book/blob/main/src/router/17_nested_routing.md): parent components remain mounted and keep state when child routes change; Router/ParentRoute/Outlet support persistent layout.
- Leptos [islands](https://github.com/leptos-rs/book/blob/main/src/islands.md): hydrate individual islands; islands-router example offers client navigation through fetched server-rendered pages; minimizing client routing trades away its conveniences.
- Leptos [resources](https://github.com/leptos-rs/book/blob/main/src/async/10_resources.md): SSR values can serialize for initial hydration without duplicate initial fetching. Authorized serialization remains the application's responsibility.
- Tauri 2 [frontend configuration](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/start/frontend/index.mdx): static-host model supports SSG/SPA/classic MPA; server-based SSR is not natively hosted.
- Tauri 2 [capabilities](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/security/capabilities.mdx) and [CSP](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/security/csp.mdx): explicit windows/remote-origin scopes and resource policy.
- Dioxus 0.7 [native fullstack](https://github.com/dioxuslabs/docsite/blob/main/docs-src/0.7/src/essentials/fullstack/native.md), [Axum integration](https://github.com/dioxuslabs/docsite/blob/main/docs-src/0.7/src/essentials/fullstack/axum.md), [release notes](https://github.com/dioxuslabs/docsite/blob/main/docs-src/blog/src/release-070.md): web/fullstack and desktop options, separate Native renderer.
- Dioxus [renderer architecture](https://github.com/dioxuslabs/dioxus/blob/main/notes/architecture/06-RENDERERS.md): Wry desktop versus Blitz/GPU native renderer. Source on main is not a pinned Console dependency or production qualification.

No design screenshot comparison, renderer benchmarks or browser execution occurred in this review. It supports architecture discussion; it cannot certify current UX quality or release readiness.
