## Exact proposed owner/API boundary

Place the small pure evaluator in `backend/crates/platform/authz/src/platform_policy.rs`, re-export through the existing authz crate. Proposed names are design interfaces, not implemented functions:

- `PlatformPolicy::compile_current()` compiles only embedded `legacy-platform-v1.cedarschema` and `legacy-platform-v1.cedar`; private compiled fields, no caller-provided policy source at production evaluation. No accessor exposes the compiled Cedar bundle, raw permit, or an alternate production evaluation method; external callers can use only evaluate_current and its composite decision. Reuse existing compiler; no new cache framework. One compiled immutable value may be composed by the root.
- `PlatformPolicy::evaluate_current(&PlatformPolicyInput) -> PlatformPolicyDecision` validates the finite material contract below and evaluates actual Cedar. Output is `Allow { policy_identity }`, `Deny { reason }`, or `UpgradeRequired`; evaluator/transport error is fail-closed with a distinct internal reason. An Allow is a pure decision, never a transaction guard, receipt or reusable grant. Do not accept this result as an SQL `authorized=true` argument.
- `PlatformPolicyInput` is a non-Serialize/non-Deserialize application facts structure: verified credential facts, raw current subject/family projection, exact existing PlatformFeature, typed target, typed operation use and call site. It is not an HTTP DTO. A pure evaluator cannot prove a Rust caller obtained facts from the database or retained locks. Input construction by the existing owning adapter from Auth verification/current owner projection is an explicit trusted boundary; tests may construct facts to exercise the predicate, not to simulate authenticated effects.
- `PlatformTarget` is finite: Companies, Company(OrgId), Groups, Group(Uuid), Operations, PlatformAudit. Collection keys are fixed constants; Operations is the fixed platform operations scope for existing global ops reads and source-owned context-exit audits; it never confers tenant RLS authority. Company/Group UUIDs are nonnil and Company cannot be the platform sentinel. Group operations may target Company when the actual command addresses subsidiary membership. Their full typed child IDs and current Group topology remain domain/coordinator checks, not inferred from the policy target.
- `PlatformUse` is ReadProjection, Effect, ContextMint. `PlatformCallSite` is DirectPlatformOwner or DerivedPlatformSourceCheck. These come from each fixed owning operation, never request headers, HTTP method alone, route text, requested role, or user-supplied feature/use labels. PlatformFeature→Cedar action is an exhaustive eight-arm mapping with no catch-all; future enum variants require explicit policy/schema/oracle review.

Keep existing responsibilities: Auth owns cryptographic verification and the proposed non-deserializable VerifiedLegacySession; existing `guard_legacy_subject_in_tx`/`legacy_session_context_in_tx` provide pieces of current material. The required new exact-family guard belongs to the Auth application/credential owner (proposed `lock_verified_legacy_session_in_tx`), composed by the actual operation coordinator in its retained transaction through narrowly granted owner helpers. Its signature/ACL/lock proof still requires the approved full census. Do not substitute `SessionVerification::legacy_session_context`, which explicitly commits a request snapshot before returning.

`request-context` may call the evaluator for admission/navigation projections, but actual read/effect owners must call it again under retained guards before materialization/effects and after waits. Provisioning/Platform REST compose the same owner; the root only injects dependencies. No Auth credential pool may acquire business-table mutation power. The isolated force-remove transport remains isolated and consumes the same finite TenantRemove source policy under its own admitted command contract.

The current `PlatformPrincipal::new(UserId)` must not remain a production authorization constructor. Remove its unconditional allow; any retained legacy fixture constructor is explicitly unprivileged/test-only. Changing `authorize(feature)` to inspect a role snapshot alone is insufficient: that signature lacks target, operation use, exact family and guard lifetime. Existing handler positives must move through genuine authentication/current owner facts; do not weaken tests to accept a fabricated principal. Exact caller conversion and backward API handling require their later owner packet; this design does not expand a serialized internal principal into a transport authority contract.

## Raw facts before Cedar

Validate the following in the pure wrapper from server-owned verified/current facts, then project the small Cedar entities. No `family_valid`, `authorized`, `trusted=true` or role array from the client/database command arguments substitutes for these comparisons:

1. Supported policy label `legacy-platform-authority-v1`, schema identity `legacy-platform-subject-resource-v1`, numeric compiled policy version1, exact embedded schema/policy digest and actual linked SDK4.12.0; Cedar language identity remains existing4.5. Cache key scope uses platform sentinel only as identity, never tenant RLS authority. Compilation/error/warning/unknown material refuses; no stale-bundle fallback.
2. Cryptographic Auth verification precedes the adapter. Verified subject and signed home are nonnil and match the actual current User/home. Current source must be active platform-home identity, unfenced Account projection, and strictly parsed known current role set. Unknown role even alongside SUPER_ADMIN, missing/NULL projection, unknown activity or unavailable source denies. JWT role/feature-grant hints, Group roles, title/rank and organizational hierarchy never supply current policy facts.
3. Signed current lifetime must remain valid at the operation's current decision time. Auth owns verification semantics; the guarded owner also checks its signed deadline after waits/before materialization or commit. No old token is re-signed or extended in production for compatibility.
4. For a bound token, match signed family ID to the exact stored family ID, subject and home; require LEGACY_COMPANY, unrevoked family, valid current identity/fence and now before the server-calculated created_at+absolute-TTL deadline. Missing/overflow/unavailable deadline denies. Revoking a family invalidates it even with another live same-user family. Successful rotation inside the same family does not itself revoke earlier access JWTs. Native ACCOUNT_V1 material never supplies legacy platform authority.
5. Absence alone invokes the historical exception. Malformed/present/null/unknown-kind binding cannot fall back. Exact legacy shapes/constraints remain as approved round2. Direct platform routes require a genuine direct platform credential; derived tokens cannot enter those routes. Derived source checks accept only view-as→TenantHealthRead/ReadProjection or writable-context→TenantManage/ReadProjection-or-Effect. Group-derived and ordinary tenant credentials never become platform source credentials. Direct source credentials are accepted if and only if callsite is DirectPlatformOwner; platform-derived credentials are accepted if and only if callsite is DerivedPlatformSourceCheck. Every derived source check requires target exactly Company(verified credential org_id), nonnil and not the platform sentinel. Operations, collections, Group, audit and a different otherwise-valid Company deny before UpgradeRequired classification. The source Company key comes from Auth-verified signed claims, never the requested target. Target Company authority/read-only wall must also pass in its own owner.
6. An old otherwise-valid direct/derived source permits only its approved read exception until original expiry and with current finite policy. Old writes/new context mints require `legacy_session_upgrade_required`401 without effects, then genuine original-parent refresh/remint/retry. View-as mutations remain forbidden regardless of binding rather than upgrade into writable view-as. Classify invalid current material as Deny first; return UpgradeRequired only for an otherwise legitimate old operation needing bound authority. Existing ordinary direct-Company legacy mutations remain a separately unconverted requirement and are not a downgrade branch for bound tokens.

After these checks, Cedar receives actual current Subject(home_org, roles, active, account_fenced), typed Resource(platform_scope,kind,key), and closed context(policy_version, session_mode,source_kind,use_kind,call_site,source_company). `session_mode=bound` is derived from exact raw correlation, not accepted as an authority input; `historical_unbound` is emitted only for the explicit absence exception. For direct sources, source_company is the fixed empty string; for derived sources it is the verified signed Company UUID. Cedar independently pairs source kind/callsite and requires company kind plus resource.key == source_company for both derived modes; the HealthRead Operations arm explicitly requires direct. Exposing these smaller Cedar projections as user-controlled input would violate this contract.

## Exact Deny, Allow and UpgradeRequired algorithm

The wrapper executes these ordered steps for the original request, never a rewritten action, use, role, source, target or session. Raw-role parsing validates known role codes only; it does not independently implement SUPER_ADMIN permission.

1. Validate exact policy/schema/SDK identity and known feature/typed target/use/callsite combinations. Validate genuine verified credential, current subject/home/activity/fence, current time, and exact binding material. A present malformed/revoked/mismatched/expired family always Denies; it is never reclassified as historical absence. Validate the source/callsite pairing and exact signed derived Company. View-as Effect/ContextMint and unsupported combinations Deny here. These checks can deny but never return UpgradeRequired.
2. Construct Cedar input from the actual facts. A genuinely bound validated credential uses `session_mode="bound"`. Only a genuinely absent binding satisfying the explicit old-shape/lifetime contract uses `session_mode="historical_unbound"`. No synthetic family, fabricated bound mode, new expiry or fallback retry is permitted. Preserve the original action/use/source/target in this single request.
3. Evaluate the exact private policy once. Its permit means **current-policy eligibility**, which is necessary but never sufficient for exposed Allow. Current MEMBER, ADMIN, empty/non-SUPER_ADMIN sets produce Cedar denial for every action/use, including historical effects/mints. Diagnostics, no permit, unavailable evaluator, error or panic produce Deny. Do not duplicate the privileged-role predicate in the wrapper. The private Cedar policy deliberately accepts both actual session modes for otherwise eligible action/use pairs so it can answer eligibility without lying about family state.
4. Only after a diagnostic-free permit, return the sole public composite `PlatformPolicyDecision`: actual validated bound => Allow(policy identity); actual historical_unbound + ReadProjection => Allow(policy identity); actual historical_unbound + Effect or ContextMint => UpgradeRequired. Exhaustive enum matching forbids another outcome. Historical Allow cannot carry an effect/mint use, and UpgradeRequired cannot be produced from an invalid or unauthorized request.

The compiled policy and raw permit remain encapsulated inside PlatformPolicy. Composition receives a PlatformPolicy value, not raw Cedar bundles or source-level authorization helpers. No production accessor, serialization or conversion can publish raw eligibility as an Allow/guard/receipt. Test-only helpers may inspect the internal result to verify the distinction, but cannot become production authorization APIs. Even a correct public bound Allow remains a decision only: actual operation owners must retain the verified source/target guards and transaction through materialization/effect/commit.

Controls explicitly distinguish the private SDK decision from the sole public wrapper decision: eligible historical effect/mint has private permit but public UpgradeRequired; historical MEMBER/ADMIN/empty has private denial and public Deny; unknown current role/invalid binding/scope denies before evaluation; eligible historical read and genuinely bound positive controls publicly Allow. Injected no-permit/diagnostic failures on otherwise eligible historical requests must publicly Deny, never UpgradeRequired. No tests or implementation are authorized by this design packet.
