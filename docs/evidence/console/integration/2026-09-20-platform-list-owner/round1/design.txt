## What exists and what is missing

`GET /api/platform/orgs` calls `platform-rest::list_orgs`, which calls `PlatformProvisioner::list_tenants(pool, actor:Option<UserId>, now)`. That coordinator opens one Business transaction, calls `platform_list_organizations()`, maps nine Company/Group identity columns, appends `platform.tenant.list` with target_type `organizations`, target_id `list`, NULL org and `{count: n}`, commits, then returns the bare array. Neither its actor argument nor the SQL function proves current source authority. The function's current body has no arguments, temporarily disables RLS, excludes the sentinel and exposes full metadata to any console_rt caller.

The generic resolver cryptographically verifies the token, checks current identity/fence and roles, then constructs the existing unconditional PlatformPrincipal. `SessionVerification::legacy_session_context` commits its Auth snapshot before returning. The SQL context projection itself is STABLE and takes no source row locks. Neither is usable as a retained list guard. The resolver must never evaluate an invented TenantList request for another caller.

Existing `guard_legacy_subject_in_tx` provides correct reusable lock operations: arm verified Company GUC; `auth_legacy_company_lock_v1` Company KEY SHARE and READ COMMITTED check; `account_company_deactivation_guard_v1` User UPDATE then Account UPDATE and fresh fence; `auth_legacy_user_active_v1` current activity. Account root absence/unavailable fence is an infrastructure refusal, not a valid negative authorization. These locks persist only in the caller's transaction. Calling this Rust helper directly with a console_rt transaction currently fails because active/context helper EXECUTE is not granted to Business; Business also cannot read credential family tables. Granting credential-table access to Business or business mutation rights to Auth is excluded.

Auth's `_in_tx` seam runs its narrow SQL owner bridge on this same transaction. No second Auth transaction is committed before Business work, and no multi-transaction pseudo-guard is introduced.

Provisioning already depends on Auth; adding its explicit Authz dependency requires ordinary architecture/generated-graph review, not an Auth→Authz cycle or source inclusion.
