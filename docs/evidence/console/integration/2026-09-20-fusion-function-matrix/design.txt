### Required same-object attestation history

A named control, `Fusion catalogue failed revalidation revokes attestation after same-object restoration`, must execute this complete ordered history through the existing exported functions:

1. Retain one outer registry object, save its exact positive values/keys and canonical serialized bytes, successfully validate that object and require isValidatedConsoleTruthLedger(same_object) true.
2. Mutate only its Fusion signature; require isValidatedConsoleTruthLedger(same_object) false before attempting revalidation. This checks whole-registry content binding only.
3. Attempt validateConsoleTruthLedger on that same mutated outer object and require the actual Fusion-specific rejection, not an unrelated prerequisite error.
4. Restore the exact original positive values and keys in place on the SAME outer object, without calling the validator during restoration or replacing that outer object. Require object identity unchanged, deep equality with the saved positive shape, and identical saved canonical serialized bytes. Remove any injected extra key rather than relying on JSON serialization to hide it.
5. Before any new validation, require isValidatedConsoleTruthLedger(same_object) STILL false. The content digest is now exactly the formerly accepted digest; only this observation distinguishes deleted validation authority from a stale WeakMap entry whose digest was merely hidden by changed content.
6. Explicitly validate that same fully restored positive object successfully; only then require isValidatedConsoleTruthLedger(same_object) true again.

No helper may clear validation state, replace the outer object, quietly revalidate during restoration, or skip step5. This complete history applies to digest-visible negative mutations. Serialization-invisible own-key additions follow the separate history below. The named control makes the lifecycle claim visible even if the remaining cases are parameterized. A test implementation that only observes false on changed bytes does not satisfy this design.

### Serialization-invisible own-key history

For an extra own enumerable undefined/function-valued property in a catalogue record or its binding, the existing stable/JSON.stringify representation omits the property. Its canonical bytes and ledger digest remain unchanged, so current isValidatedConsoleTruthLedger can remain true before revalidation. Do not require pre-revalidation false or expand the global digest/attestation API to create that guarantee.

1. Successfully validate one positive outer registry object; save exact positive values/keys and canonical bytes; require validated true.
2. Inject a neutral extra own enumerable property directly in memory, with undefined or a function value. Prove the extra persists in Object.keys and as an own property, while canonical serialized bytes remain identical to the accepted bytes. Do not round-trip the mutated object through JSON or use a special property such as toJSON.
3. Call the actual exported validator on that SAME outer object. Require rejection at the Fusion exact-key boundary and then require validated false.
4. Remove the injected extra key and restore the exact original values/keys IN PLACE on that SAME outer object, without intervening validation. Prove unchanged outer identity, exact restored shape/key equality and identical saved canonical bytes; validated must STILL be false.
5. Explicit successful revalidation of that restored object is required to restore validated true.

Both variants preserve the decisive post-rejection, post-restoration false observation. Only the pre-revalidation content-binding observation differs. Apply this distinction to every invisible variant, including N20/N26; ordinary added JSON-visible values follow the digest-visible history. No helper may clear private state, replace the outer object, or implicitly validate during restoration.

`oracle-roster.json` names the positive and corruption coverage. Every negative starts with a passing reviewed positive fixture, mutates only the intended new catalogue/support binding, and follows its digest-visible or serialization-invisible same-object failed-revalidation/restoration history above through the actual exported validator. Extra own enumerable undefined/function-valued properties must be injected in memory into both a catalogue row and its binding, because serializing the fixture first would erase the fault. At least the changed-signature probe must fail on the old checker and pass after the owning fix. Retain the first current-file structural test and run the complete existing test file after integration; report discovered/executed counts rather than presuming104 remains its total. Run planner regression because the validated registry digest changes; broaden only for demonstrated affected paths.
