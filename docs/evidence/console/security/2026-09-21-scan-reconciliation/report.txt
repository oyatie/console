## Threat Model

Console is a Rust/Axum modular monolith for a multi-tenant company platform. Internet clients reach Traefik and public API/auth/realtime routes; verified JWTs are converted to tenant principals, transaction-local org context, and Postgres FORCE RLS. Separate platform, group-admin, and machine identities cross distinct boundaries. High-value assets include tenant HR/payroll/organization data, authentication credentials and sessions, evidence object storage, audit/governance records, database identities, and release artifacts.

### Assets

- Company-scoped HR, payroll, organization, workflow, finance, communications, and audit records
- Passkeys, bootstrap/recovery codes, JWT keys, access tokens, refresh families, and role/grant state
- Postgres runtime, migration-owner, and privileged command identities
- Primary and replica evidence objects, database backups, mail credentials, and integration secrets
- Governance approvals and natural-person four-eyes evidence

### Trust Boundaries

- Internet or native client -\> Traefik/TLS -\> console-app public API and realtime routes
- JWT verification -\> live scope resolution -\> Principal -\> transaction-local app.current_org -\> Postgres RLS
- Tenant, platform, group-admin, and machine-principal tiers
- API/worker -\> Postgres, object storage, SMTP/mail, and optional audit custody
- Repository release workflow -\> immutable container digest -\> Argo/Kubernetes desired state

### Attacker Capabilities

- Unauthenticated callers can reach public authentication, storefront, support, sales, and native-association routes.
- A tenant user controls request data for routes allowed by their role, scope, and grants.
- A privileged tenant user may hold import, payroll, user-management, or organization-change authority.
- The model does not assume compromise of the host, cluster control plane, database owner, secret store, signing keys, or GitHub protected environment.

### Security Objectives

- Preserve tenant isolation and bind every data operation to the verified Company org.
- Keep identity tiers non-interchangeable and make deactivation, role changes, and recovery immediately effective.
- Require single-use authentication credentials and bounded untrusted work.
- Enforce complete-scope authorization and natural-person maker-checker separation.
- Keep role-bound approval steps executable as authorization policy, not descriptive metadata.

### Assumptions

- Repository desired state is not proof of current live deployment state.
- The committed production ingress/configuration is evaluated without assuming undocumented out-of-band proxy variables.
- The dark observability and on-prem stacks remain unactivated unless an operator explicitly enables them.
- No dynamic exploit, external network request, or live secret inspection was performed.

### [1] One executive can approve every role-bound organization-change step

| Field | Value |
| --- | --- |
| Severity | high |
| Confidence | high |
| Confidence rationale | The fixed role chain, coarse REST guard, unused role_key, and status transition are all explicit in the same source path. |
| Category | authorization |
| CWE | CWE-862 |
| Affected lines | backend/crates/orgchange/domain/src/lib.rs:173-186, backend/crates/orgchange/rest/src/lib.rs:587-600, backend/crates/orgchange/rest/src/lib.rs:731-737, backend/crates/orgchange/adapter-postgres/src/lib.rs:1810-1820, backend/crates/orgchange/adapter-postgres/src/lib.rs:1879-1977, backend/crates/platform/db/migrations/0198_create_org_change.sql:48-65 |

#### Summary

Organization-change submission creates ordered HR, finance, legal, and executive approval steps, but the decision route permits any Executive or SuperAdmin for every step. The adapter loads role_key but never authorizes the actor against it; the same account can approve all four steps in order and move the request to APPROVED.

#### Root Cause

The workflow persists role-bound approval steps but implements only one coarse endpoint-level Executive/SuperAdmin check.

**Every approval step uses the same role floor** — `backend/crates/orgchange/rest/src/lib.rs:731-737`

The step's declared capacity is not part of route authorization.

```rust
fn allow_approve(p: &Principal) -> Result<(), RestError> {
    role_floor(p, &[Role::Executive, Role::SuperAdmin], "role is not allowed to approve org changes")
}
```

**role_key is loaded but only written into an event reason** — `backend/crates/orgchange/adapter-postgres/src/lib.rs:1879-1977`

No live principal capacity or role mapping is compared with role_key before the decision commits.

```rust
let role_key: String = step.try_get("role_key")?;
...
UPDATE org_change_approval_steps SET decision = $2, decided_by = $3 ...
...
Some(&format!("{role_key}:{}", next_decision.as_db()))
```

#### Validation

Validation outcomes are recorded below.

Validation method: End-to-end approval state-machine trace

- **Status:** validated
- **Disposition:** reported

Assertions:
- Submission always creates HR, finance, legal, and executive steps.
- Any Executive or SuperAdmin may call decide for each step.
- The adapter enforces order and drafter inequality but not role_key.
- After the last approval the request becomes APPROVED and can be effectuated.

Counterevidence and remaining uncertainty:
- Steps must be decided in order.
- The drafter's same account cannot approve.
- Decisions are row-locked and single-use.

Limitations:
- No runtime organization-change request was created; the static state transition is direct.

#### Dataflow

The canonical finding records the affected path at backend/crates/orgchange/domain/src/lib.rs:173-186, backend/crates/orgchange/rest/src/lib.rs:587-600, backend/crates/orgchange/rest/src/lib.rs:731-737, backend/crates/orgchange/adapter-postgres/src/lib.rs:1810-1820, backend/crates/orgchange/adapter-postgres/src/lib.rs:1879-1977, backend/crates/platform/db/migrations/0198_create_org_change.sql:48-65, but no expanded source-to-sink narrative was recorded.

Attack steps:
- Obtain the first pending step ID.
- Approve it as an Executive.
- Repeat for finance, legal, and executive steps in order.
- The final decision changes request status to APPROVED.
- Invoke or arrange effectuation after the effective date.

#### Reachability

One executive account sequentially approves all nominal capacity-specific steps.

- **Attacker:** Executive or SuperAdmin distinct from the drafter

- **Entry point:** Organization-change decision endpoint

- **Sink:** Approval-step update without role_key authorization

- **Outcome:** Request reaches APPROVED without HR, finance, or legal reviewers

Preconditions:
- A submitted organization-change request exists.

Existing controls:
- Ordered steps
- Same-account drafter prohibition
- Tenant RLS
- Row locks

#### Severity

**High** — A single executive account can deterministically collapse a four-capacity approval chain and authorize consequential organization changes without HR, finance, or legal review.

Severity decreases only if role_key is informational rather than an authorization requirement, contrary to domain and migration documentation.

Impact assessment:
- **Level:** high
- **Rationale:** Unilateral approval can lead to applied organizational and employment changes.

Likelihood assessment:
- **Level:** high
- **Rationale:** No additional credential or capacity is required beyond the accepted executive bearer token.

#### Remediation

Define an explicit, live authorization policy for each ApprovalRoleKey and enforce it inside decide_step's locked transaction before recording the decision. Missing mappings or membership must deny. If distinct reviewers are also required across capacities, enforce canonical Person separation from prior deciders.

Tests:
- An Executive who lacks HR, finance, or legal capacity cannot decide those steps.
- Each declared role can decide only its matching step.
- A missing or unknown capacity mapping fails closed.
- One actor cannot collapse the complete chain when distinct reviewers are required.

Preventive controls:
- Make role_key an executable policy input rather than display metadata, and centralize step authorization.

### [2] Credential reset leaves existing access and refresh sessions usable

| Field | Value |
| --- | --- |
| Severity | high |
| Confidence | high |
| Confidence rationale | The complete reset transaction contains passkey deletion and OTP issuance only, while the separate deactivation path demonstrates the available session-revocation primitive. |
| Category | session-management |
| CWE | CWE-613 |
| Affected lines | backend/crates/platform/provisioning/src/lib.rs:292-395, backend/crates/platform/auth-rest/src/lib.rs:1355-1415, backend/crates/platform/auth/src/refresh.rs:175-213, backend/crates/identity/adapter-postgres/src/lib.rs:475-578 |

#### Summary

Administrative credential reset deletes the target's passkeys and issues a recovery OTP, but it does not revoke the target's refresh families or invalidate access tokens. An attacker with a stolen session can continue refreshing after the victim completes recovery.

#### Root Cause

Credential reset is implemented as authenticator replacement but presented as account recovery, without coupling recovery to session revocation.

**Reset deletes passkeys and creates an OTP** — `backend/crates/platform/provisioning/src/lib.rs:321-370`

No refresh-family revocation or session-generation bump occurs inside the reset transaction.

```rust
DELETE FROM auth_webauthn_credentials
WHERE user_id = $1
RETURNING id, credential_id
...
issue_bootstrap_if_needed_tx(..., IssueMode::ForceReset).await?
```

**Rotation accepts any unrevoked family** — `backend/crates/platform/auth/src/refresh.rs:175-213`

A family untouched by reset continues through the normal rotation path.

```rust
SELECT ... t.used_at, t.revoked_at, f.revoked_at ...
FROM auth_refresh_tokens t
JOIN auth_refresh_token_families f ON f.id = t.family_id
...
if family_revoked_at.is_some() { ... }
```

**A stronger credential and session sweep already exists** — `backend/crates/identity/adapter-postgres/src/lib.rs:475-483`

The repository already models session revocation as part of compromise-sensitive account lifecycle changes.

```rust
/// Soft-deactivate a user AND revoke every active credential + session.
```

#### Validation

Validation outcomes are recorded below.

Validation method: Static transaction and refresh-rotation trace

- **Status:** validated
- **Disposition:** reported

Assertions:
- Reset never updates refresh-token tables or subject session generation.
- The target remains active.
- An unrevoked family can continue rotating and minting access tokens.

Counterevidence and remaining uncertainty:
- Old passkeys are removed.
- Open bootstrap credentials are superseded.

Limitations:
- Already-issued access-token lifetime and configured refresh TTL determine the exact persistence window.

#### Dataflow

The canonical finding records the affected path at backend/crates/platform/provisioning/src/lib.rs:292-395, backend/crates/platform/auth-rest/src/lib.rs:1355-1415, backend/crates/platform/auth/src/refresh.rs:175-213, backend/crates/identity/adapter-postgres/src/lib.rs:475-578, but no expanded source-to-sink narrative was recorded.

Attack steps:
- Retain a target refresh token.
- Allow an administrator to reset the target's passkeys and issue a replacement OTP.
- Present the still-unrevoked refresh token.
- Receive a replacement refresh token and new access token.

#### Reachability

A session thief survives the victim's recovery procedure.

- **Attacker:** Holder of an existing target access or refresh token

- **Entry point:** Normal refresh endpoint after administrator credential reset

- **Sink:** Refresh-family rotation and new access-token issuance

- **Outcome:** Continuing account control after recovery

Preconditions:
- The stolen family was valid before reset.

Existing controls:
- Absolute family TTL
- Refresh reuse detection
- Passkey deletion

#### Severity

**High** — The account-recovery operation fails to evict the threat it is intended to remediate, allowing continuing account takeover through an existing refresh family.

Severity decreases if reset is explicitly documented as authenticator replacement rather than compromise recovery; repository comments describe it as account recovery.

Impact assessment:
- **Level:** high
- **Rationale:** Recovery does not terminate the compromised session.

Likelihood assessment:
- **Level:** high
- **Rationale:** The omission is deterministic for every valid pre-reset family.

#### Remediation

Within the same credential-reset transaction, revoke every refresh family and token for the target and increment session_generation. Enforce session generation during request-context resolution so existing access JWTs stop immediately as well.

Tests:
- A pre-reset refresh token must fail after reset.
- A pre-reset access token must fail on the next authenticated request.
- Reset, revocation, session-generation increment, and OTP issuance must commit atomically.

Preventive controls:
- Centralize all compromise-recovery flows on one audited credential-and-session sweep primitive.

### [3] One-time enrollment codes can mint multiple independent sessions

| Field | Value |
| --- | --- |
| Severity | high |
| Confidence | high |
| Confidence rationale | Comments, SQL, the public handler, and a regression test explicitly confirm that concurrent redemptions both succeed and each handler invocation issues a token pair. |
| Category | authentication |
| CWE | CWE-294 |
| Affected lines | backend/crates/platform/provisioning/src/lib.rs:480-548, backend/crates/platform/auth-rest/src/lib.rs:1126-1183, backend/crates/platform/provisioning/tests/bootstrap_passkey_replay.rs:31-72 |

#### Summary

OTP redemption is intentionally verify-only: it leaves the credential open until passkey registration and issues a new access token and refresh family on every successful redemption. A captured bootstrap, recovery, or enrollment-handoff code can therefore be replayed before registration to retain an independent long-lived session after the intended user enrolls a passkey.

#### Root Cause

The design moves single-use enforcement from authentication to later passkey registration while granting full sessions at authentication time.

**Redeem reads an open credential without consuming it** — `backend/crates/platform/provisioning/src/lib.rs:530-548`

The redemption transaction performs no state transition that excludes a second caller.

```rust
SELECT id, user_id
FROM auth_bootstrap_credentials
WHERE token_hash = $1
  AND consumed_at IS NULL
  AND revoked_at IS NULL
  AND expires_at > $2
```

**Every successful redemption issues a normal token pair** — `backend/crates/platform/auth-rest/src/lib.rs:1168-1183`

Each replay produces an independent refresh family rather than a retry-only enrollment capability.

```rust
let user = load_user_auth_context_in_org(...).await?;
let tokens = issue_token_pair(&state.pool, services, &user).await?;
```

**Regression test requires both concurrent replays to succeed** — `backend/crates/platform/provisioning/tests/bootstrap_passkey_replay.rs:44-63`

The exploitable replay window is an intentional tested behavior, not an ambiguous race.

```rust
assert!(
    handle_a.await.unwrap().is_ok() && handle_b.await.unwrap().is_ok(),
    "verify-only redeems must both succeed concurrently"
);
```

#### Validation

Validation outcomes are recorded below.

Validation method: Independent source trace corroborated by repository regression test

- **Status:** validated
- **Disposition:** reported

Assertions:
- The same open code can be redeemed more than once before registration.
- Each redeem creates an independent refresh-token family.
- Consuming the OTP during one passkey registration does not revoke already-issued sibling families.

Counterevidence and remaining uncertainty:
- Expiry, revocation, and per-client rate limits narrow the window.
- Registration eventually consumes the credential.

Limitations:
- No dynamic replay was executed; the repository test already codifies the concurrent success condition.

#### Dataflow

The canonical finding records the affected path at backend/crates/platform/provisioning/src/lib.rs:480-548, backend/crates/platform/auth-rest/src/lib.rs:1126-1183, backend/crates/platform/provisioning/tests/bootstrap_passkey_replay.rs:31-72, but no expanded source-to-sink narrative was recorded.

Attack steps:
- Obtain or observe the one-time code.
- Redeem it before or concurrently with the intended user.
- Receive an independent access token and refresh family.
- Continue rotating that family after the intended user registers a passkey and consumes the code.

#### Reachability

A captured code is replayed to establish a session that survives the legitimate enrollment.

- **Attacker:** Unauthenticated party with a disclosed bootstrap, reset, or handoff OTP

- **Entry point:** POST OTP redemption endpoint

- **Sink:** Normal access-token and refresh-family issuance

- **Outcome:** Persistent access to the victim account

Preconditions:
- The code remains unexpired, unrevoked, and unconsumed at registration time.

Existing controls:
- OTP expiry and revocation
- Rate limiting
- Passkey registration consumes the open credential

#### Severity

**High** — A network attacker who obtains one nominally one-time credential can establish durable account access, including an independent refresh family that survives later OTP consumption.

Severity decreases if all OTP delivery and display channels are guaranteed single-party and session issuance is narrowly scoped; it increases for administrator bootstrap codes with long TTLs.

Impact assessment:
- **Level:** high
- **Rationale:** Account takeover with a renewable session.

Likelihood assessment:
- **Level:** medium
- **Rationale:** Requires disclosure of a bearer code, but replay itself is deterministic.

#### Remediation

Atomically consume the OTP on its first successful redemption. If interrupted onboarding must be resumable, return a narrowly scoped, short-lived enrollment capability rather than a normal access/refresh pair, and exchange it for a normal session only after passkey registration succeeds.

Tests:
- Two concurrent redemption attempts for one code must yield exactly one successful authentication result.
- An enrollment capability must be unable to access ordinary tenant APIs or mint a refresh family.
- Completing enrollment must revoke or invalidate every pre-enrollment capability.

Preventive controls:
- Represent authentication and enrollment capabilities as distinct token types with non-overlapping audiences.

### [4] Authenticated clients can allocate unlimited persistent WebSockets

| Field | Value |
| --- | --- |
| Severity | medium |
| Confidence | high |
| Confidence rationale | Two independent investigators confirmed the unbounded admission path, long-lived session loop, and lack of repository-backed ingress limits. |
| Category | denial-of-service |
| CWE | CWE-770 |
| Affected lines | backend/crates/platform/realtime/src/lib.rs:381-392, backend/crates/platform/realtime/src/lib.rs:468-529, backend/crates/platform/realtime/src/lib.rs:668-772, backend/crates/platform/realtime/src/lib.rs:1147-1239, backend/app/src/lib.rs:3519-3536 |

#### Summary

The public WebSocket route accepts any valid tenant access token, unconditionally inserts each connection into an unbounded process-wide HashMap, and has no per-user, tenant, IP, global, or idle limit. A cursor also spawns an independent unbounded replay task. One low-privilege account can consume sockets, tasks, heap, and database work until shared API availability degrades.

#### Root Cause

Realtime bounds data per connection but has no admission or lifetime budget for the connection itself or its replay work.

**Every connection is inserted without a quota** — `backend/crates/platform/realtime/src/lib.rs:494-529`

connection_buffer bounds one queue, not the number of queues, map entries, sockets, or replay tasks.

```rust
let (events_tx, events_rx) = mpsc::channel(capacity);
...
self.connections.lock().await.insert(id, ConnectionSlot { ... });
if let Some(last_message_id) = last_message_id {
    tokio::spawn(async move { hub.run_replay(id, principal, last_message_id).await; });
}
```

**Idle sessions remain open indefinitely** — `backend/crates/platform/realtime/src/lib.rs:1197-1239`

There is no heartbeat or idle timer branch.

```rust
loop {
    tokio::select! {
        notice = disconnect_rx.recv() => { ... }
        event = events_rx.recv() => { ... }
        incoming = socket.recv() => { ... }
    }
}
```

#### Validation

Validation outcomes are recorded below.

Validation method: Independent route-to-hub source traces

- **Status:** validated
- **Disposition:** reported

Assertions:
- connect never checks connection_count or acquires a semaphore.
- Any authenticated tenant role can reach the upgrade.
- Idle sockets have no application deadline.
- Each cursor-bearing connection can create a replay task.

Counterevidence and remaining uncertainty:
- Authentication is required.
- Per-connection event channels are bounded.
- Lagging consumers are disconnected.
- External infrastructure may impose unspecified ceilings.

Limitations:
- No live file-descriptor or ingress-limit readback was available.

#### Dataflow

The canonical finding records the affected path at backend/crates/platform/realtime/src/lib.rs:381-392, backend/crates/platform/realtime/src/lib.rs:468-529, backend/crates/platform/realtime/src/lib.rs:668-772, backend/crates/platform/realtime/src/lib.rs:1147-1239, backend/app/src/lib.rs:3519-3536, but no expanded source-to-sink narrative was recorded.

Attack steps:
- Open repeated authenticated WebSocket upgrades.
- Keep each socket idle.
- Optionally supply a valid old cursor to spawn replay.
- Continue until process or infrastructure resources are exhausted.

#### Reachability

One tenant account opens many long-lived sockets and optionally multiplies replay work.

- **Attacker:** Any authenticated tenant user

- **Entry point:** GET /api/v1/ws

- **Sink:** Unbounded connection map and per-connection replay task

- **Outcome:** Exhausted file descriptors, heap, tasks, and database capacity

Preconditions:
- A valid access token and network reachability to the public API.

Existing controls:
- Bounded event queue
- Lag disconnect
- Authentication

#### Severity

**Medium** — Any authenticated tenant user can attack shared availability, but each individual event queue is bounded and external infrastructure may impose incidental limits.

Severity increases if ingress and operating-system connection ceilings are high or replay history is large.

Impact assessment:
- **Level:** high
- **Rationale:** Shared API and realtime availability can be affected across tenants.

Likelihood assessment:
- **Level:** medium
- **Rationale:** Requires an account but little per-connection cost.

#### Remediation

Acquire lifetime permits before upgrade and enforce global, per-tenant, per-user, and trusted-client-IP connection caps. Add upgrade-rate limits, heartbeat/idle deadlines, replay concurrency and total-record budgets, and matching versioned ingress in-flight limits.

Tests:
- Excess connections for one user and tenant receive 429 or 503 and do not enter the hub.
- Idle connections close after the configured deadline and always release permits.
- Replay tasks obey a global semaphore and total page/record/time limits.

Preventive controls:
- Expose quota, rejection, active-connection, and replay-concurrency metrics with alerts.

### [5] Sparse XLSX uploads can trigger multi-billion-cell allocations

| Field | Value |
| --- | --- |
| Severity | medium |
| Confidence | high |
| Confidence rationale | Two independent investigators found the same parser root cause; the allocation is explicit in vendored source and precedes application validation. |
| Category | denial-of-service |
| CWE | CWE-400, CWE-409 |
| Affected lines | backend/app/src/hr.rs:144-170, backend/app/src/hr.rs:4171-4186, backend/app/src/hr.rs:4534-4546, backend/app/src/hr.rs:4612-4635, backend/crates/registry/adapter-postgres/src/lib.rs:3589-3602, third-party/rust/vendor/calamine-0.35.0-quickxml41/src/xlsx/mod.rs:1727-1794, third-party/rust/vendor/calamine-0.35.0-quickxml41/src/lib.rs:854-874 |

#### Summary

Equipment and HR import endpoints cap only the compressed multipart body. The vendored calamine parser collects sparse cells and expands the attacker-controlled bounding rectangle into a dense Vec before application row limits execute. A small valid workbook with cells at distant Excel coordinates can exhaust a 512 MiB API pod.

#### Root Cause

Upload admission constrains compressed transport bytes but not ZIP expansion, worksheet coordinates, total cells, or dense parser allocation.

**Worksheet parsing hands sparse cells to dense Range construction** — `third-party/rust/vendor/calamine-0.35.0-quickxml41/src/xlsx/mod.rs:1727-1794`

No application cell, coordinate, or expanded-size budget is applied before materialization.

```rust
let mut cells = Vec::new();
...
while let Ok(Some(cell)) = cell_reader.next_cell() { cells.push(cell); }
...
Ok(Range::from_sparse(cells))
```

**Extreme coordinates determine allocation size** — `third-party/rust/vendor/calamine-0.35.0-quickxml41/src/lib.rs:860-874`

A few cells spanning A1 to XFD1048576 request roughly 17 billion default cells.

```rust
let cols = (col_end - col_start + 1) as usize;
let rows = (row_end - row_start + 1) as usize;
let len = cols.saturating_mul(rows);
let mut v = vec![T::default(); len];
```

#### Validation

Validation outcomes are recorded below.

Validation method: Independent endpoint-to-vendored-parser source traces

- **Status:** validated
- **Disposition:** reported

Assertions:
- Multiple reachable import routes call worksheet_range before row validation.
- Range::from_sparse allocates rows multiplied by columns.
- The 16 MiB request cap does not bound sparse worksheet dimensions or decompressed content.

Counterevidence and remaining uncertainty:
- Import routes require org-wide HR or master-list authority.
- Compressed input is capped.

#### Summary

**Missing proxy configuration becomes zero trusted hops** — `backend/app/src/lib.rs:1098-1107`

```rust
fn parse_trusted_proxy_count(raw: Option<&String>) -> Result<usize, AppError> {
    match raw {
        Some(raw) => raw.parse::<usize>(),
        None => Ok(0),
    }
}
```

**All proxied callers resolve to the transport peer** — `backend/crates/platform/request-context/src/lib.rs:103-109`

Behind Traefik, peer.ip() identifies the proxy-side transport peer rather than the external caller.

```rust
if trusted_proxy_count == 0
    || !trusted_proxy_cidrs.iter().any(|network| network.contains(&peer.ip()))
{
    return peer.ip();
}
```

```rust
if let Some(ip) = trusted_client_ip {

}
```
