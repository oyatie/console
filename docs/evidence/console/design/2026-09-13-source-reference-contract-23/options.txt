Decision23 — reuse native relational integrity
A. Existing22 constraints alone: insufficient. They fix manifest membership bytes but cannot show the named native source exists or that every native result is represented.
B. Extend native owners with generated discriminator columns + standard reciprocal foreign keys: SELECTED. Fixed7-family graph, same receipt/draft owners, built-in deferred identity/concurrency checks. Costs: wider sparse effect projection, additional UNIQUE indexes and FK internal locks; inventory and measurement remain explicit. New tables0, dynamic dispatch SQL0.
C. LIST partition effects by family: rejected for this boundary. Parent unique/primary keys must include partition key, which would change22 global(org,command,ordinal) uniqueness or require separate enforcement. Seven partitions add lifecycle work without a demonstrated workload need.
D. Only owner/constraint triggers with7 branches: viable but more bespoke identity/concurrency enforcement and catalog surface than native FKs. Keep typed owner guards for semantics/authorization/current-head CAS/decoded projections that FKs cannot express; do not duplicate native RI with bespoke loops.
E. Universal source ledger/table or new claim table: rejected. Seven native owners and22 claim effects already own these facts. A new generic revision store would duplicate native truth; a separate claim table would duplicate immutable kind2 linkage. Common object revisions remain the editable draft history.
The chosen generated columns are server/database projections. Users see existing typed object controls, not family codes/FK columns or a new setup wizard. New source kind enrollment requires reviewed native source, decoder, FKs and owner policy integration; arbitrary runtime table names are not an extension mechanism.
