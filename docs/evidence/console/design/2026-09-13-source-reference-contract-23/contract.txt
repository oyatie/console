SR23 — Exact source identity and recoverable input
Bounded scope: complete the reciprocal IDENTITY component left open by21/22, plus the closed19 admission-event identity transitions and one-time revoked predecessor claim linkage. The seven native tables and three heads are still proposed full-domain tables. This is an ALTER fragment over specified prerequisite columns/PKs, not their complete CREATE definitions or an executable migration. It cannot enroll sources by itself. No added source table, claim table, editable entity engine or approval pipe.

1. Native relational constraints chosen
22 effect relation stays unpartitioned with PK(org,command,ordinal), fixed family/kind checks, immutable members and bounded sealed count/digest. Each native revision has exactly one reciprocal REVISION member keyed by Company/family/root/revision/creating command/custody. Source->effect includes both command and digest; effect->source selects the owning table through a generated conditional root. No per-source UNIQUE(org,command): one command may emit many roots/revisions. The seven family codes identify native storage/decoder, not people, reasons or permissions.
All FK target keys in this fragment are ordinary UNIQUE constraints with immediate uniqueness. The FKs are MATCH SIMPLE, NO ACTION and DEFERRABLE INITIALLY DEFERRED. The22 header/member INSERT guards and immediate member->receipt FK remain unchanged. No deferred UNIQUE target is referenced. NO ACTION is selected because graph participants may be provisionally out of order until deferred validation; immutable owners and ACLs still prohibit historical deletion/update, so it does not authorize cleanup.
MATCH SIMPLE is intentional: inactive generated family root NULL means that other-family FK is inapplicable. In the active family, root, Company, revision, command and custody cannot be NULL. Claim successor fields are additionally all-nonnull by22; generated event expectations cannot be caller-selected. Do not change generated selectors into writable nullable inputs, or use optional effect links on source revisions. New source tables in this fragment require membership for every row; admitting historical unrepresented rows is not a nullable compatibility branch. Any later legacy migration must prove provenance or keep those rows unenrolled, with F05 handling dependent readers explicitly.

2. Closed19 event identities, not a generic workflow enum
19 fixes PROPOSE1 -> VERIFY2 -> REVOKE3 or SUPERSEDE3, or PROPOSE1 -> REVOKE2. Native event CHECK constrains exactly those pairs. A generated prior-event FK recursively through at most2 edges proves the prior event and identical original admission digest. The PK forbids both VERIFY2 and REVOKE2 for the same root, and forbids multiple terminal3 events. PROPOSE is the only no-prior branch. This is a bounded source-verification protocol already chosen in19; it is not a general Console action lifecycle. New admission/correction gets a new root, not event4 on a terminal root. If19 changes, this exact design must be revised, not silently generalized at implementation.
These constraints prove immutable event identity structure only. Prior verified event existence does not prove independent-human verification, qualified issuer/current trust, custody-byte authenticity, source applicability, legal adequacy or that native heads match the latest valid event. All are distinct owner/authorization/retention/current-time obligations. A source19 VERIFY body remains exactly bound to original admission1; scalar projections must be verified against retained normalized bytes by the owning decoder before writes.

3. Two replacement shapes under one owning verification action
For an already REVOKED predecessor, kind2 CLAIM points to exact REVOKE3 custody and the same-family successor VERIFY2 custody created by THIS command. REVOKE3's prior-event FK proves VERIFY2 then PROPOSE1; REVOKE2 of an unverified proposal cannot qualify. The predecessor's original command is deliberately not part of the claim's old-source FK. It stays bound to the predecessor's own REVISION member. Never relabel that old command as the new claim command.
The three native heads keep current_revision and add only successor_claim_command_id for this revoked path. Its exact FK to the claim and the claim's reverse FK to the head make the relationship reciprocal. Nullable pointer is safe here because an existing immutable claim requires the nonnull exact head tuple; NULL cannot erase a committed claim. Existing partial UNIQUE(org,family,root) WHEREkind2 allows one claim per predecessor. Once committed, changing pointer, root, current revision or removing the head would break that FK while the immutable claim remains. Current head CAS/absence check and source family guards still belong to the native owner and must be implemented; no missing head row may be treated as a lock.
This refines15's proposed physical activated_successor_ref into a READ PROJECTION rather than storing duplicate successor fields in the head. Revoked-path successor tuple resolves from the immutable claim; SUPERSEDED-path tuple resolves from its native event. No new claims table. Existing approved meaning of one activated successor and no resurrection is retained. If a previous partial prototype stores a duplicate pointer, migration must remove/converge only through F05 after proving read compatibility;23 authorizes no live drop.
For a VERIFIED predecessor, the same successor VERIFY command appends native SUPERSEDE3. Its successor projection is all-nonnull only for SUPERSEDE; same-table FK binds exact successor VERIFY2/custody/creating command. The22 REVISION member has NULL successor fields, as before: the linkage lives in the native SUPERSEDE event, not a fabricated kind2 claim. Successor root must differ from predecessor. All predecessor/successor result revisions require their own reciprocal REVISION members, automatically joining this same receipt where newly created.
These are exact historical successor revisions, never foreign keys to the successor's mutable current head. Later successor REVOKE3 must remain possible; it does not revive its predecessor or retarget old lineage. To activate replacement now, native owner still checks exact current predecessor and successor admission/head, same-subject/purpose relationship and current independent verification. A syntactically valid old VERIFY reference cannot independently authorize a new action.

4. Subject identity and editable correction fields
Structural FKs prevent cross-Company or wrong-family identity substitution. Cedar may separately authorize operators from another Company in the SAME customer Group; cross-customer context never follows these joins merely because an Account has other memberships. Object/reference resolution remains server-owned under exact active tenant context.
Same family is not sufficient for replacement. Qualification requires the original qualification kind/purpose and appropriate governed subject; eligibility requires the intended employee/Employment and business period; tax evidence requires intended employee and business period with the applicable assessment/selection linkage. The full selector predicates from15/19 and exact immutable typed admission projections remain mandatory F01/F02 owner contracts. Corrections can legitimately change edition, evidence, assessed amounts, profile/selection or applicable ranges where the owning action permits. Do not use predecessor-payload byte equality as a proxy for matching identity or forbid the very correction being made.23 does not claim these semantic predicates implemented by its FKs.

5. Atomic write, saturation and current-head enforcement
Use22 provisional header-first transaction after20 receipt-first replay/provenance reconciliation and all registered source/policy/head/adoption locks and validation. Write source revisions, effect members, successor native event or claim/head pointer, and the exact adoption/gate/attempt/work participants. All within the one owner transaction, with22's final bounded manifest check, deferred FK checks and final current-time/authority validation before one COMMIT. Preserve22 no-subtransaction and named-constraint-mode requirements.
A late source revision cannot commit outside the sealed set: it needs its exact REVISION member; existing native PK prevents pretending a second source row is an already represented identity; a new member cannot fit after22 ordinal saturation. No additional full manifest scan is needed for every source. Late claims likewise require a member slot and reciprocal head linkage. This argument assumes immutable existing sources/members, enforced constraints and unprivileged writers; trusted admin disabling triggers/constraints is outside it. Native head regression/max-event completeness, source-body scalar integrity, input custody, aliases/legacy shape and domain adoption are not closed by cardinality.
Early SET CONSTRAINTS after the complete graph validates it; any later dependent write still incurs its FK. Setting constraints immediate before graph construction can fail closed; do not catch the failure and continue partial mutation. Lost commit acknowledgement is UNKNOWN, never retry-as-new. Historical replay returns original receipt under CURRENT disclosure without recomputing source eligibility or mutating new evidence. Operational diagnostic raw PostgreSQL errors, including key/row DETAIL and failing cast input, stay sensitive per22/F04. FKs may internally check rows independent of RLS; a constraint failure is not a public existence oracle.

6. Enrollment and verification limits
Full seven table payload/index/retention/actor definitions, current head creation/CAS/transition bodies, source-generation guards, raw/alias owner action roster and all-null receipt downgrade refusal, current CompanyActor/Cedar/trust, role/ACL/default grant/SELECT/TRUNCATE closure and complete adoption/attempt/work/gate participants remain mandatory. This SQL fragment installs no permissions; absence of GRANT here is not proof existing inherited/default grants are safe. Restore validates the full graph plus current authority before serving; historical xmin or a successful FK check cannot readmit a tenant.
FK checks create internal indexed probes and row locks. The whole finalizer must include those in its lock/race/deadlock and workload analysis, not only explicit FOR UPDATE statements. Needed existing native PK/head PK plus21 new UNIQUE targets and their write/storage cost are intentional integrity cost, not a performance guarantee.15/20 family/head ordering remains the owner guide; PostgreSQL constraint lock order and failure handling require the later executable race harness. A deadlock can abort a transaction and must preserve/reconcile input according to proven outcome, not become a silent retry of a changed intent. No PostgreSQL parse/typecheck/run, EXPLAIN, memory measurement or Verus theorem was performed here.
