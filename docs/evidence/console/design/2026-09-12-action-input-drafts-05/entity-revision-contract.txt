EV1 — Common object revisions for draft change tracking
Proposed normative supplement FD1.13-FD1.17. Read with draft-contract.txt. No implementation or authority amendment. Source base 05200e43af13b527ce031b04369e05852862f1d6.

FD1.13 Identity, ownership and time
First proof: an instance-backed ActionInputDraft is the durable proposed input to an existing payroll owning Action. Its instance ID is its draft ID; its common engine revision ID identifies saved input. The PayRun/wage remains projected from its domain owner. A save appends only proposal-object history and its receipt, never payroll truth. A draft may produce zero, one or multiple result objects; result links record exact source draft/revision. Do not rename the proposal into a PayRun or let a generic instance writer edit a projected domain table.
For a new request/document whose domain genuinely owns draft-to-submitted lifecycle, the same object ID may continue through publication. That capability must preserve private pre-submission revision visibility and use that domain's writer. It is not automatically enabled by the generic engine's Draft -> Active transition. The first payroll proof selects the linked-proposal case, so no second identity convention is left to its implementer.
The common revision store owns payloads, sequence, hash linkage and head advancement. Draft control owns unique intent slot/custody/attempt bindings; these reference the engine's head and do not maintain a second payload history. All typed reference keys are Company-correlated; cross-cell references require an explicit owner contract, not an unscoped UUID. Draft lifecycle EDITABLE/SEALED/CONSUMED is the input protocol in FD1.7, not an assumption that InstanceLifecycleState already implements it. Generic lifecycle/property Actions cannot bypass draft controls.
Proposal revisions record when saved intent became current, not when the proposed business change becomes legally or operationally effective. A requested future effective date is a typed input property. For this instance-backed proposal, the common valid_from is allocated by the server under the locked head: max(transaction clock, previous valid_from + database timestamp quantum). Revision sequence is authoritative ordering; recorded_at keeps actual observation time. The client cannot backdate or choose this sequence timestamp. Business objects retain their own effective-dated semantics without change. Expose user save time, not an invented legal effective date; as-of proposal reads use revision ordering/time explicitly.

FD1.14 Shared guarded saves and typed draft properties
Consolidate the existing action writeback CAS/receipt behavior into the common instance revision owner/application boundary so REST and SSR use the same guard. Required order for new writes is current identity/policy guards -> relevant assignment guard -> command replay guard -> draft/attempt control -> common instance head -> participating domain locks. Resources within a class are locked by stable Company/object ID order. All operations involving both WorkItem and draft acquire assignment before draft/head. Retry/replay still follows AI1 current-disclosure-first rules; no payload is returned merely because its command previously succeeded.
Editing context is a server-issued opaque binding to Company/draft/Account, custody/assignment generation and draft lifecycle epoch, separate from the payload revision. Authorized start/resume issues it. Save, automatic merge, restore, schema upgrade, seal and discard must carry it; the owner compares it under assignment/control guards and binds it into the request receipt identity. Every handover, seal/unseal and terminal transition advances the relevant generation, even if input payload is unchanged. Old requests cannot regain validity after A -> B -> A or an editable -> sealed -> editable cycle. Automatic rebase cannot cross generations: fresh authorized resume and explicit renewed intent is required. Already-committed receipt replay remains a historical, currently authorized read, not a new generation check that conceals success; it cannot reactivate old writes. Execution/cancellation use the exact attempt and its own guard/state, never substitute a new editing token into an old attempt.
The first slice uses one Company transaction. Handover locks the same assignment fence before enumerating its exact current draft set, preventing a concurrent start from escaping that set. Saves, start, restore, seal, execute and purge participation use this fence when work-bound. Existing callers with a different order must be adapted before draft actions activate; the ordering is a required change, not an assertion about all existing code.
save accepts expected common revision, expected editing-context token, stable command ID and a bounded patch keyed by declared property IDs. The owner reconstructs from its locked authoritative revision and checks each changed property's current permission; no redacted full-object replacement. Required-on-submit differs from required-in-a-saved-draft. The selected representation is per-property typed DraftCell (Unset, Incomplete bounded editor text, or Value matching the declared kind), interpreted using a pinned input schema; this is an explicitly registered draft type capability, never a relaxation of ordinary object validation. Unknown kinds, undeclared keys, arbitrary nested JSON and unregistered validators fail closed for draft saves. Lists contain stable element IDs; array offsets cannot silently retarget a concurrent patch. No LLM interpretation.
Schema-defined reference cells become resolvable links only after type/Company/target validation. They remain proposal-context edges: discoverable only with permission on the draft, property and linked target. They cannot count as effective employment/contract links or trigger business subscriptions. Incomplete strings/search queries have no object-link or business-derivation semantics. Automatic derivation may use authorized pinned source values for draft previews but never writes business state; hidden operands must not leak through a preview result without permission to disclose that result.
Accepted content-changing saves append a full common revision, advance the head and store a minimal receipt atomically. Canonical equality covers input cells and provenance/schema/source refs; a change in source basis is meaningful even if a displayed amount stays equal. An authorized no-op acknowledges the current revision without appending a redundant revision. Its retry receipt binds the same request; later replay must not move a newer head backwards. Stale expected revision fails before no-op acceptance, rather than using no-op to bypass concurrency checks. Ordinary save does not change source-schema bindings; schema upgrade is explicit FD1.15.
Receipt identity/digests are internal integrity data. Client receipts identify only the acknowledged save and an opaque revision token. Never serialize the existing raw CommandReceipt.instance attributes/hash into draft responses. Save retry comparison uses stable original request binding, not recomputed current defaults. Retried business execution and draft restoration remain different operations.

FD1.15 Historical projection, restore and schema evolution
The integrity verifier reads the complete retained chain internally under narrowly authorized maintenance access. The user history API is a separately authorized projection through the same policy owner; current head visibility is necessary but not sufficient. Evaluate permission for historical revision custody/publication segment and each field at request time. Publication does not declassify private revisions. Never send a full chain to the browser to filter there, or treat a filtered response as the input to verify_chain.
History timeline access requires explicit current permission to disclose revision existence/order and page progress for the selected history scope, separately from field values. In this slice that is the whole draft chain: default private custody may grant its owner this metadata right, but current-object read and receiving a submitted revision do not. When this metadata right is absent, the timeline endpoint uniformly returns nondisclosing unavailable based on permission alone, whether the chain contains 0 or 201 hidden revisions. Do not condition availability on inspecting whether hidden revisions happen to exist. Direct read/compare of independently authorized pinned revisions remains available through current revision/property authorization; the timeline limitation does not hide an already-authorized submitted artifact.
For callers with the explicit whole-chain existence/progress right, history pages contain at most 50 entries using keyset pagination and opaque cursors bound to Company/object/principal/policy context. No hidden-revision scan/filter is required in this mode; properties and actor/time/reason metadata remain separately projected. If the permitted plan cannot execute within bounded database work/time, use a sanitized operational failure, never an unbounded fetch. Do not emit hidden-field change labels, raw totals or hashes. Callers without metadata rights receive identical timeline availability/continuation behavior for identical granted revision sets; cursor shape and notifications cannot reveal protected history volume. Strict timing noninterference is not claimed. A later bounded authorized-history index could enable richer mixed-visibility timelines; it is not silently assumed built here.

Compare at most two selected retained revisions. Project both sides by current property/history rights; render only authorized differences and any separately permitted unavailable/restricted explanation. Client tokens/hashes must not permit guessing low-entropy confidential values. Snapshot means saved draft input plus exact source refs, not an immutable copy of the entire surrounding graph. When a linked source is gone or forbidden, say unavailable within discovery rights; never silently substitute its live head as historical evidence.
restore(source_revision, expected_current_revision, expected_editing_context, command_id, selected_property_ids) is an explicit draft Action. Read, history and edit permissions are distinct. Under the common guards, load and verify the retained source, copy only selected authorized editable cells, preserve hidden/current-unselected values, revalidate current draft schema, append a new revision with restored_from provenance. Require at least one eligible selected field; a no-op follows FD1.14. The UI previews permitted changes and missing inputs. Restore cannot change immutable Company/action/target/custody, revive terminal attempts, grant approval, replace assignment or write business truth. A SEALED draft must first conclusively cancel/unseal under FD1.8; an unresolved attempt blocks restoration. Restore vs save is CAS, not last-writer-wins.
Historic schema definitions are data, not executable downloaded renderers. Revision read uses its recorded schema version and a supported safe renderer; unavailable/unsupported definitions return an explicit unavailable view, never reinterpret old enum/reference values under a newer definition. A schema upgrade is an explicit guarded Action appending a new revision with old/new schema refs and deterministic mapping provenance. Only registered lossless mappings may automate transfer; dropped/ambiguous/type-changed values stay in permitted old history and require user repair, not silent coercion. Existing sealed attempts remain bound to their exact old schema/input; current executable compatibility is rechecked before any effect. If no supported mapping exists, block affected submission and preserve allowed historical read and correction entry. Restoring older data uses that same mapping discipline.
No Git branch/checkout UI or alternate executable branch is required. Restore is sufficient for this requested scope. A future copy-as-new-intent cannot copy command IDs, approvals or task assignment; it needs its own domain duplicate-intent invariant. It is not implicitly admitted here.

FD1.16 Efficient retention and integrity
Initial representation: reuse full snapshots, existing identity/hash/CAS mechanisms, coalesced autosaves, no-op suppression, bounded reads. Derive a two-version diff on demand; do not maintain a second authoritative delta stream. Do not introduce Git/Dolt/CRDT/lakeFS for this small-form requirement. Native PostgreSQL MVCC alone is not a retained application history; explicit existing revision records are the reuse target. Later measured pressure may justify common-store payload compression or deltas/checkpoints while preserving revision IDs and read/restore semantics; no speculative second implementation now.
Illustrative assumption, not forecast or benchmark: 100 continuously active editors saving every 5 seconds for 8 hours produce 576,000 saves. At 4 KiB per full payload this is 2,359,296,000 bytes/day before metadata, GIN/indexes, WAL, replication and backups. Coalescing/no-ops reduce actual accepted revisions. Two thousand pilot people is not a concurrency claim. Instrument accepted/no-op/conflict counts, payload bytes, save latency, scan counts, and retained bytes per Company, without raw input labels. A full historical GIN index can multiply write cost; measure the current index before deciding a common-store migration. No per-save whole-chain verification or unbounded rehydration in the interactive path.
Use FD1.11's explicitly proposed retention window. Preserve the complete chain while editable/retained; no arbitrary 20-version eviction. Only an entire eligible terminal draft payload chain is a deletion unit in this slice; no middle-revision deletion and no silent chain rebasing. Required submission/evidence pins or unknown attempts block purge. Pin creation and purge serialize through the same draft/head fence; pin creation checks payload still exists and cannot resurrect an expired object. A durable minimal tombstone preserves identity/command terminal status and records authorized disposal, without claiming the removed content can still be reconstructed.
Current migration0155 explicitly forbids revision DELETE, including via trigger. Do not disable that trigger, grant general runtime DELETE, or claim soft disposal removes personal data. Before retaining real private drafts, a separately reviewed narrowly scoped common-owner retention operation and migration must prove whole-chain disposal, pin races, replay guards, Company confinement and backups. Its authority must not allow deletion of ordinary business chains. This is a concrete remaining implementation/design sub-contract, not cleared by this candidate. Retention period/hold legality needs qualified policy separately. Physical purge is therefore HOLD; no real sensitive draft activation until resolved. Non-sensitive fixtures can prove save/read semantics meanwhile, subject to delivery approval.
Retained payload/hash mismatch is an integrity failure: stop restore/seal for the affected draft and show an authorized repair/escalation path; never treat corruption as an empty draft or recalculate a chain over damaged bytes. Hash chaining detects discrepancies relative to a trusted anchor; it is not independent proof against an administrator able to rewrite all storage/anchors. Whole-chain verification is bounded background/page work with a recorded verified position; read/restore verifies the selected row/link against available trusted verification state. Independent anchors, backup trust and repair authority remain operational design work, not a cryptographic claim established by this source.

FD1.17 Adoption gates and finite proof
Before enabling this draft type, enumerate and close every generic read/write surface: instance CRUD/lifecycle, Action/preflight/receipt replay, history/as-of, list/search/aggregate/traversal, link previews, SSR/hydration, exports, subscriptions, audit and admin tools. Each must either use the common draft-aware authorization/DTO path or explicitly deny this type. No route may fall back to current-head-visible => full-history-readable or whole-attribute audit for private draft content. Domain-specific control records cannot be bypassed by generic property/lifecycle mutation. Field masking at the final UI alone is insufficient.
Scope selection: reuse instance store and common guarded Actions for linked payroll input proposals; add typed draft validation, minimal control/attempt binding and recipient-specific history projection. New request same-ID publication, arbitrary branching, general collaborative sheets, engine-wide delta storage and new databases are not needed for this proof. Their broader product relevance is preserved without claiming they are implemented.
Acceptance-plan.csv is a non-executable set of design oracles. Tests and implementation remain behind exact approved design/test SHAs. Outstanding B03/B04/B07/B08 plus physical-retention/migration/anchor detail prevent a whole-design-ready claim. Rollback must disable new draft mutation while retaining authorized readers, receipt reconciliation, cancellation guards and existing owner behavior. No migration, product code or production action is performed by this packet.
