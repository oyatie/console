FD1 — Durable input intent without a second business writer
Proposed design for B06 and related B07 states. Extends candidate03 AM1/AI1 and candidate04 PC1; does not implement them or activate current-authority HOLDs.

FD1.1 Source facts and selected owner
Scoped source search finds policy/adapter-postgres save_draft at :125, which writes cedar_policy_drafts: a policy author's reviewable domain artifact, NOT a generic action-input autosave store. Ontology PreparedCommand validates a request in memory; no durable editor draft is established there. ontology/application validate_params currently checks declared keys/required only, accepts empty schemas and does not provide deep input typing. Migration0177 provides immutable Company command receipts but no editable drafts; projected-usecase dispatch explicitly lets the domain own its transaction. Payroll UI accepts already-authorized view DTOs, not a demonstrated editable autosave model. These are source facts, not proof that no other repository could ever have a draft.
Extend the existing common ontology instance/revision owner; ActionInputDraft is an instance-backed governed proposal object, not a parallel history store. Its typed input revisions live in ont_instances/ont_instance_revisions through the common writer. Draft preparation owns custody, incomplete-input semantics and submission attempts; business domains remain the only writers of wage/Employment/review proposal/application/certificate facts. Control records may bind draft instance IDs to unique intent slots, assignment generations and attempts; they must not duplicate editable payload history. FD1.13-FD1.17 specify the common-engine fit and required changes.
Source correction: the common engine already creates v1 in draft, appends full revisions, and exposes get_as_of/history. Although StageRevision itself has no expected-version field, ontology/rest execute writeback checks expected_revision under lock and serializes command receipt retries before calling stage_revision_in_tx (:2443 onward). Reuse that protection by consolidating it into the responsible common owner/application seam shared by adapters; do not add an unguarded autosave route or claim CAS is absent everywhere. Existing history routes gate the current head and return the whole chain; that is insufficient for draft property/history privacy.
This slice remains Company-scoped. An applicant or former worker may have Account-only authentication and a target posting/issuer Company without workforce membership; own-intent permission is independent of employment. Forms with no target Company, secrets/credential forms and full collaborative spreadsheets need their respective later contracts. Never invent a dummy Company or turn the canonical projected domain roster into a generic writable store.

FD1.2 Draft identity and custody
ActionInputDraft key: (org_id,draft_id), stable random ID allocated once per explicit start intention. Immutable bindings: action stable ID/version, target owner/object reference or typed create-target scope, initial form-schema provenance, custody_ref and original creator Account. Each input revision owns its current schema reference; only the guarded schema-upgrade Action may change that reference, compatibly with the immutable Action/target. Common-engine input revision: permitted typed edit cells and base business-object/evidence refs. Draft control state binds the common head revision to current assignment generation, draft lifecycle and attempt/result refs; validation/readiness is reevaluated. No separately incremented input-history counter. No cross-Company or action retarget-in-place.
Custody_ref is either the creator's Account-owned input intention or an existing owning WorkItem reference, NOT an internal/external user type. A private application/PTO/certificate request can start Account-owned before submission; Company admin/UserManage or a future recipient cannot read it just because it concerns that Company. Once the user explicitly submits, the resulting business record follows its own access policy. Do not silently publish the editor history to the receiving employer.
Input opened for an already assigned business work item is work-bound by default and shows that connection: its currently authorized responsible worker can continue it; original creator is immutable provenance, not permanent exclusive ownership. WorkItem owner remains responsible for task assignment; draft owner cannot create or reassign business tasks by autosave. If an Action starts new work without an existing task, its explicit 'start work' owning operation must establish the task before a work-bound draft is admitted; a GET page load does not create it. General automated assignment is still B04.
For this slice one accountable editor at a time follows Account custody or the current WorkItem assignment; multiple tabs/devices of that Account are supported with optimistic concurrency. Other authorized participants may read allowed draft fields or prepare separate source tasks, but collaboration does not create multiple ambiguous current custodians. General simultaneous multi-person sheet editing remains a separate capability. Editing authority is current Cedar/resource/field permission plus that precise custody/assignment relation; neither condition alone grants business execution.
Start path: explicit action entry -> server authorizes start/save for exact target -> find a current accessible matching active draft for this custody/action/target context or create by stable create command -> render authorized fields and saved status. Ordinary resume GET has no creation/business effect. Explicit 'new separate request' uses a new draft identity; reopening a tab does not accidentally create duplicate intents. An active-intent uniqueness constraint on (Company,custody_ref,action_version,target_ref,intent_slot) backs race-safe start/resume; intent_slot is owner-defined stable context, not a random slot minted on every render.

FD1.3 Schema and unfinished input
One authoritative versioned ActionInputSchema, projected into form controls and server draft/execute validation, defines fields, scalar/reference types, editable/visible policy groups, allowed partial editor states, limits, coupled validation groups and required-on-submit fields. Do not keep unrelated frontend/backend copies of field rules. Existing loose validate_params is insufficient; new draft admission requires a declared validated schema, never an empty-schema accept-anything fallback. Deep type validation at execute remains mandatory at the business owner.
Save accepts schema-defined unfinished edit cells, e.g. a missing required field or an explicitly bounded numeric editor token '-', without treating that token as a business number. Distinguish DraftCell::Value(typed value/object ref), DraftCell::Incomplete(bounded editor text for that declared field), and unset/explicit clear. Object selection binds an existing authorized object ID; search text is not a resolved entity reference. No arbitrary JSON keys, HTML execution, credentials, OTP/passkey material or pasted file bytes are admitted. Notes remain escaped bounded narrative linked to the draft; they do not become inferred policy or entity links.
At seal, every effectful field must normalize to the exact canonical business input; incomplete/invalid required fields block it. The server validates current reference targets, supported-case rules and required evidence using domain-owned preparation. A saved draft is not a successful preflight, and successful preflight is not authority to execute later.
Defaults are authorized object projections with provenance, not silent user edits. Record which values are user-authored versus source-linked and the source version. On source change, refresh untouched linked defaults only with a visible permitted change indication; preserve user-authored input and mark conflicts/staleness for review. Never overwrite a typed amount behind the user's back or silently convert newer defaults into an already sealed command.

FD1.4 Save semantics, acknowledgements and no business effect
save_draft(command_id,draft_id,expected_draft_version,expected_editing_context,field_patch) is a draft-owner Action. Server resolves Account/Company/target, current custody/assignment and property-save rights, validates patch shape/limits, applies CAS, stores the new draft revision plus save receipt atomically. Missing/unauthorized fields in a client patch are rejected, not silently dropped. Omitted fields are unchanged; explicit clear is separate and allowed only where schema/policy permits. A redacted form never replaces the entire underlying payload.
A successful save changes only draft intent/history and bounded draft audit. It does not write wage rows, calculate pay, reserve a payroll period, create Employment/application records, submit a request, consume approval, send mail or complete a task. Domain facts change only through explicit owning execution.
The client sends one save at a time per tab, coalesces later edits into a pending patch and keeps the exact pending command identity on response loss. Proposed initial cadence: debounce 600 ms after edits, maximum 5 seconds while typing, immediate flush before internal navigation or explicit submit. Server ACK includes opaque draft version, acknowledged command/revision and authorized current save metadata. '저장됨' appears only when all local edits through that sequence are acknowledged and no newer dirty change exists. Out-of-order or duplicate responses cannot roll back the displayed state. The UI distinguishes saving, saved, unsaved/offline, conflict and blocked.
If an identical save command already committed, disclose its receipt only under current draft/field rights and do not reapply it; changed payload under the same ID conflicts. Replayed old ACK is historical and cannot reset a newer draft head. A rejected save leaves prior server data unchanged and current unsaved editor input in memory while still authorized. Permission loss requires clearing revoked input from the managed UI, not retaining it under a generic 'unsaved' exception.

FD1.5 Two-tab/device conflicts
Default concurrency is compare-and-swap, never last-write-wins. Two saves based on the same server revision: one commits; the other receives a conflict with only currently authorized server/base changes and its local patch preserved. A small deterministic three-way merge may auto-rebase only when a retained authoritative base exists and the changed FIELD GROUPS are provably independent under the schema: compare server changes since base with proposed touched groups, preserve explicit clear/unset semantics, revalidate merged draft, then CAS the current head through a new merge/save command bound to the original patch.
Fields coupled by business meaning (e.g. amount/currency or period boundaries) belong to one atomic conflict group; even disjoint field names conflict within that group. Concurrent changes to the same group require the user to inspect authorized differences and choose current, own or edited values. No subjective/LLM merge, silent 'keep mine' or hidden-value overwrite. Repeated conflicts remain resumable; no unbounded retry. Maximum 2 automatic rebase attempts before presenting conflict.
Never trust client-supplied base values as the authoritative comparison. Use retained authoritative common-engine revisions for conflict resolution; storage compaction must preserve their read semantics. If an allowed retention purge or verified integrity/unavailability condition removed the base, disable auto-merge and require explicit refresh/authorized comparison before saving a new patch. Conflict payloads and version tokens expose no restricted field names/values/digests. In this single-current-editor slice concurrent tabs share current Account policy, but policy changes still re-project every side of the comparison. Inability to disclose a conflicting group must not be converted into a permission grant.

FD1.6 Navigation, offline and reload
Internal navigation tries to flush dirty input and awaits ACK; after 5 seconds without known success show saved-on-server revision and unsaved state, with stay/retry or explicit leave-with-unsaved-change warning. Do not freeze the whole app indefinitely. Browser close/crash cannot be made reliable with beforeunload/sendBeacon: last acknowledged server revision survives, unsent/unacknowledged in-memory edits may not. State this honestly; browser events are best-effort assistance, not proof of persistence.
For sensitive HR/payroll input, this slice stores offline edits only in live tab memory. No raw drafts in localStorage, sessionStorage, IndexedDB, service-worker caches, URL/query strings or analytics. Reconnection first refreshes authentication/permission and current server revision, then reconciles the same pending save command and conflicts; it does not auto-submit a business action. A browser restart restores the last permitted SERVER draft. Offline durability beyond that is not claimed; encrypted offline document editing is future reviewed scope.
Before changing Company/work context, freeze/flush pending work in its original immutable scope. Never retarget an old patch to the newly selected Company. Opening the new context uses its own authorized draft. A pending old save response may update only its own draft state; it cannot replace the new screen. Logout clears live sensitive buffers, subscriptions and managed caches; drafts remain server-side under retention/current policy.

FD1.7 Seal, exact execution attempt and commit boundary
Draft lifecycle: EDITABLE -> SEALED -> CONSUMED; EDITABLE may become DISCARDED/EXPIRED; SEALED may return to EDITABLE only after its attempt is conclusively cancelled or failed with no effect. Access-blocked/source-stale/conflict are current readiness conditions, not fake successful outcomes. No auto-expiry of SEALED/unknown attempts.
seal_draft(seal_command_id,draft_id,expected_acknowledged_revision,expected_editing_context) verifies current authority, complete normalized inputs, exact business target/basis and current required review-evidence contract. It creates an immutable DraftSubmissionAttempt with attempt_id, action/version, Company/target, exact normalized payload stored server-side, internal digest, Account/custody/assignment proof, expected business versions, and one fresh domain command_id. It freezes the draft to that revision and records attempt READY atomically. Changed data requires another explicit attempt after definitive cancellation/failure; no modifying the sealed payload. The seal response is not business completion or approval.
The user-facing submit click first saves and seals, then invokes execute_draft_attempt(attempt_id) for that exact intent in the same interaction. If the response is lost between steps, resume displays the saved sealed intent and reconciles it; a READY attempt is not presented as 'submitted'. No automatic background human impersonation is introduced. Explicit retry continues the same attempt/command while authorized.
To admit an Action to this draft execution path, its SAME-Company business owner must support one transaction boundary shared through owner-owned ports: current identity/policy guards in AI1 order -> draft/attempt ownership guard -> domain locks in prescribed order -> validate exact attempt READY and current draft assignment, current domain/evidence/state/CAS/SoD/gates -> consume any exact required gate -> business effect + domain immutable receipt/audit -> mark attempt SUCCEEDED and draft CONSUMED with result reference. All commit or all roll back. Draft owner never writes business tables; the domain owner executes the normalized payload. A generic wrapper must not preconsume governance approval.
Preflight/execute still use the business owner's current rules, not the saved schema/policy snapshot as permission. Current security/disclosure checks precede receipt presentation. Known validation/denial before effects may record a terminal REJECTED_NO_EFFECT attempt with sanitized reason under the same serialized guard; no gate/business effect or task completion may have happened. Infrastructure failure with uncertain commit stays outcome unknown until receipt/attempt reconciliation; don't declare rollback from an HTTP timeout. Actual database rollback leaves READY and permits same-command retry while current authority holds.
Separate transactions for seal and execution are deliberate: a crash after seal leaves a durable unexecuted intent; a crash after the atomic effect leaves SUCCEEDED/receipt together. There is no success gap requiring an LLM or UI guess. Existing projected-usecase owners currently own their transactions; owner participation in this protocol must be explicitly adapted and tested before that Action is enabled. Do not claim that reusing PreparedCommand alone supplies this atomicity.

FD1.8 Duplicate execution, cancellation and task result
One active sealed attempt per draft; attempt and domain command IDs are unique in Company scope and bind exact actor/action/target/payload. Duplicate execute requests serialize on the same attempt/domain receipt. SUCCEEDED returns only the currently allowed original result without executing again; REJECTED_NO_EFFECT/CANCELLED cannot later execute when permissions return. A changed request gets a new attempt only through an explicit edit/seal sequence. Action outcomes requiring a further approval remain that action's truthful pending business state, not the draft's unfinished input.
cancel_attempt(cancel_command_id,attempt_id,expected_version,reason) locks the same current-authority/assignment/attempt guards as execute. If READY and no effect can still commit outside that protocol, mark CANCELLED and unseal/restore editable revision. If execute wins, cancellation sees SUCCEEDED and refuses to undo it; link the authorized owning correction path. Unknown/running cannot be cancelled merely because receipt lookup returned empty. A delayed execute after cancellation checks terminal attempt state and cannot commit.
Task completion is the owning task/domain transition, not inferred from autosave or draft CONSUMED. Where the admitted business Action itself owns task completion in the same transaction, it does so and records its receipt. If task closure is a separate owner, draft success does not falsely close it; expose the business result and that owner's still-pending task truth. General cross-owner task orchestration remains B04.

FD1.9 Work handover and private-intent protection
Work-bound drafts link to the durable atomic task and original creator/editor provenance. Work assignment changes through the task owner, with expected assignment generation, current suitability/authority and exact scope. The draft owner follows the new CURRENT assignment only through an atomic handover barrier for that WorkItem/draft set: task owner assignment guard and draft/attempt guard join the same Company transaction/order before enabling this path. If an assignment owner cannot participate, do not expose its draft handover until an equally safe reviewed protocol exists.
A handover plan lists the exact task/action/draft scope and new Account; policy independently determines which fields the successor may see/edit. It does not clone every old permission, change the original human author or turn 'external' into a barrier. Ordinary incoming drafts remain EDITABLE under a new editing epoch. Commands carry the editing-context token from authorized start/resume, including assignment/custody generation and lifecycle epoch (FD1.14); A -> B -> A never makes old A commands current again. The old actor's in-flight save/execute either commits before the handover fence or loses authority afterward; old tab writes cannot reclaim ownership.
For a SEALED old-actor attempt: if SUCCEEDED, preserve the old actor/result and give the successor a permitted readback/next business task, never resubmit it. If READY with no effect, handover cancels it under the same fence before assigning a new editable intent; the successor must inspect permitted inputs and explicitly seal a NEW command under their own identity. If unresolved execution is in flight, serialized owner resolution precedes transfer; do not transfer an unknown attempt as if it had not run. The barrier supports this bounded synchronous case, not arbitrary distributed worker takeover.
A successor with fewer field permissions receives only permitted saved values and an authorized restricted/missing-evidence state. Hidden fields remain protected in storage and are not cleared by their next patch. They cannot submit a command requiring human review of those hidden fields; either another eligible task actor handles that atomic work or policy-approved field-scope input work proceeds separately. Explicit authorized manual reassignment remains available when automatic matching cannot find one candidate.
Account-owned private drafts do NOT automatically transfer on employment departure or managerial request. Departure preserves Account/self-service continuity while revoking only dependent work rights. A user can explicitly publish/submit or convert an eligible private draft into a work-bound intent only through a governed owner action that previews the disclosed fields, recipient/work scope and consent/approval required by policy; the conversion is not a generic admin 'take ownership' endpoint. That optional conversion is not needed to implement automatic work-bound continuity and is not silently enabled in the first slice.

FD1.10 Authorization, SSR and attachments
Every draft start/read/save/history/conflict/seal/execute/discard/transfer operation evaluates current Account/resource/action/property rights. Company RLS applies even to Account-only applicants; no dummy Employee/role is required and no CompanyActor is a feature grant. Draft content itself has policy custody; access to the eventual employee object alone does not imply access to another person's private intention. No rank/title defaults.
SSR builds only permitted draft view DTOs; no hidden values/field names/internal effect digests in HTML, hydration, inline state, exception logs, draft search, counts or notifications. Authenticated sensitive responses are private/no-store absent a separately proved strategy. Resuming a draft rechecks current references/policy and clears revoked managed props. Link previews to the draft reveal only what the receiver may discover; sharing a chat link does not transfer private intent.
Attachments are typed references to staged storage objects with separate uploader/draft/resource policy and safety status. Draft save does not make uploads public or copy file bytes into JSON. Seal requires required attachments to be durably available and acceptable; pending/failed scan or revoked entitlement blocks the affected Action. Discard/expiry releases only this draft's reference; a file already referenced by a committed domain object must not be deleted. Staging storage/scan lifecycle integration needs its owner contract before attachment-bearing Actions activate; initial input-draft proof may use existing authorized immutable evidence refs, not fake uploaded objects.
Audit stores necessary operation IDs/actor/scope/version/outcome references; avoid complete raw inputs, raw payroll values or confidential narrative in ordinary logs. Saved revision content is governed draft data, not indiscriminate immutable audit payload. Existing domain receipts retain their owner-specific disclosure/retention rules and must not be copied wholesale to a broadly visible draft list.

FD1.11 Bounds, retention and deletion safety
Proposed pilot limits to validate: canonical serialized current draft <=64 KiB; patch <=16 KiB; owner schema supplies smaller per-field/list limits; metadata-list pages <=50; at most one in-flight save per tab and bounded two automatic rebases. Reuse full snapshots in the common revision store initially; coalesce input and suppress no-op revisions. There is no 20-revision destruction rule. Keep the complete draft chain through its approved retention window; query it with keyset pagination, not full-chain fetch. Retained bases remain readable beyond 20 edits. Measure write/storage cost before changing the common engine to deltas/checkpoints. Store intended inputs and typed references, not copies of every linked business entity; see FD1.16.
Proposed retention policy for later exact design approval: Account-owned EDITABLE draft expires 30 days after last accepted save; active WorkItem drafts do not expire solely because a colleague is absent; after the task is terminal or explicit draft discard/consumption, draft input payload becomes eligible for purge after 30 days, subject to approved retention/legal-hold policy. This is a product default proposal, NOT a Korean statutory retention conclusion. Policy must be explicit/versioned before tenant activation; no perpetual retention inferred from account continuity. Sealed/unknown attempts are reconciliation work, not auto-delete candidates.
Purge eligibility runs through draft control and the common revision owner with the same guards; no unknown/in-flight effect or retained required pin may exist. FD1.16 restricts physical deletion to whole expired draft chains through a separately reviewed retention capability; existing append-only triggers prohibit it today. It is not an ordinary runtime DELETE or a promise that current disposal deletes payloads. Keep the minimal tombstone/result/command-binding evidence required by the approved retention and domain replay contracts; the domain receipt remains with its owner. An expired/deleted draft ID is never recreated implicitly by save/execute; obsolete clients receive nondisclosing expired/unavailable and cannot replay a purged intent into a fresh business effect. Exact metadata retention and legal hold inputs need their own qualified operations policy, not magic infinite retention.
Expiry/discard may close unsubmitted private input, not withdraw a submitted application/PTO/payroll decision. Unsealing after no-effect failure preserves permitted saved input and allows correction; it does not remove the old attempt's terminal replay guard. Backup restore must preserve draft/attempt/domain receipt consistency and reapply current access/retention controls before serving recovered payloads. No production deletion is performed by this evidence.

FD1.12 Adoption and remaining scope
First full-depth proof should use the current payroll wage/review owning Actions: save incomplete authorized inputs without changing wages; two-tab conflict; current-policy seal; exactly one domain write/receipt/CONSUMED transition; stale/denied execution preserves recoverable draft. The same contract covers applicant/own-record paths once their owner DTO/actions from candidate03 exist; no separate applicant auth realm.
Rollout: common revision-owner guard and Account/Company identity closure -> draft instance type plus control/attempt bindings (no parallel history table) -> deep edit-schema validation and all-route draft property/history policy closure -> bounded save/resume UI -> participating domain owner transaction ports and cancellation/assignment guards -> exact admitted Action enablement. Existing policy-domain drafts remain with policy owner. Existing direct business routes keep their same command/receipt/domain guards and cannot replay a cancelled draft command through a bypass path; command provenance/sealed-attempt binding must be checked at the shared owner before enablement.
Rollback disables new start/seal/effects while keeping authorized saved-draft read/reconciliation, terminal attempt guards and business history. Do not roll back to an owner that ignores attempt cancellation or to a UI that mistakes SEALED for submitted. This contract does not implement B03 Group dispatch, general B04 automatic reassignment, encrypted offline persistence, full sheets coediting, all B07 screens or B08 monetary statement publication. No executable product tests or production Actions before current delivery gates.
