RR17 — One shared custody/adoption/disposal/recovery mechanism
RR17.1 Reuse, identities and confined storage
Reuse common instance revisions/drafts/attempt snapshots, Docs objects/copies/custody/holds, erasure-ledger chain, storage adapter and ExternalSealSigner. Docs dispose_object marks custody DISPOSED but does not physically remove bytes; its evidence_disposal.complete audit label is not physical-erasure evidence. Concrete storage already has delete_object_version/head_object_version; expose those through the exact-version capability rather than replacing the adapter. Generic S3ObjectStore key DELETE, optional checksum comparison, an ETag or provider success alone never proves the admitted target/version removed.
Proposed shared controls (schema shape inretention-records.json): retained_units and payload locations; content_pins; domain_adoptions; disposal_jobs; disposal_manifest_items; disposal_batch_receipts; journal_acknowledgements; recovery_admission_receipts. RetentionPolicy/hold purpose/configuration uses existing governed objects and Docs hold ownership, not duplicated per-business cleanup services. Typed unit kinds/owner adapters are a closed compiled registry: common draft chain, normalized attempt snapshot, exact Docs artifact copy, declared derived projection. Any new payload-bearing copy/adapter must enroll inventory/disclosure/disposal behavior before activation. Schema-type identity, not a narrative or arbitrary SQL selector, chooses the adapter.
Retained unit identity survives payload disposal as a minimal tombstone. Pins/adoptions/manifest link to that identity; physical revision/object copy IDs remain exact expected targets and hashes in the typed manifest. Units in Company never become Group-owned because a parent job selects six Companies. Account root is never a draft disposal unit. A domain adoption record uniquely binds owner result, exact normalized submitted snapshot plus all required notes/evidence/artifact versions, policy/retention obligation and current source custody. Adopt and release draft-only content pin in SAME owning transaction. A draft chain with any active revision pin is retained whole; domain/source pins independent from private-draft pins. READY/UNKNOWN or unverified snapshot adoption never releases pin. A retained domain snapshot must be genuinely independently readable after draft payload removal.

RR17.2 Prepare, journal and batch protocol
Prepare under current authority/work/draft/attempt/retention-unit/hold guards, following the global total order and predeclared EXCLUSIVE needs. Verify eligible terminal class/window, no unknown attempt/content pin/hold and exact payload copy inventory. Quarantine unit and freeze ordered manifest of exact registered targets, expected digest/size/version, immutable schema and cancellation generation. No deletion before independent journal accepts INTENT and its current readback. Job is not a permission token; every batch rechecks current generation/state/holds/manifest and current clock. Adding a pin after quarantine returns authorized unavailable, never a resurrected dependency.
Reuse RR1 cancellation: local CANCEL_PENDING committed after proving zero batches/no unresolved effect -> independent terminal cancellation ACK outside transaction -> local CANCELLED/epoch finalization. Every destructive path refuses CANCEL_PENDING/CANCELLED and recovered unknown phase; old INTENT ACK cannot override it. If batch already won, keep partial unit quarantined and preserve committed history; stopping cannot undo removed bytes. New hold stops subsequent batches under same fence and records what is already gone. No direct trigger disable, broad DELETE grant, client-set GUC exemption or force-delete UI.
SQL payload batches max500 rows/4MiB,2s statement cap, one job per Company/two total. At most3 conclusive no-effect retries with same batch identity; unknown cannot advance. Exact delete + row/digest-bound receipt + checkpoint + erasure-ledger borrowed append share ONE Company transaction. Existing pool-owning ledger append is extended with a borrowed owner helper, not called as a separate transaction. Ledger free-text relation/selector remains historical evidence and is never replayed as SQL. Export each committed batch receipt to independent journal and verify before next batch. Adopted evidence/mandatory receipt metadata survive. A large chain is never exposed as a valid shortened chain while batches are incomplete.
External object bytes cannot commit atomically with PostgreSQL. Use a distinct typed provider-step manifest: local durable authorized intent and quarantine -> exact immutable version deletion outside DB with conditional provider identity -> exact-version inventory/readback -> DB receipt/journal reconciliation. A timeout is UNKNOWN until exact provider state proves removal or retained object; a latest-key404 is not proof. Physical step never marks the DB unit globally complete while other replicas/versions/exports remain unresolved. Retained lock deadlines/provider holds may delay removal; show physically retained/unavailable truth rather than falsely destroy. Qualified provider/version/conformance and immutable-original requirements from15 remain prerequisites.

Provider issuance is an explicit unresolved F03 boundary: a durable SQL intent alone cannot prevent a paused/stale worker issuing DELETE after a new hold, cancel or recovery fence. The selected adapter must specify where send authorization linearizes, how obsolete issuers are fenced and in-flight/unknown requests are drained/reconciled. A hold after an already-issued irreversible request cannot promise its reversal. No external-delete enrollment until the issuance protocol and its negative cases are closed; the saga above is not proof that this race is solved.

RR17.3 Independent journal choice and proof boundary
Select a per-Company append journal with immutable event objects plus compare-and-set head at an independently operated physical site, using existing storage/signing client seams. This is a capability contract, not a claim today's SeaweedFS trait/provider supports it. journal entry contains stream/sequence, stable intent/batch/cancel identity, predecessor hash, exact manifest/receipt hash and minimal typed target refs; no salary or narrative payload. The external holder accepts an append only if expected head matches, records immutable bytes, advances linearizable head and returns signed acknowledgment binding exact accepted event and current head. Only fully accepted head-visible entries are authoritative; orphan object upload is not acceptance. Same identity+same bytes replays, changed bytes conflicts; concurrent append loses CAS and re-resolves, never forks.
Holder read_current_head uses nonce-bound authenticated freshness/readback against pinned independent trust anchors; a cached old signed tip is not a current tip. Writer can request bounded append but cannot erase/rewrite accepted events, lower head, replace verification keys or self-certify currentness. Holder/key authority and object retention/live backups are outside the restored Console DB/site. Another bucket or replica in the same failure/custody domain is insufficient. Reuse ExternalSealSigner transport/verification primitives, add the exact append/head/readback adapter and provider conformance proof inF06; do not claim an existing general sign method already implements this journal. No independent service or storage is deployed by this packet.
Current keys/rollover and maximum accepted head are independently retained. Rollover needs old/new authorized evidence and live current holder, not a restored DB choosing its own key. Outage/fork/stale-head/unknown append makes cleanup pause; existing lawfully held business work can proceed only when its own admission/dependency evidence permits, never because a cleanup timer expired. No data-erasure/legal assurance inferred from a signature alone.

RR17.4 Restore and serving fence
Restore into isolated environment: no customer ingress, authenticated reads, background dispatch, sync, notification or cleanup workers. Independently advance/fence serving generation and verify old deployment cannot keep serving/writing; restore-local counter is not sufficient. Current journal/identity/policy/source/business control recovery inputs must be independent or explicitly re-established by accountable authorized operators while isolated. Restored passkeys, deleted credential rows, old refresh families/grants and old workload credentials are NOT current authority. Revoke all pre-recovery sessions and disable credential/relationship proofs whose current state cannot be established; supervised recovery preserves Account identity without trusting a resurrected credential. Do not simply issue fresh sessions from unverified old passkeys.
Verify image/schema/object-version inventory and independent journal tip/key lineage. Reapply only confirmed typed disposal scopes using registered owner adapters and exact identities; confirmed cancellation preserves material subject to current policy. INTENT with no confirmed outcome remains quarantined until originating DB/WAL/provider/receipt evidence or governed owner resolution proves outcome; absence in an old restore proves nothing. Restore of already-confirmed deletion must not be defeated by stale restored pin/policy. If exact confirmed scope conflicts with independently current required evidence/hold or digest identities, stop/quarantine; never broadly delete around inconsistency.
Reconcile domain effects/attempts/gates/task epochs/charges/publication/Account and Group authority before admission. Journal does not reconstruct uncheckpointed payroll or lost plaintext. Independently confirmed command receipts and provider effects establish whether newer work occurred beyond restore point; unresolved target stays isolated/charged. No automatic replay of old queued business commands. Verify retained submitted evidence by exact independent identities, rebuild projections and context hints from admitted owner sources, then final catch-up to current journal head. New recovery admission receipt binds image/schema/manifest, journal tip+applied watermark, isolated unknown targets, current authority/credential state, exact retained/removed fixture checks, compatible binary and new serving generation. Partial Company admission needs proven dependency closure and honest disclosure; otherwise whole affected Company remains paused.

RR17.5 Backup and retention truth
Current CNPG manifest declares one instance,5GiB,60connections,1GiB memory limit and35d backup retention; it is not deployed capacity/RPO/RTO evidence. Historical local Barman/SeaweedFS probe restore is useful source evidence, not this integrated recovery rehearsal. Another file's older indefinite-retention claim is not current configuration. Inventory actual base backups/WAL dependencies, versions, replicas, last successful prune and oldest usable point before asserting a backup horizon. Never compute physical destruction as local deletion+35days or edit shared WAL to erase one person. Per-draft envelope-key destruction is not selected without explicit key-custody/non-reconstructability requirements; this protocol prevents serving restored disposed data but does not claim cryptographic erasure.
Proposed recovery drill targets RPO<=5minutes for ordinary restorable business data and RTO<=4hours for the specified retained dataset, measured from independently confirmed failure fencing to authorized readmission. These are validation hypotheses, not promised SLA. Confirmed journal disposition/serving-generation facts require lossless independent recovery for admission; a5minute allowance cannot justify replaying a destroyed payload or revoked credential. If prerequisites are missing or unknown effects cannot be resolved, safety keeps admission blocked even beyond the time target. Exact production target/risk acceptance remains a separate authority choice.
