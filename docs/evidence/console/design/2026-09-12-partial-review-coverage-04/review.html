설계 후보 04 · B02/B07의 부분 열람과 업무 완료 · 제품 구현 아님

각자 볼 수 있는 업무를 검토하고,
전체는 빠짐없이 완료하기

같은 급여안과 원장 객체를 유지합니다. 사람별로 실제 검토한 대상·근거·결정을 연결하고, 서버가 필요한 검토가 정확히 모두 갖춰졌는지 확인합니다. 자신이 볼 수 없는 금액까지 승인하는 마지막 결재자를 만들지 않습니다.

왜 화면 필터만으로는 부족한가

기존 코드는 급여안 전체에 제출자 한 명과 결정자 한 명을 기록합니다. 일부 급여만 표시한 화면에서 기존 전체 승인 액션을 실행하면, 보지 못한 금액까지 승인했다고 기록할 수 있습니다. 그렇다고 임시 담당자의 권한에 맞춰 급여안을 복제하면 업무 원장과 정정 이력이 사람의 권한 변화에 따라 갈라집니다.

선택한 방향은 기존 급여 소유 계층에 검토 대상·제안·결정·완료 근거를 연결하는 것입니다. 금액 계산은 기존 원장과 계산 커널이 계속 소유합니다. 별도 결재 엔진이나 두 번째 급여 writer를 만들지 않습니다.

어떤 일이 누구에게 보이는가

업무사용자가 하는 일그 일이 뜻하지 않는 것
원천 자료 준비허용된 근태·계약 등 입력을 기존 객체에서 확인·정정급여 금액 전체를 열람하거나 승인하는 권한
개인별 급여 검토해당 계산에 필요한 금액·공제·근거·차이를 보고 제출 또는 독립 결정숨겨진 다른 사람의 급여 승인
공통 항목 검토회사 정책이 요구한 합계·조정 등의 정확한 근거를 보고 결정직급에 따라 생기는 포괄 승인권 또는 기본으로 추가되는 결재 단계
업무 범위 현황권한이 있는 범위의 미완료·담당 미지정·완료 상태 확인개인별 금액 조회권 또는 다른 범위까지 완료했다는 주장

각 업무 단위에는 현재 책임자를 한 명 지정합니다. 적격자가 여러 명일 수 있어도 실제 책임이 모호한 “일부 분담” 상태로 두지 않습니다. 여러 단위를 화면에서 묶어 처리할 수 있고, 같은 사람이 서로 다른 범위의 여러 배정을 가질 수 있습니다. 직함·직급은 미리 만들지 않습니다.

실제 입력과 결정 흐름

내 업무 → 이미 채워진 허용 자료 확인 → 필요한 원천 정정 → 계산 결과·차이·근거 확인 → 검토 요청 → 독립된 검토자의 승인 또는 수정 요청 → 내 결과 확인

기본적으로 각 금액 결정의 제출자와 결정자는 서로 다른 검증된 자연인입니다. 정책상 추가 실행허가가 있는 경우에만 해당 단계를 표시합니다. 실행허가와 급여 결정은 다른 기록입니다. 회사 정책이 공통 합계 검토를 요구하면 그 항목도 같은 제출·결정 방식으로 처리합니다.

검토에 필요한 근거는 액션 근처에 표시합니다. 민감정보가 들어 있다는 이유만으로 주민등록정보나 의료 원문까지 모두 열어야 하는 것은 아닙니다. 그 결정에 필요한 필수 정보와 승인된 원천 확인 증거만 요구합니다. 필수 근거가 부족하면 다른 적격자에게 연결하고, 사용자가 볼 수 있는 다른 작업은 계속할 수 있습니다.

전체 완료의 조건

서버는 권한으로 필터링된 화면 목록이 아니라, 해당 업무 범위의 권위 있는 대상 집합을 사용합니다. 모든 대상의 현재 검토가 하나씩 있어야 하고, 추가로 필요한 공통 검토도 완료돼야 합니다. 누락·중복·반려·오래된 근거가 있으면 전체 완료가 아닙니다. 단순히 승인 개수와 인원수가 같다고 통과하지 않습니다.

마지막 개인별 또는 공통 결정이 들어오면 같은 트랜잭션에서 완료 근거를 기록합니다. 범위 정정 후 남은 검토가 이미 모두 유효한 경우에도 같은 검사를 실행합니다. 누군가 대신 클릭한 것으로 기록하지 않고, 실제 사람들의 결정과 이를 조합한 서버의 결과를 구분합니다. 이 단계는 비지급 급여 초안 검토이며 지급을 실행하지 않습니다.

숨겨져 있거나 반려됐거나 담당자가 없다는 이유로 대상을 빼는 것은 불가능합니다. 근거와 권한이 있는 실제 범위 정정만 허용하며, 좁아진 범위의 완료를 전사 급여 완료처럼 표시하지 않습니다.

수정해도 유효한 작업은 남깁니다

전체 승인 전 오류를 수정하면 원천 소유 액션으로 사실을 고친 뒤, 급여 소유 계층이 영향을 받는 계산과 검토 제안을 새 버전으로 만듭니다. 새 검토 주기 전환과 현재 대상 갱신은 원자적으로 처리합니다. 이미 전송된 원천 수정이 있다면 그것까지 취소됐다고 표현하지 않고 결과를 보존합니다.

다른 사람의 기존 검토는 같은 급여안 안에서 대상·원천·계산·정책·필수 근거가 그대로라는 사실을 검증할 수 있을 때 유지합니다. 금액만 같아서는 부족합니다. 영향 범위를 증명하지 못하거나 공통 규칙이 바뀌면 관련 검토를 다시 받습니다. 전체 승인 후에는 이전 설계의 새 정정 급여안으로 이어지며, 새 안에 이전 승인을 옮기지 않습니다.

이미 검토를 마친 담당자가 퇴사해도 유효한 결정은 남습니다. 단순한 로그아웃·권한 만료·퇴사를 이유로 같은 일을 다시 시키지 않습니다. 아직 실행하지 않은 의도, 명시적으로 회수된 결정, 변경된 원천 또는 동일인 결재 같은 결함은 구분해서 처리합니다.

보안과 실패 상태

내가 검토한 단위가 완료되면 “내 검토 완료”를 보여줍니다. 전역 현황 권한이 없는 사람에게 전체 인원수·남은 기밀 대상·숨겨진 금액·처리 시점을 전달하지 않습니다. SSR HTML과 초기 데이터, 알림·채팅 객체 카드·검색·내보내기에도 적용합니다.

응답이 끊기면 같은 명령의 영수증으로 결과를 확인합니다. 성공인지 모르는 상태에서 새 명령을 만들지 않습니다. 일괄 결정은 최대 100개 명시된 제안을 한 트랜잭션으로 처리하고, 더 큰 선택은 고정된 명령 ID를 가진 묶음으로 나눠 각각의 결과를 표시합니다. 이는 제안된 초기 운영 값이며 아직 성능을 입증한 수치는 아닙니다.

검토 결과와 다음 공백

정확한 SHA에 대한 독립 검토에서 공통 결정 경로, 정정 주기 전환, 정정 후 완료 처리의 세 가지 지적을 수정하고 범위별 수용을 받았습니다. 검토 이력도 보존합니다. 전체 설계 승인이나 구현 허가는 아닙니다.

39개 비실행 검증 시나리오와 15개 화면 상태를 정리했습니다. 상세 계약 PC1에는 객체·Action 입력, 원자성, 잠금 순서, 재시도, 기존 API 우회 차단과 롤백 경계를 담았습니다. 기준 소스 신원과 문서 무결성 검증을 함께 확인할 수 있습니다.

남은 설계는 전사 실행의 영속성, 일반적인 자동 배정·인계, 서버 입력 초안 수명주기, 나머지 화면 상태, 직원 금액 명세 공개·이의제기입니다. 이번 단계에서는 제품 코드·실행 가능한 제품 테스트·현재 권위 문서를 변경하지 않았습니다.
