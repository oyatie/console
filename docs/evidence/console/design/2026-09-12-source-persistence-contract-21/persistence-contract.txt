SP21 — Publication identity, sealed effect membership and independent custody
Selected design extends20's one actual owner transaction and17's shared retention mechanism. Keep15/18 native source revision tables with indexed typed subject/time/kind fields; keep14 common instance revisions as the sole editable draft history. Qualification kinds use the existing proposed qualification family, not tables per purpose/title. Do not replace native reference targets with an untyped JSON entity store, duplicate the draft editor in source tables or add a second command receipt namespace.

Identity and cardinality
Source roots use17's normalized names, not15's generic redundant id: calendar_id, assignment_id, coverage_id, close_basis_id, qualification_id, assessment_id, evidence_id. All references include org_id and exact positive revision. Source21 key requirements are in source-key-matrix.json. Common source revision identity checks (org_id,instance_id,id,version), owner schema and source hash under the pin fence; no UUID-only match. Account attribution uses13 company_actors, not accidental equality with users IDs.
A publication command can emit many source revisions: auto-split calendar publications with matching assignments; successor VERIFY plus predecessor SUPERSEDE; or successor VERIFY plus one immutable successor claim on an already REVOKED predecessor. Therefore NO UNIQUE(org_id,command_id) on these source-revision tables. Each immutable revision still has exactly one creating command; one receipt can bind multiple distinct effects. Every emitted revision/claim must appear once in the final result set. Scope/policy reasons never choose a new pipe.

One additional derived membership relation: ont_action_source_effects
This relation indexes native source results under the EXISTING0177 receipt (org_id,command_id); it is not a writer, draft history or second receipt. Extending that receipt with a nullable-for-legacy source_effect_protocol/count/digest distinguishes enrolled SOURCE_EFFECTS21. Legacy receipt bytes/readers remain untouched. Native18 payroll_input/calculation membership stays in its existing owning tables; no rewrapping those batches in this relation.
Registered source commands persist 1..1024 effect rows, each<=fixed member shape. This is a proposed structural cap, not measured latency. Calendar split profile fits up to366 publications+366 assignment revisions (732); any additional affected assignments/lineage effects must fit the complete registered plan, otherwise refuse before sealing/effect and retain the existing acknowledged draft. This cap does not authorize arbitrary batch actions or manual partial activation. Whole prepared-row byte/lock/load admission remains F01/F02/F08; per-leaf64KiB is not a whole-command memory budget.
Effect kinds are typed REVISION or SUCCESSOR_CLAIM and fixed source-family codes. source-key-matrix.json maps each to its actual source owner/table. Ordered effects use (family code, root UUID raw16, revision, effect kind code) with no duplicate identity. Ordinal0..count-1 is server-derived. REVISION records the exact newly created source revision and its creating command. SUCCESSOR_CLAIM records the exact previously verified then REVOKED predecessor revision and exact newly VERIFIED successor plus the claim's creating command; predecessor revision's OLD creating command must not be relabeled. VERIFIED predecessor replacement is a newly created SUPERSEDE revision, not a duplicate claim effect.
All effects carry exact source custody digest; claims additionally carry exact successor identity/digest. Receipt membership digest uses a fixed binary frame in result-membership.json. This commitment has no monetary, source-qualified or authorization meaning by itself. The SQL backstop recomputes the frame from actual constrained rows, verifies count/contiguous order/canonical identity order and exact registration/owner/Company, then checks reciprocal source membership and successor claim projection. Source row FKs tie effect entries to exact subtype/root/revision/creating-command/digest; claim refs instead tie old predecessor and new successor, plus immutable head claim evidence. Cross-Company refs and a valid revision of a different kind/subject must fail even if the digest matches.

Prevent append after completion
Deferrable checks run on BOTH receipt insertion and member/source/claim insertion, not only on the first header. At transaction end the immutable receipt names exactly the complete set, every member resolves, every source emitted by this command is included, and each claim matches its unique predecessor head linkage. Immutable members cannot UPDATE/DELETE. Inserting a late member cannot expand the sealed receipt count/digest; inserting a late source without a member fails reciprocal membership. Runtime/generic writer paths are DB-denied under20. Privileged migration/maintenance paths remain separately trusted and catalog-reviewed; a trigger does not protect against an adversary allowed to disable it.
The cycle source -> effect member -> receipt -> complete source set is checked at transaction end, using deferred composite FKs/constraint triggers. No committed PENDING business source, separate finalize job, or swallowed partial helper error. Exact source table DDL and all trigger/helper bodies remain F02 prerequisites, not implemented by this document.

Source selection and heads
Publication root IDs and immutable subjects are fixed before commit; revision advancement uses expected head+1 with checked i64 overflow and one writer under20 guards. Root creation absence is serialized under the registered creation key. A newer exact calendar revision does not silently rewrite assignments naming an older retained calendar revision. Eligibility of the exact selected version is determined by current governing rules/explicit revocation and effective dates, not max(revision). Calendar/assignment root/head concrete DDL and temporal selector completeness remain required F02 work; unknown/gap/overlap produces a blocker.
Coverage has immutable Company/employee/Employment/full-month subject. Matching the current employment_source_bindings projection is insufficient after exit/rehire; historical binding and exact effective Employment are needed. Close membership matches Company/employee/period and current native input/source validity including WAGE SHARE from corrected20. Actual operational amendments have UUID sets, no invented amendment_revision counter. Package bytes stay authoritative preserved evidence; indexed reference/member projections are validated from exact bytes and sealed in the same finalizer, never a competing editable truth.
Qualification/eligibility/tax PROPOSE starts admission revision1. VERIFY is a separate event with exact original admission digest; executable references name VERIFIED event revision, not proposal1 by default. Event custody digest and original admission digest are distinct. Current qualified independent-human checks remain trusted Rust plus current identity/source dependencies; SQL checks exact event/head/claim shape and monotonicity. Revoking a successor never revives its predecessor.

Independent adopted submission
The adopted domain submission is a DISTINCT retained_unit from the private draft chain and attempt payload, using17's same custody registry/adapter mechanism. A second location of the private unit is insufficient: its disposal inventory would either retain private drafts forever or erase domain evidence. The source/domain obligation owns the new snapshot unit; all result refs retain it through purpose-bound adoption records. Multiple effects may share one exact adopted command snapshot where their obligation/read scope permits, with per-result/purpose adoption links; do not copy full submission once per split result needlessly.
The distinct domain snapshot UNIT IDENTITY and its real guard row must already exist before final source publication, as20 LO9d requires. Stage that identity through the existing common retention preparation owner as an explicit registered action before source command sealing, bound only to the exact acknowledged draft/control/input/schema/custody identity that already exists. No future domain-command reservation is presumed:14 reserves that command at seal. The seal transaction atomically adds an immutable one-attempt/command linkage to the pre-staged unit under the declared fences; it does not retarget the unit payload identity. A later resealed attempt needs a newly prepared unit identity/linkage, not reassignment of the cancelled attempt's unit. This is an automatic orchestratable preparation step, not a new receipt/approval engine or business adoption. It may hold an empty/staged snapshot location until publication; immutable required input identity is fixed and the finalized copy digest is verified separately. A UUID with no retained-unit row cannot be locked. Missing/stale/quarantined preparation refuses finalization and returns to preparation/reseal after conclusively ending any old attempt; historical replay never stages anything. Full retained-unit selector/state/location DDL remains F03 and must represent this distinction before enrollment.
The adopted data includes exact normalized source19 body, required outer reason/notes, expected references, original Account, schema/codec, source draft revision UUID/version/hash, immutable command fingerprint, and exact gate/evidence provenance required for the decision. A naked payload digest cannot replace readable evidence. Retain only purpose-required data and apply current field/history disclosure on every later read. Generic audit and receipt must NOT copy full InstanceState/attributes/notes; actual ontology REST's generic serialization must refuse/delegate enrolled sources and private drafts.
A source has permanent lineage to retained draft/control/attempt identity but no RESTRICT dependency on disposable private attributes/reason. Source readable evidence resolves through independent domain adoption. Actual0155 append-only triggers currently prohibit private deletion/nulling:21 does not relax them. Until a confined, separately proved retention transition exists, cleanup remains unavailable. CompanyActor identity persists after exit and does not itself grant access.
