IF21 — Verus information-flow and cross-customer isolation proof targets
Owner clarification: tenant means CUSTOMER GROUP, not Company. Pilot is one tenant containing six Companies; Company remains legal/RLS cell. This proof compares distinct customer tenants A and B. Intra-tenant Company access remains Cedar-controlled and may intentionally span several Companies. Neither a Company UUID check nor a Company-scoped RLS test alone establishes cross-tenant isolation.

Security property, not a tool checkbox
Broaden20's Verus candidate beyond arithmetic to a small verified information-flow core: binding immutable active customer context, projecting domain results, constructing allowed operational events and admitting outbound payloads. Use the actual executable Rust path with ghost specifications, not a separate demonstration calculator/filter. Official Verus supports specified Rust verification and concurrent reasoning; no inspected source establishes an automatic whole-program information-flow checker. Noninterference requires an explicit relational specification (e.g. two executions/self-composition), proofs for every allowed transformation and a justified connection to every real sink.
The ordinary tenant-serving path must not release B's business data in active tenant A context, even if one login Account has separate access to both tenants. Switching tenant context is a new authenticated, authorized request context; no mixed cache/queue/cursor/object result is carried over implicitly. Global Account authentication/recovery and legitimately public platform registry data are separate owned inputs, not Company/tenant business records. Cross-tenant exchange, if introduced later, needs its own explicitly approved narrow release contract; this packet grants none. Same-tenant cross-Company authorization is a different property and does not weaken the cross-customer invariant.

Relational target
Let Obs_A be the exact externally observable event trace at the selected logical sinks for active tenant A. Let s ~A s' mean identical A-visible state, authenticated active context, governing policy/topology snapshot, public inputs and explicitly permitted release values, while B's private business state may differ. For the same admitted A request and coupled public environment, prove:
  s ~A s'  =>  Obs_A(run(s)) = Obs_A(run(s'))
State the public scheduler/randomness coupling and termination assumptions explicitly. DB/cache/error/queue/I/O values, delays and branch/event occurrences that may depend on B are part of the implementation relation to prove or refine; they cannot be assumed equal merely to make this theorem pass. B-derived metadata cannot be relabeled public or added to permitted release values. Public environment coupling excludes secret-dependent adapter outputs. A proof only comparing final returned values after both runs terminate is termination-insensitive; it is NOT a timing, availability or traffic-analysis guarantee. Extend observation to event occurrence/order/count/status/body/headers/lengths/notifications/outbound destination and error classes where actually modeled. Do not infer full noninterference from ordinary type safety or one-run tenant_id equality.
Tenant separation also needs state integrity: an A command cannot mutate B-owned business state. Current Company->tenant ownership is derived from authoritative topology under its fence, not a client TenantId and not an unchecked claim in stored payload. A typed context and composite keys help enforce the precondition; Cedar/SQLx/PostgreSQL correctness and current operand loading need a separately justified contract/refinement. They are not proved by writing assume(tenant_matches).

Direct and implicit flow
A sensitive wrapper without Display/Debug/Serialize prevents some direct mistakes, but raw extraction/aliasing/formatting/error conversion can bypass it. A secret-dependent branch that emits the same constant log only on one path leaks a bit; a filtered list count, different404/403, cache hit header, debug panic, metric label or notification presence may also leak. Verified flow tracks data dependencies AND control dependencies, or proves two-run observation equality directly. Merely logging a fixed enum instead of a string does not prove constant event occurrence. Tenant IDs/resource IDs/digests and metric dimensions can themselves be restricted metadata.
Reuse owning projection/DTO and redaction boundaries where they fit. Domain models must not acquire blanket public serialization just to simplify SSR. Model permitted disclosure as a narrow release decision for exact active tenant/principal/resource/field/purpose/sink/current authority window. It cannot be a freely constructible allowed=true marker. A release decision for browser viewing does not authorize operational logging, email delivery, export or a third-party request. Dynamic Cedar behavior is not replaced by static job titles or an enum of user personas.

Sinks and transport
Operational logs accept only reviewed non-sensitive event data and permitted occurrence patterns. Required sensitive audit evidence belongs in a separately access-controlled retained audit store with encryption and purpose-bound reads. Encrypting a log store does NOT authorize copying every sensitive payload into operational logs; future decryption/access remains a disclosure channel.
For outbound traffic, prove authorized message construction and destination/credential/tenant binding, not a cryptographic theorem from send_https(). Plaintext sensitive bytes must not reach an unapproved egress sink. TLS/AEAD implementations, certificate/hostname checks, key management, provider behavior and OS/network enforcement remain explicit trusted/external boundaries. Ciphertext depends on plaintext; literal two-run byte equality cannot be claimed for ciphertext. Computational confidentiality requires cryptographic assumptions, and lengths/timing/destinations may remain visible unless separately padded/hidden.
Required deployment checks cover redirect targets, DNS/rebinding, proxy/environment overrides, DNS labels/URLs/query strings, retries/alternate transports, SMTP TLS downgrade, object-store endpoints, tracing exporters, panic/core dumps, process stdout/stderr, queues/dead letters and browser third-party requests. SSR controls the initial serialization, but hydration JSON/HTML attributes, caches, websocket topics, downloadable links and browser egress still need the same policy. Do not claim Verus verifies these adapters by wrapping them in external_body.

Proof boundary and acceptance
Initial finite target: selected tenant-bound result projection + operational event builder + outbound release admission on the actual production call graph. These are candidate boundaries, not invented installed types or an implemented central service. A runtime-checked facade must establish verified preconditions for unverified callers; run applicable check-safe-api. Inventory every raw source accessor, serde/Display/Debug impl, SQL/error conversion, external_body, assume_specification, unsafe/FFI boundary, feature/cfg and effectful dependency reaching the sinks. Omitted callers/sinks invalidate a whole-path claim. Preserve20's full-toolchain pinning and nonvacuity checks.
Before claiming a selected theorem: independent review of s~A, Obs_A, allowed release, current policy window and all assumptions; nonempty concrete A/B fixtures; verifier rejects deliberately wrong tenant, secret-dependent log branch and omitted-field/redaction mutations; ordinary builds and meaningful runtime canary/RLS/egress checks exercise the same exec path. Build-time dependency/import/route checks and deployment egress restrictions make bypass harder but do not independently prove noninterference.
Shared DB/cache/CPU/memory/scheduler/resource contention can expose timing/availability across tenants even when logical payload isolation is proved. Constant-time crypto, bounded work, quotas and stronger process/cell isolation are separate defenses; no claim all such side channels are closed. A malicious database administrator, OS, verifier/compiler dependency, approved recipient or key holder outside the stated trust model is not defeated by an application proof. Distinguish these limits in every proof report instead of advertising an unconditional system-wide guarantee.
No Verus proof, SQL test, sink-completeness audit or production guarantee has been executed in21. The source census is a bounded initial inspection. Existing literal-only pii-no-logs explicitly misses interpolated/data/control flow; current broad DbError formatting and Debug-capable credential structs are candidate paths to audit, not confirmed exfiltration events. Verus must evaluate confidentiality alongside arithmetic, not wait for money-only proof adoption. F04/F08 include the exact information-flow and sink/refinement acceptance contract; full deployment/crypto proof remains separate.
