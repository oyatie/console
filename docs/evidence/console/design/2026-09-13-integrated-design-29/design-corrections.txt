CaseRespond accepts current case/task expectations, explanation and one typed disposition per current issue item. No user must publish a content object before typing or submitting a question. Ordinary explanation still matters: handler's task view surfaces it beside relevant facts under current disclosure.
The existing payroll request/append/respond finalizer calls common.create_case_content in its borrowed Company transaction. The common revision stores exact ReviewRequestContent or ReviewResponseContent; the native case/response references that real result. Request input contains no future content revision/hash. The sealed intent and OWNER_SUBMISSION contain the typed original input; generating a later common revision never changes the original command fingerprint. Replay first returns the prior receipt under current disclosure and never creates another content revision/task.
For a new request, payroll reserves actual case identity from the command's allocated target, validates current historical-subject/target/item/evidence permission, derives ReviewRequestContent from input, creates its immutable common instance/revision and native case membership, then creates the workflow task or unassigned exception and all custody/receipt participants before one commit. It neither requires active Employment nor invents an assignee. A missing-publication inquiry checks known permitted Employment+period without looking up or exposing a hidden run.
CaseAppend is the next full request-content revision, composed automatically from currently permitted acknowledged values plus user's edits. Payroll checks expected case/content/issue revision, immutable target and subject, same original request content instance, unique stable issue IDs and presence of all existing issue IDs (no implicit withdrawal by deleting an item). The complete set stays<=64, total registered bytes<=64KiB; per-field maxima are not permission to exceed the aggregate cap. A caller need not retype old narrative: the composer carries it forward and lets them add clarification, with exact prior versions retained. Old issue identities/claims and original authors remain readable under history policy. The new current issue revision and common head change together. A stale handler response cannot cover a newly appended issue using its old expected revision.
For response, payroll validates exact current issue coverage and responsible task/actor, including inherited distinct-human resolution rules; builds one ReviewResponseContent containing all item explanations/dispositions; common owner creates one response content instance. StoredIssueDisposition contains only item_id,kind,content_revision, with every revision pointing to this same exact response content and matching its decoded item. Native membership has no independently writable text mirror. Domain correction/work/publication references inside that content remain subject to owning guards. OUTSIDE_SUPPORTED_PROCESS stays pending and requires real accountable follow-up; it is not RESOLVED or CORRECTED. No new separate user content-publication workflow or generic privileged CRUD bypass is selected.
All case narrative, item descriptions, claims and disposition text use the existing current Cedar projection boundary for requester/handler, exact schema field groups and origin Company; no raw content enters broad receipt/audit/log. 3. One field address for read, edit and errors
FieldAddress=(field_id,parent_item_ids,item_id|null). field_id identifies the compiled exact schema field; parent_item_ids contains ONLY containing repeated-item identities from outer to inner. item_id identifies this field's current repeated item, not an ancestor. It is null for the field itself or an ordinary child field, and nonnull for a scalar/record/list item in the field's repeated collection. The schema registry maps each level to its fixed owner path; no caller supplies arbitrary JSON paths. Maximum containing depth8; current item cannot repeat an ancestor ID.
All Patch variants, ProjectedFieldNode and field error entries share this exact address. SET/CLEAR/SET_INCOMPLETE target scalar fields or scalar collection items. CLEAR on a scalar item leaves that stable item present with Unset value, rather than removing/reordering it; REMOVE_ITEM explicitly removes. SET replaces the typed value while retaining identity. SET_INCOMPLETE records exact bounded editor text and blocks complete submission until parsed/fixed. INSERT_ITEM requires a fresh nonnull current item ID. REMOVE_ITEM and MOVE_ITEM require existing nonnull current item ID. CREATE_CONTAINER uses null item_id for a singular container field and fresh nonnull item_id for a record/list collection member. It cannot reset an existing container silently. after_item_id/previous_visible_item_id must be null or a permitted sibling of the same parent collection; no ordinal, hidden sibling or stale ID is inferred.
Example scalar tax list F: insert address(F,[],S1)=1 and(F,[],S2)=2. Set incomplete address(F,[],S2) to '-' and save; reload returns the same S2 with INCOMPLETE('-') and S1 unchanged. SET(F,[],S2)=3 repairs it; a concurrent removal of S2 gives preserved-input conflict, never retargets S1. Error address for S2 is identical. Scalar-item field semantics validate element type, not the list container type.
Example nested calendar: record duty D in duties uses address(duties,[],D); its start field uses(start,[D],null); break record B uses(breaks,[D],B); break start uses(start,[D,B],null). Disallowed or nonexistent parent/item returns authorized generic conflict without leaked labels/values. Atomic coupled-field validation applies after the whole save, as before. Complete-row deletion is explicit and historical revisions remain retained. ProjectedFields pagination remains exact-snapshot/current-policy bound and can repeat permitted ancestor context; address identity deduplicates it.
