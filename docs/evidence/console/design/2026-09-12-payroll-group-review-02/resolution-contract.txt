Proposed gap resolutions for independent review — not implementation authority

D01. Domain and scope
Console remains the full native-object operating system / Foundry-suite target. This candidate covers payroll draft execution and group management contracts only; HR/attendance/labor and shared approvals, communication, calendar and sheets remain required subsequent depth. No new generic Foundry engine is introduced to bridge native payroll inputs. Existing payroll owner and calculation kernel remain the sole payroll writer and arithmetic owner. Active PRODUCT expansion is still an unapplied, separately governed amendment.
Pilot facts: one Group tenant, six Companies, 2,000 people total, Console operated. Multi-company actions are per-company writes. Group-wide settings are Group-owned facts, never a seventh employer. Load/SLO values in prior research are experimental assumptions, not approved SLA.

D02. Calculation unit and immutable input revision
A payroll draft run belongs to exactly one Company, one inclusive period_start/period_end Date pair, and one explicit pay_date (default period_end). Support initial full-calendar-month periods only; convert to [start,next_month) only for temporal intersection queries. Never change the existing wire interval silently.
The existing draft_run_id is the business run key. The caller's create run_id is correlation only and survives retry. Calculation unit for the first supported kernel is one employee in one Company and pay period, with exactly one effective Employment throughout that period. More than one simultaneous Employment requires a later aggregation policy and blocks this first kernel; never silently sum or discard it.
PayrollInputRevision logical identity is (org_id,draft_run_id,input_revision positive integer), unique; run head holds current_input_revision and a monotonic run_revision. A unit is (input_revision,employee_id) and binds the exact employment revision; no prior-roster line can participate unless present in this revision's immutable membership. Excluded prior units remain historical. Every source carries owner kind, Company, object ID, immutable revision or content hash, effective period, provenance reference and validation status. Do not invent mutable revision IDs for immutable existing wage rows.
Manifest includes schema version, Company/run/period/pay_date, sorted calculation units and source references, normalized integer-won inputs, applicable rule build/version and typed blockers. Canonical encoding and SHA-256 cover these fields; hash excludes display text and transport timestamps, includes the identity/hash of relied-on notes or attachments. Mutable annotations remain visible as newer annotations, never rewrite a signed snapshot.
prepare_inputs requires command_id, expected_run_revision and expected_input_revision (0 before first preparation), full target selection and typed source references. In one Company transaction, lock run head; recheck current authority and source versions/eligibility; build the complete revision including blocked units; append immutable revision/membership; advance head once; append owner audit and receipt atomically. Competing same-base prepares: one succeeds, other stale_revision without writes; identical command/payload replays its receipt. No fake data_import_rows.
Native and imported adapters normalize into this same manifest; imports are evidence, not a second calculation writer. Existing imported runs remain identifiable legacy snapshots until explicitly prepared/migrated; never label legacy historical calculations as newly verified.

D03. Wage entry and correction
Reuse employee_contract_wages and payroll's writer. Original wage rows remain append-only with their existing unique effective date. Introduce an append-only wage-correction chain owned by payroll rather than changing an error into a fictional next-day raise. Identity is base_wage_id plus correction_revision; each revision references the previous revision (0 = base), original effective_from, employee/company, corrected wage_kind/amount_won/monthly_standard_hours, evidence refs, reason, actor and receipt. Unique(base_wage_id,previous_revision) prevents forks; expected predecessor CAS; old rows never update/delete.
All wage readers, including existing payslip-draft lookup and native prepare, must resolve the same latest correction for a selected effective-date base. A newly effective wage is a new base row. A correction may change values for that date but cannot retarget employee/company/effective date; that is a separate future employment/contract amendment. Bounds preserve existing DB rules: amount positive signed 64-bit won; hours 1..400; source_note <=500 characters.
Wage create/correct require current PayrollRunManage, same-company employee and readable evidence. Command replay and payload conflict use existing owner receipts extended to these commands. Response loss recovers by command receipt, never guessing which same-date row succeeded. Existing POST without command key retains uniqueness conflict semantics; upgraded UI uses versioned command. Old readers must be upgraded before correction writes are enabled; rolling back to a reader that ignores corrections is forbidden after first correction.

D04. Tax evidence and supported-case gate
Add payroll-owned admit_tax_evidence and verify_tax_evidence actions, not a client verified boolean. Admission records immutable source artifact reference/hash, issuer/table version, exact row locator, applicable date range, income basis/band and subject-specific selection inputs (including household/dependent/withholding choices where the source requires them), exact income/local tax amounts and Company/employee/Employment/period. The source's units and interpretation are explicit. Underlying file/object access is checked; a URL alone is not custody.
Verification requires separate governance authorization for payroll tax evidence, current PayrollRunManage, and a distinct resolved natural person from the admitting actor. Verification binds all those fields and manifest hash; accepts only an approved source/rule reference supplied by the qualified source-review process. Missing or unknown source approval is blocked, not inferred from a domain name. A synthetic-only fixture source is admitted through the same actions in disposable test databases and cannot be enabled in tenant production by a request flag.
Verification is immutable and has validity bounds plus append-only revocation/supersession. On prepare/close/calculate/submit/decide, recheck current revocation and applicability; a revoked or mismatched source blocks new progression while prior immutable calculations remain inspectable by authorized readers. No consumer can promote imported VERIFIED_SOURCE_ROW text into independent source verification.
Supported positive case: exactly one full-month Employment; unchanged MONTHLY wage covering the whole period and pay_date; no mid-month hire/exit/wage change, unpaid reduction, overtime/premium/other earning adjustment or competing Employment; closed complete attendance; explicit approved applicability facts matching every deduction the existing kernel computes; exact documented income basis matching the tax evidence row; supported pay date/rate version and pension basis. Unknown applicability/basis is a blocker, never a default true or zero. Contract gross equals the verified ordinary-monthly wage only in this supported case. Each exclusion has a typed reason and owning correction path. This candidate does not claim those exclusions cover the entire payroll product.
Synthetic positive fixtures must choose this supported profile explicitly. Real official-source qualification, tax policy and legal/payment clearance remain external authority HOLDs; code acceptance uses clearly synthetic source evidence and cannot establish Korea compliance.

D05. Correction and transition matrix
Every command is fenced by expected_run_revision, expected_input_revision and, after calculation/submission, expected calculation/submission identity; existing preflight and execute use the same guard, execute rechecks under the owner transaction. Eligibility refresh must detect relevant source insertions as well as changes to already selected rows. No after-the-fact job is the only stale-source defense.
prepare_inputs: STAGED|BLOCKED_LEGAL_GATE|READY_FOR_REVIEW only -> STAGED with new input revision; blockers describe readiness, not hidden state changes.
close_attendance: those three preparation states only + nonempty manifest/current sources, complete attendance and valid covering period lock + explicit attest -> ATTENDANCE_CLOSED binding exact input revision. Pending leave warning remains warning unless its facts invalidate supported calculation eligibility; no new legal refusal invented.
calculate: ATTENDANCE_CLOSED only + exact closed input revision/current sources -> CALCULATED with new immutable calculation version, line results/blockers, payable=false. Existing transactional CALCULATING is not durable progress. Partial results carry no whole-run net total; submit requires every active unit calculated and no open required exceptions.
submit: CALCULATED only + current complete calculation/sources -> SUBMITTED; append immutable submission snapshot containing input/calculation/roster/evidence digest and submitter identity. Submissions never follow a mutable run head implicitly.
decide: SUBMITTED only + exact submission identity/current sources, independent natural-person proof and policy -> APPROVED or REJECTED; reject reason mandatory; immutable decision. APPROVED remains nonpayable.
reopen_inputs: STAGED|BLOCKED_LEGAL_GATE|READY_FOR_REVIEW|ATTENDANCE_CLOSED|CALCULATED|REJECTED -> STAGED with reason, prior run revision CAS and stale current close/calculation references. It appends a supersession record without rewriting previous results/decisions. Subsequent prepare creates the next input revision. Does not unlock attendance globally; valid existing close evidence can be referenced again only after the close guard revalidates it.
SUBMITTED requires explicit cancel_submission by its submitter or a currently authorized replacement manager with reason, exact submission CAS and audit -> STAGED, invalidating the submission for decisions; race with decide has one winner under the same run lock. No silent withdrawal by a source-change worker. A source change instead renders the submission stale and disallows a decision until cancellation/reprepare.
APPROVED and every payment/issued state forbid reopen/cancel in this slice. An approved incorrect draft is displayed as requiring a separately reviewed superseding-run correction process; it cannot be paid under this slice. No implicit compensation or reverse payment.
Existing REJECTED->CALCULATED withdraw remains an unchanged-input path only: permitted if the exact calculation/source snapshot is current; otherwise return stale_source and direct to reopen. It is not recalculation.

D06. Shared authorization, approval and adapter compatibility
Extend the existing owning application/port boundary; REST, canonical Action and UI invoke the same payroll command guard and lifecycle writer. UI never supplies trusted authority or a Person identity. Permission, scope, revision, source eligibility, checklist, reason, approval policy and natural-person rules apply at this boundary even through the old route. Legacy requests missing required reviewed-version/approval witnesses fail with explicit precondition-required response and no mutation; wire acceptance must not preserve an unsafe bypass. Document this intentional compatibility change; upgrade callers before enabling the required fence. Previously accepted receipts remain historical facts and replay requires current read/execute authority.
For the payroll extension choose atomic approval consumption, not compensate-by-unconsuming after failure. Reuse governance four_eyes_check_conn/four_eyes_consume_conn inside the SAME Company owner transaction that writes the payroll effect, owner audit and command receipt. The canonical wrapper must not preconsume approvals for commands using this owner transaction. Existing other domain flows are unchanged and their separate-transaction limitation remains documented.
Governance must bind approval to Company, action, exact target, requester identity, payload digest, input/calculation/submission revision and current policy requirements; extend its owned approval context if absent. Do not reuse target-only approval after amount changes. The owner rechecks approved context and current policy under its transaction. A failure before commit rolls back consumption/effect/receipt together. A crash after commit recovers from owner receipt; an absent outer projection/audit is repaired idempotently and is never authority to execute twice. Approval rejection, revoke, changed policy or stale snapshot yields no effect.
Lock order: run head, relevant source/version guards in stable owner-kind/ID order, then approval binding/consumption; all participating writers must use compatible locks or revision CAS. Record bounded deadlock/serialization retry; same command ID and payload. Do not claim serializable isolation by itself closes a stale-policy or cross-transaction gap.

D07. Identity for group-delegated actors — decision still requires separate design evidence
Existing natural-person resolution uses users.employee_id and company-local employee_person_bindings. A group principal operating another Company is not proof of either a target-company identity or a globally unique natural person. Different UUIDs from different Company namespaces do not prove different humans.
Required behavior is fixed: resolve trusted actor identity at the identity owner, compare verified natural-person identity in an explicitly defined domain, fail closed on unknown/conflicting bindings, record identity/version at submission and recheck on decision. Names, email strings and client-supplied Person IDs are never equality evidence. Cross-company delegation must not become SUPER_ADMIN or a second user record with assumed independent humanity.
Before approving cross-company submission/decision tests, independently design whether existing Person ownership can provide verified group equivalence (with enrollment/correction/custody/revocation) or whether target-company bound acting accounts with verified same-person linkage are required. Do NOT silently add a global identity registry. Candidate01 did not settle this; current review must mark it a blocking gap for the full group execution candidate, not pretend fail-closed alone delivers group approvals.

D08. Group bundle ownership and failure model
Existing workflow_runs are Company-bound and group consolidated_read fails the aggregate on member error. Neither is a durable Group-operation owner. Required contract: stable operation ID/requester and exact frozen company/target/action/version set; separately typed Group-owned control metadata and Company-owned child intents, no business payload/salary in an unscoped coordinator; authorization-filtered readback, no leakage from counts/error/timing beyond explicitly permitted scope.
Recommended extension: control metadata owned by platform/group with explicit Group RLS/security-definer boundary and personal-data classification; Company child execution owned by payroll using existing command receipts. This is a reviewed new persistence boundary, not an extra mixed-org payroll writer and not ObjectKey::Group by implication. The exact protected storage policy, worker claim/lease, actor reauthorization mechanism and source-of-truth header/child transaction boundaries require independent design before approval; a generic reuse-workflow placeholder is insufficient.
Required observable child states: NOT_STARTED, RUNNING/UNKNOWN (only when persisted claim supports it), SUCCEEDED(receipt), BLOCKED(current policy/source/approval), FAILED_RETRYABLE, FAILED_FINAL, CANCELLED_BEFORE_EXECUTION. Header reports progress over frozen targets with partial/unknown states; never group-atomic success. Queue bounds/backoff and maximum attempts must be explicit design values before tests.
Persist intent before dispatch. A retry uses the exact same child command ID and payload; never mint a new ID to recover a timeout. Query receipt before retry; reauthorize for disclosure and new execution. Permission loss does not erase committed effect, nor permit viewing its amount. New Group members are not added to an old operation. Cancel acts only on proven-unstarted intents; running/unknown reconciles before deciding. Completed effects are never silently undone; business correction is a separate owning Action. If no eligible human successor exists, route a visible blocked assignment instead of granting privilege.
D07 and the unresolved storage/worker details here block full bundle design approval. They do not require throwing out existing Company payroll or pretending the full target has shrunk.

D09. Employee surface and UX
V10 is not backed by a monetary self-service API in candidate01. First reviewed employee surface may show only the existing authorized readiness DTO. A real self-service amount view needs a payroll-owned DTO projected by authenticated user -> own Employment mapping, authorized publication state and line/field visibility; no path employee_id from the client alone and no Manage API reuse. Publication/dispute/correction actions and historical access after departure are a separate explicit contract, not hidden TODO under a finished screen.
V01-V09 share reusable object headers and command forms but require actual permission-filtered data. Contact workspace stays independent from object inspector when it is later built. No background data transfer is presented as a human approval. Current blocked conditions appear next to primary action with reason, responsible owner and path back; required details/differences/evidence remain visible. Preserve selected scope/period/filter/focus and non-sensitive navigation across return; private monetary drafts require authorized server persistence, not raw localStorage. Changing Company rechecks and clears unauthorized props/caches.
Screens must define success, loading, empty, denied, partial, stale, failure and unknown-result behavior, keyboard/focus and recovery before UI tests are approved. This is a review criterion; this text does not replace a concrete screen state matrix.

D10. Migration and proof boundaries
Future schema expands must name tables/constraints/owners, backfill and validate all readers before new writes; legacy and new records are distinguishable. Rollback never deletes correction/input/approval/receipt history; disabling new writes does not make old readers safe. No generated migrations or product tests are written in this design-review step.
Test planning is non-executable until exact approved design SHA. Positive required native case: create supported source facts and verification through owning actions, zero import rows, exact known integer arithmetic and persisted manifest/calculation, same-date correction produces new calculation and old revision still readable. Negative blockers are a separate suite and cannot satisfy the positive case. Include same-natural-person two accounts, unknown identity, revocation, stale source inserted between preview and execute, cross-tenant negative fixture, approval/effect crash points, committed replay, membership exclusion, independent child partial failure and response loss. A test cannot accept merely any nonzero exit; assertion discovery and actual failure must be proved.
No approved design SHA, no executable test candidate; no approved test SHA, no implementation lane. The review evidence must distinguish resolved design contracts, still-blocking design decisions, and future implementation/legal/production verification.

D11. Replay ordering clarification (proposed after Round 3 counterexample)
Authenticate and resolve the Company boundary first; look up command identity only under that scope. If a matching committed owner receipt exists, validate actor/action/object identity and immutable payload digest, then current permission to view/replay that receipt; return the historical committed result with its exact versions and a separate current-state/stale/revoked indicator. Do not fail that historical lookup solely because its input revision is no longer current. Revocation cannot undo a committed effect; the receipt is not authorization for a new effect. If current authority denies disclosure, return a nondisclosing denial, not receipt contents. Only when no committed receipt exists may a NEW execution proceed through current source/state/policy/approval guards and command serialization. An absent receipt alone never proves no in-flight command can commit. Concurrent same-command attempts serialize before deciding whether to execute; the losing attempt reads the winner's committed receipt or observes a definitive rollback. This specification does not settle D08 coordinator leases or changed-actor successor commands.

D12. Required unresolved UX/approval decisions — not permission to implement placeholders
Define business submitter vs payroll decider separately from any generic execution-gate requester/approver; specify exactly which identity pairs must differ and what the user sees when an additional configured gate is required. A business approval screen cannot imply a second human gate was fulfilled. Bind both, when configured, to the same immutable business submission without allowing object-type-only approval.
Define the owning post-approval draft correction/cancellation/supersession action before calling correction end-to-end complete. D05's safe refusal is containment only, not a completed operational fallback. It must keep approved history, prevent duplicate payable outcomes, invalidate outdated projections, and preserve payment/issuance HOLDs.
Define monetary input draft ownership, save/restore/expiry, concurrent edit conflict, actor handover, scope change and data revocation. A generic promise to preserve context is not a persistence contract. Define a screen-by-screen state/error/action matrix, including employee own-read publication and correction request. These are blocking for the corresponding UI/test candidate, even if foundational payroll tests can eventually be scoped separately by a reviewed design decision.

D13. Cross-company actor persistence is a separate unresolved contract
Round 4 identified that natural-person equivalence alone does not satisfy target-Company actor foreign keys. Canonical receipts require (actor_id,org_id)->users(id,org_id); wage writes require (created_by,org_id); workflow runs require (initiated_by,org_id). Group delegation currently preserves the original account ID while selecting another Company. Define the trusted execution/attribution model and compatibility of these owning writes before claiming positive Group operations. Do not create an arbitrary target-company user, drop actor attribution, relax composite FKs or elevate a service identity to bypass this. Same-human proof and target-company actor persistence are distinct gates; both require positive end-to-end action/receipt readback and independent review.
