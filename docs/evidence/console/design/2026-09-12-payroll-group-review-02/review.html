이번에 확인한 핵심

  • 정상 업무가 끝나야 합니다. 기존 P04는 계산 반영 또는 차단을 모두 통과로 허용했습니다. 새 계획 O01은 native 원천만으로 실제 계산 성공과 정확한 저장 결과를 필수로 요구합니다. 차단 사례는 별개입니다.
  • 정정은 원래 효력일과 이력을 보존해야 합니다. 기존 급여 테이블의 동일 날짜 유일성과 수정 금지 때문에 잘못 입력한 급여를 기존 API만으로 바로잡을 수 없습니다. append-only 정정 이력과 모든 reader의 동일 해석을 제안했습니다.
  • 전사 권한, 자연인 동일성, 실행자 저장은 서로 다른 문제입니다. 법인 B 소속 담당자가 A의 업무를 처리할 때 필요한 권한·동일인 증명·A의 영수증에 기록될 실행자 귀속을 각각 설계해야 합니다.
  • 결재는 정확한 업무 내용에 묶여야 합니다. 급여 결정과 별도의 실행허가를 구분하고, 원천/계산/제출 버전을 결속해야 합니다. 승인 소비와 급여 효과·영수증을 같은 owner transaction에 넣는 방향을 제안했습니다.
  • 실패·부재·중단 뒤에도 이어져야 합니다. 전사 묶음의 부분 완료, 담당 교체, 승인 후 오류 정정, 입력 초안 복원과 직원 화면의 정상 경로는 아직 명시적 설계가 필요합니다.

검증 및 제한

소스 19개를 기준 Git blob과 대조하고 원본 후보 payload의 해시를 보존합니다. 현재 PRODUCT/ROADMAP/DELIVERY는 바꾸지 않았습니다. 실제 제품·성능·법률·production 검증을 통과했다고 주장하지 않습니다.

문서 gate는 원본 후보의 Markdown 사본 2개가 문서 manifest에 없고 DELIVERY 링크 2개가 누락되어 실패했습니다. 최초 sandbox 실행의 Git custody 실패는 권한 있는 재실행으로 구분했습니다. 전체 diff 검사에는 이전 고정 CSV의 CRLF도 포함되어 실패했습니다. 새 CSV는 LF로 정리했지만 원본 증거는 덮어쓰지 않았습니다. 이 패킷은 merge 가능한 제품/권한 후보가 아닙니다. 문서 gate 출력 · 고정 후보 전체 diff 출력

이어질 설계 작업 순서

  1. B01·B09: 전사 담당자의 신뢰할 식별·실행·저장 귀속을 함께 설계합니다. 권한만으로 가짜 법인 계정을 만들지 않습니다.
  2. B02·B05: 급여 결정/실행허가 역할과 승인 후 정정까지 닫습니다.
  3. B03·B04: Group 제어 기록과 Company 실행 경계, 담당 교체·재시도·부분 실패를 고정합니다.
  4. B06·B07·B08: 입력 초안 수명주기, 화면별 상태·복구, 직원 정상 경로를 실제 계약으로 작성합니다.
  5. 수정 설계의 정확한 SHA에 독립 합의를 얻은 뒤 승인 요청을 합니다. 승인된 설계로 테스트 후보를 작성·독립 검토하고 test SHA 승인 후 구현 lane을 준비합니다.

현재 승인할 준비가 된 설계로 제시하지 않습니다. 현행 DELIVERY의 “Four independent design-review rounds, consensus, and a revision-bound explicit approval (design SHA)” 및 “Tests written first against that design SHA” 순서를 유지합니다. 별도 법률·지급·배포·Intelligence HOLD도 유지됩니다.
