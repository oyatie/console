BW31 — Browser Account entry wire refinement
Status: proposed, not approved. Inherits design7b6e4c6836750a23fc5fc38bdd37ac391e970215 AS1/GN16. This packet specifies boundaries; it implements no endpoint, cryptography, migration, Cedar permit or frontend. Source and test approval remain separate.

1. Scope and explicit changes
First acceptance path: public terms -> registration/start -> actual WebAuthn registration -> registration/finish -> cookie-authenticated accounts/me -> successful empty contexts. An Account needs no Company, Employment, Person, title, policy-role label or CompanyActor. Zero contexts means an authorized successful discovery result, never an unavailable-policy fallback. Account-only entry does not implement applicant cases or former-worker certificate delivery.
Material refinements: a shared Account terms head and ceremony binding fields; exact browser cookies and signed request-proof protocol; per-item accept_items in registration/finish; AccountActionRef replacing ambiguous Company ActionRef in Account self-projection. Existing Company and Group action refs are unchanged. Native bearer transport and populated navigation retain their separate acceptance work; this packet's browser routes refuse Authorization headers rather than guess transport. Future native admission cannot weaken the same Account/session checks.

2. Immutable terms and shared current authority
Release contains allowlisted immutable manifest/content bytes. Public GET /api/v2/auth/terms returns TermsCurrent with terms_version (lowercase SHA256 hex of exact manifest bytes), terms_revision (positive decimal string), and manifest_url. GET /api/v2/auth/terms/manifests/{sha256} returns those exact application/json UTF-8 bytes. GET /api/v2/auth/terms/content/{sha256} returns exact text/plain; charset=utf-8 bytes with nosniff. Paths accept only64 lowercase hex digits and resolve registered artifacts, never caller-selected filesystem paths/network URLs. Unknown digest404; artifact unavailable503; no redirect. Public document responses may cache immutable registered bytes; /terms is no-store and uses authoritative head.
Manifest has1..8 required items with distinct registered terms_kind, title, locale and content_sha256. It embeds no self digest; publication resolves/verifies every content digest. No optional consent is silently included. Each rendered item is separately acknowledged; finish carries accept_terms_version and accept_items containing exactly every required kind with accepted:true. Missing/duplicate/unknown/false entries422 before activation. This records explicit item acknowledgments, not proof of reading, comprehension or legal validity. Test manifest/content are conspicuously TEST_ONLY. Production publication requires separate qualified content/release authority and refuses TEST_ONLY. No Company audit is used to infer Account consent.
One narrow native Account-owned account_terms_head row is shared authority: singleton id1, manifest_sha256 bytea32, revision positive bigint, release_receipt_ref and updated_at. Replica configuration says which immutable artifacts it can serve; it cannot choose current authority. Absent/unavailable head or unsupported current artifact ->503 authority_unavailable; never stale local acceptance. A version/ref mismatch is409 terms_changed only after valid public authority is available. All accepted items persist exact per-item digest/version/event/time in approved account_terms_acceptances/account_security_events in the activation transaction.
Publication is an operator release action outside public HTTP: validate artifact and capacity, CAS expected revision, append a durable release receipt and update head in one transaction. Head revision never decreases. Publication locks only head, never Accounts. Registration acquires account_security first, head FOR SHARE second, then AS1's remaining family/key/ceremony locks. Hold head through activation commit; FOR KEY SHARE is insufficient for non-key digest UPDATE. Start also binds both digest and head revision to ceremony. A->B->A cannot revive a ceremony because its head revision differs. Rollback keeps current head/revocations and compatible readers; incompatible binaries hold enrollment closed. No request-time remote artifact fetch or new registry service.

3. Wire, admission and registration
All app-owned request/response wrappers are closed JSON schemas in wire.schema.json. Native WebAuthn subobjects use the existing pinned webauthn-rs serde types and cryptographic validation; structural examples are not valid signed credentials. public_key_options contains the library's full {publicKey:...} wrapper, not its inner object. UUID canonical lowercase; positive versions decimal strings; UTC RFC3339 timestamps. Limits are bytes on UTF-8 encoded requests as well as schema cardinality; oversized request413 before buffering unbounded data.
Public read routes need no identity. Browser POST routes require Content-Type application/json, exact Origin equal to configured public HTTPS origin, and Sec-Fetch-Site=same-origin when provided. Origin missing/null/multiple/mismatched ->403 request_origin_denied before any state mutation. No Referer fallback. Host/forwarded headers never select allowed origin; trust only configured proxy boundary. No credentialed CORS, wildcard CORS, JSONP or auth redirects. OPTIONS from another origin grants nothing. Reject any Authorization header, duplicate recognized cookie names, mixed browser/native transport inputs or unknown body fields. Empty/malformed credential cookies are invalid credentials, not permission to switch parser.
POST registration/start {terms_version} ->200 RegistrationStart. Browser with an authenticated Account must use existing-key enrollment; this endpoint returns409 already_authenticated and creates nothing. For a new attempt server generates immutable Account UUID, PENDING_ENROLLMENT guard and a five-minute single-use ceremony, binding Account UUID, terms digest+head revision, challenge, RP-ID, origin and SHA256 of32 random nonce bytes. Browser receives nonce only as __Host-console_account_enrollment cookie. No session or business token is issued. WebAuthn user handle is the16 Account UUID bytes, base64url; server selects it. No email/Company/Account selector or account merge.
POST registration/finish {ceremony_id,credential,accept_terms_version,accept_items} ->201 SessionEstablished. Require unexpired nonce cookie and exact ceremony binding, current terms head, actual verified WebAuthn registration with user verification, and server-matched user handle/RP/origin. Under locks recheck all facts, add key and exact item evidence, activate Account, create ACCOUNT_V1 family and consume ceremony atomically. Failure cannot partially persist credentials, accepted terms, ACTIVE or sessions. No pending Account access token exists.
Expiry/wrong nonce/unknown/used ceremony ->401 enrollment_invalid; invalid typed item set422; valid attempt whose terms changed409 terms_changed. No hidden Account identity in these errors. Failed cryptographic/binding requests cannot clear an unrelated live enrollment cookie. Successful finish clears its nonce cookie. Start with a currently valid enrollment nonce invalidates that previous pending ceremony before issuing a replacement; it cannot delete a completed Account. Independent first requests without a prior nonce may create separate attempts, so UI must not silently submit two registrations. A subsequent start is a distinct attempt, not identity deduplication; at most one ACTIVE transition/session creation per attempt. Pending/expired cleanup must preserve completed Account/key/evidence; quota enforcement cannot delete usable Accounts.
Lost finish response: never store plaintext refresh credentials to replay201. Client first tries cookie-authenticated /me; if cookie arrived it continues. Otherwise use a fresh discoverable passkey login with the created key. Repeated finish never creates another Account/key/acceptance/family and returns401 enrollment_invalid with no credentials. Do not automatically start a new registration after network error. Multiple independently completed attempts may create distinct Accounts; no claim that this deduplicates a natural person.

Discoverable login wire: POST /api/v2/auth/passkey/login/start {} ->200 LoginStart with the same full public_key_options wrapper and a separate five-minute __Host-console_account_login nonce cookie. Existing authentication ceremony_kind is retained; account_browser_flow=ACCOUNT_LOGIN selects v2 binding. Store only nonce hash, configured origin and challenge, with no client Account/Company selector. POST /api/v2/auth/passkey/login/finish {ceremony_id,assertion} ->200 SessionEstablished only after current verified primary WebAuthn assertion, matching login nonce/origin/RP/challenge, Account ACTIVE and AS1 guard/counter/family checks. Clear login nonce on success. Wrong/expired/consumed attempt401 authentication_invalid; no credential issued. Login can intentionally replace browser cookies only through fresh primary proof, never through current-cookie identity or an employer invitation; it does not merge Accounts. No automatic original-key/new-Account recreation after failed registration response.

4. Session cookies, parsers and errors
Cookie names are __Host-console_account_session (ACCOUNT_V1 access JWT, SameSite=Lax), __Host-console_account_refresh (opaque refresh, SameSite=Strict), __Host-console_account_enrollment (random nonce, SameSite=Strict), and __Host-console_account_login (separate login nonce, SameSite=Strict). All Secure; HttpOnly; Path=/; no Domain. Cookie input is parsed exactly once; duplicate recognized names reject400 ambiguous_credentials, not first/last wins. Legacy console_refresh never authenticates v2. Clearing uses empty value; Max-Age=0 and same attributes/path. No session/refresh token appears in JSON, SSR HTML/hydration, URL, logs, browser storage or messages. Set-Cookie and Cookie/Authorization headers are redacted before logging/tracing/export.
Session cookie Max-Age=floor(exp-now), access exp<=now+15minutes and existing stricter configured/absolute lifetime. Refresh cookie age never exceeds stored token/family expiry. Enrollment Max-Age300, server expiry authoritative. SessionEstablished is {account:AccountProjection}; AccountProjection exactly matches GET /api/v2/accounts/me (200). Registration assurance is PASSKEY_PRIMARY after required verified ceremony; assurance is an owner result, never a requested boolean. Expired/invalid Account access ->401 on /me; live ACTIVE/generation/family/protocol/revocation/absolute limits required every time. No refresh fallback on business, me,contexts or SSR protected reads. Current security suspension denies even unexpired JWTs.
Every private/auth proof/POST response is Cache-Control:no-store, Pragma:no-cache and Vary:Cookie,Origin as applicable. Auth errors use {error:{code,message}} with closed fields; no IDs, raw inputs, secret fragments or authority internals. codes/statuses enumerated in routes.json. Unsupported storage/authority returns503, not empty success or old parser fallback. Error receipt logging uses bounded code/trace IDs only. Clear expired cookies only for exact validated browser flow; invalid/foreign-origin requests must not mutate identity/session state.

5. Signed request proof (CSRF)
Choose signed request proofs over a stored synchronizer-token set. Existing PEM-backed ES256 signing/verifying material is reused; no JWKS or already-implemented rotation mechanism is claimed. Compatible key rollover/drain must be verified before activation with exact issuer, aud=console.account.csrf.v1 and token_kind=account_csrf_v1. Claims sub,sid,security_generation,iat,nbf,exp bind to independently cookie-authenticated current Account and family. Proof TTL<=5minutes and absolute family lifetime; no assurance upgrade or new session. Reject future iat/nbf and expired proof using server time; no unbounded library leeway. Proof is never accepted by ACCOUNT_V1 or legacy authentication parsers and an access JWT is never a request proof. CSRF cannot prevent same-origin script compromise.
GET /api/v2/auth/csrf requires X-Console-CSRF: fetch, same-origin Sec-Fetch-Site if supplied, and no cross-origin CORS. If Origin is supplied it must match; missing Origin on a same-origin GET is allowed because the non-simple header and no CORS prevent cross-origin browser reading. Access cookie is preferred if fully valid. If absent or expired only, refresh credential may identify a current session through the same auth-owner validation used for refresh, without consumption,rotation,extension or token issuance. Invalid signature/kind/generation/state never triggers parser downgrade. If two successfully validated supplied credentials name different Account/family, reject400 ambiguous_credentials. Refresh validation includes Account ACTIVE, exact generation/protocol/family, unrevoked family, unused/unexpired token and absolute lifetime. No speculative Account/family writes or CompanyActor creation on this GET. Response200 {csrf_proof,expires_at}; no account/access/refresh projection. Missing/invalid credentials401; signing or live authority unavailable503. No credential-bearing redirects.
Client keeps proof only in memory. Every authenticated browser mutation requires X-Console-CSRF equal to a validated proof and exact configured Origin; absence/mismatch403 csrf_invalid. Compare proof sub/sid/generation exactly with that mutation's independently verified credential context. Registration start/finish and discoverable login are pre-auth ceremonies protected by exact Origin and their own nonce/challenge binding, not by an invented pre-existing session proof. No selected Company/header/GUC grants identity authority.
Refresh uses refresh cookie as its credential and exact bound proof; no body token. Same-family rotation preserves primary age/assurance and CSRF binding until proof expires or security/family changes. Current proof can be reacquired after expiry/reload without extending authentication. Per-tab proofs do not revoke each other. Actual simultaneous refresh-token use retains approved reuse detection; no unreviewed grace/replay-success exception. Cross-tab refresh coordination and fallback must pass its separate compatibility tests before automatic background refresh is enabled.
POST /api/v2/auth/logout {} requires session-bound proof and current live session from valid access or refresh-only flow; revoke exact own family and return200 {outcome:COMMITTED}, clear both credential cookies. Retry with already revoked family returns401 without further state mutation or Set-Cookie; do not revive or inspect other sessions. Invalid-cookie recovery uses fresh sign-in which replaces browser cookies. Client must serialize auth-cookie-changing operations; late responses/concurrent logout/login require their explicit compatibility proof and cannot be declared safe from this prose alone. Security-revoked/expired sessions cannot recover business access by logout. Browser can return to public sign-in; server invalidity remains authoritative. Local cookie removal is not proof server revocation succeeded.
External object-link navigation: Lax access enables authorized SSR while access is valid. If expired, Strict refresh may be absent on the initial external GET. Serve a neutral no-data bootstrap shell, then same-origin proof fetch + refresh + freshly authorized target retry. Do not immediately force login, leak target labels, put credentials in return URLs or auto-execute any action. Return destination is a same-origin relative read target validated against mounted routes; choosing it grants no access. JS-unavailable/authority-unavailable path offers explicit retry/sign-in while keeping protected data omitted. This is a required compatibility acceptance, not claimed implementation.

6. Account self-actions and context projection
AccountActionRef is {action_key,registration_revision}; each pair binds an immutable release-owned Account action registration. It is not Company ActionRef or GroupActionRef and never contains a sentinel org. The initial registration manifest admits account.session.logout revision1 mapped to identity/auth's existing own-session logout use case. Other actions appear only after their actual owner and current checks are enrolled; no reflection over route strings. Displaying the reference grants nothing and no role/title preset is needed.
GET /api/v2/accounts/me/contexts?page_size=1..100&cursor=opaque uses GN16. Default25; reject duplicate/unknown query params or malformed page_size422. Fixed first-wire query is ALL including authorized historical contexts; no caller-supplied Account/group enumeration. Response200 {contexts:[...],next_cursor?:opaque}; empty list omits next_cursor, never null. No total/hidden count. COMPANY items use context_ref:{org_id}; GROUP use {group_id}; label is a currently permitted string. entry_ref:{kind:WORKSPACE} is the existing safe repair destination semantics for the enclosing disclosed context, not an arbitrary URL and not an action grant. Any request for target data/action re-resolves current scope and Cedar.
No CompanyActor is created on GET. GN16 completeness, candidate freshness including denied->allowed, temporal changes, limits32Groups/256Companies, current policy and cursor5minute lifetime remain mandatory. Context hints alone never authorize a label. Valid Account with no contexts receives an actual empty result and Account settings; unavailable authority503 navigation_unavailable, never silently empty. Invalid current auth401; stale/expired/foreign cursor409 stale_cursor with no hidden ownership distinction. A known undiscoverable context target404. Populated context owner fixtures remain a separate acceptance family; first empty-context test does not fabricate Companies/assignments.

7. Operational bounds and acceptance limits
Registration start body<=4KiB; finish<=64KiB; WebAuthn parsing depth<=32; Account wrapper/terms manifest<=16KiB; up to8terms items each<=64KiB; proof header<=4KiB; cookie header<=16KiB; contexts response<=128KiB and100items; label<=256UTF-8 bytes; action list<=16. Unsupported/unserviceable bound ->explicit413/422/503, never truncation. Initial deployment requires measured per-route concurrency/pending-attempt cap/rate limits and cleanup recovery evidence before activation; this packet does not manufacture50k/1M capacity claims. It does fix bounded payload work and avoids per-request remote content fetch or per-Company signup scans.
Success,origin/nonce swap,replay,lost-response recovery,stale/ABAterms,artifact outage,publication-vs-finish race,cookie ambiguity,CSRF parser confusion/family mismatch/expiry,zero-context-vs-unavailable and noCompanyActor are required executable candidates after approval. Fixture/hash/schema verification in verify.py is document consistency only. Full Account tests, implementation admission, production exposure and legal content authority remain HOLD.
