BW31 — Browser Account entry wire refinement
Status: proposed, not approved. Inherits design7b6e4c6836750a23fc5fc38bdd37ac391e970215 AS1/GN16. This packet specifies boundaries; it implements no endpoint, cryptography, migration, Cedar permit or frontend. Source and test approval remain separate.

1. Scope and explicit changes
First acceptance path: public terms -> registration/start -> actual WebAuthn registration -> registration/finish -> cookie-authenticated accounts/me -> successful empty contexts. An Account needs no Company, Employment, Person, title, policy-role label or CompanyActor. Zero contexts means an authorized successful discovery result, never an unavailable-policy fallback. Account-only entry does not implement applicant cases or former-worker certificate delivery.
Material refinements: a shared Account terms head and ceremony binding fields; exact browser cookies and signed request-proof protocol; per-item accept_items in registration/finish; AccountActionRef replacing ambiguous Company ActionRef in Account self-projection. Existing Company and Group action refs are unchanged. Native bearer transport and populated navigation retain their separate acceptance work; this packet's browser routes refuse Authorization headers rather than guess transport. Future native admission cannot weaken the same Account/session checks.

2. Immutable terms and shared current authority
Release contains allowlisted immutable manifest/content bytes. Public GET /api/v2/auth/terms returns TermsCurrent with terms_version (lowercase SHA256 hex of exact manifest bytes), terms_revision (positive decimal string), and manifest_url. GET /api/v2/auth/terms/manifests/{sha256} returns those exact application/json UTF-8 bytes. GET /api/v2/auth/terms/content/{sha256} returns exact text/plain; charset=utf-8 bytes with nosniff. Paths accept only64 lowercase hex digits and resolve registered artifacts, never caller-selected filesystem paths/network URLs. Unknown digest404; artifact unavailable503; no redirect. Public document responses may cache immutable registered bytes; /terms is no-store and uses authoritative head.
Manifest has1..8 required items with distinct registered terms_kind, title, locale and content_sha256. It embeds no self digest; publication resolves/verifies every content digest. No optional consent is silently included. Each rendered item is separately acknowledged; finish carries accept_terms_version and accept_items containing exactly every required kind with accepted:true. Missing/duplicate/unknown/false entries422 before activation. This records explicit item acknowledgments, not proof of reading, comprehension or legal validity. Test manifest/content are conspicuously TEST_ONLY. Production publication requires separate qualified content/release authority and refuses TEST_ONLY. No Company audit is used to infer Account consent.
One narrow native Account-owned account_terms_head row is shared authority: singleton id1, manifest_sha256 bytea32, revision positive bigint, release_receipt_ref and updated_at. Replica configuration says which immutable artifacts it can serve; it cannot choose current authority. Absent/unavailable head or unsupported current artifact ->503 authority_unavailable; never stale local acceptance. A version/ref mismatch is409 terms_changed only after valid public authority is available. All accepted items persist exact per-item digest/version/event/time plus the SAME release receipt/revision/manifest tuple in account_terms_acceptances in the activation transaction. storage-refinement.json explicitly adds nullable legacy-preserving columns and a new closed ControlEvidence ACCOUNT_TERMS_RELEASE variant for TERMS_ACCEPTED security events. Head, acceptance and event reference exact composite tuple equality, never independently existing UUID/digest values. Legacy evidence is not backfilled with a fictional release receipt; first-acceptance PK/history remains immutable.
Publication is an operator release action outside public HTTP: validate artifact and capacity, CAS expected revision, append a durable release receipt and update head in one transaction. Head revision is exactly predecessor+1 (genesis1), never decreases; bigint overflow fails closed. OperatorApprovalRef resolves exact closed TermsPublicationApproval bytes in the trusted deployment custody bundle; app JSON or a hash is not approval. Publisher verifies authenticated operator custody and separately qualified content-authority references before mutation; production authority remains HOLD. See storage-refinement.json for ownership, tuple constraints and retained bytes. Publication locks only head, never Accounts. Registration acquires account_security first, head FOR SHARE second, then AS1's remaining family/key/ceremony locks. Hold head through activation commit; FOR KEY SHARE is insufficient for non-key digest UPDATE. Start also binds both digest and head revision to ceremony. A->B->A cannot revive a ceremony because its head revision differs. Rollback keeps current head/revocations and compatible readers; incompatible binaries hold enrollment closed. No request-time remote artifact fetch or new registry service.

3. Wire, admission and registration
All app-owned request/response wrappers are closed JSON schemas in wire.schema.json. Native WebAuthn subobjects use the existing pinned webauthn-rs serde types and cryptographic validation; structural examples are not valid signed credentials. public_key_options retains the library's full creation/request wrapper, not its inner object. Request options allow the pinned optional mediation:"conditional" field; creation does not. UUID canonical lowercase and non-nil; positive versions decimal strings; UTC RFC3339 timestamps. Limits are bytes on UTF-8 encoded requests as well as schema cardinality; oversized request413 before buffering unbounded data.
Public read routes need no identity. Browser POST routes require Content-Type application/json, exact Origin equal to configured public HTTPS origin, and Sec-Fetch-Site=same-origin when provided. Origin missing/null/multiple/mismatched ->403 request_origin_denied before any state mutation. No Referer fallback. Host/forwarded headers never select allowed origin; trust only configured proxy boundary. No credentialed CORS, wildcard CORS, JSONP or auth redirects. OPTIONS from another origin grants nothing. Reject any Authorization header, duplicate recognized cookie names, mixed browser/native transport inputs or unknown body fields. Empty/malformed credential cookies are invalid credentials, not permission to switch parser.
POST registration/start {terms_version} ->200 RegistrationStart. Browser with an authenticated Account must use existing-key enrollment; this endpoint returns409 already_authenticated and creates nothing. For a new attempt server generates immutable Account UUID, PENDING_ENROLLMENT guard and a five-minute single-use ceremony, binding Account UUID, terms digest+head revision, challenge, RP-ID, origin and SHA256 of32 random nonce bytes. Browser receives nonce only as __Host-console_account_enrollment cookie. No session or business token is issued. WebAuthn user handle is the16 Account UUID bytes, base64url; server selects it. No email/Company/Account selector or account merge.
Resident credential request: extend platform/auth existing start_passkey_registration for ACCOUNT_REGISTRATION only. Deliberately adjust the typed creation authenticator_selection.resident_key to Required and require_resident_key to true; require existing selection and UV Required or refuse internal authority503. Preserve every other field, original opaque PasskeyRegistration state and existing finish_passkey_registration verifier. Persist adjusted challenge with state. This is an explicit bounded exception to opaque challenge forwarding, not a new crypto implementation. Pinned core0.5.5 ignores state.require_resident_key on finish; direct core builder would add no signed residency proof and would require unnecessary raw Credential conversion. Neither credProps.rk nor this setting proves resident storage cryptographically. Guarantee is a discoverable request to a conforming supported browser/authenticator; compatibility requires actual resident registration followed by fresh no-allowCredentials discovery. A dependency change must re-review this exception. Nonresident-only devices fail browser creation without activation; never silently downgrade. SoftPasskey with injected allow-list is not this compatibility proof.
POST registration/finish {ceremony_id,credential,accept_terms_version,accept_items} ->201 SessionEstablished. Require unexpired nonce cookie and exact ceremony binding, current terms head, actual verified WebAuthn registration with user verification, and server-bound creation Account user handle plus verified RP/origin. Registration Account binding comes from stored ceremony/state. Discoverable assertion userHandle is unsigned, untrusted lookup/correlation input: require its exact16 bytes to equal the Account owner of the exact credential whose stored public key verifies the assertion, and recheck that binding under the Account guard. The signature covers authenticator data plus client-data hash, not userHandle; neither a supplied handle nor credential ID alone authenticates an Account. Under locks recheck all facts, add key and exact item evidence, activate Account, create ACCOUNT_V1 family and consume ceremony atomically. Failure cannot partially persist credentials, accepted terms, ACTIVE or sessions. No pending Account access token exists.
Expiry/wrong nonce/unknown/used ceremony ->401 enrollment_invalid; invalid typed item set422; valid attempt whose terms changed409 terms_changed. No hidden Account identity in these errors. Failed cryptographic/binding requests cannot clear an unrelated live enrollment cookie. Successful finish clears its nonce cookie. Start with a currently valid enrollment nonce invalidates that previous pending ceremony before issuing a replacement; it cannot delete a completed Account. Independent first requests without a prior nonce may create separate attempts, so UI must not silently submit two registrations. A subsequent start is a distinct attempt, not identity deduplication; at most one ACTIVE transition/session creation per attempt. Pending/expired cleanup must preserve completed Account/key/evidence; quota enforcement cannot delete usable Accounts.
Lost finish response: never store plaintext refresh credentials to replay201. Client keeps expected Account UUID in current attempt memory, decoded from the server creation options user.id (exact16 bytes); never guess it from another session. It first tries cookie-authenticated /me and continues only on exact Account equality. Otherwise use a fresh discoverable passkey login with the created key and compare the same expected UUID. Other-Account success requires an explicit identity choice, never attribution to this enrollment. After reload losing the expected UUID, show ordinary sign-in, not a claim of recovering a particular attempt. Distinguish transport retry from consumed-ceremony replay: while the original ceremony is unexpired, valid and unconsumed, resubmitting the same in-memory credential and acknowledgments may commit exactly once and return201. Concurrent retries serialize and only one can commit; consumed attempts return401 enrollment_invalid without reminting credentials or effects. Before-commit request loss can therefore resume the same attempt. Keep the credential response only in current-attempt memory, never browser storage/logs. After expiry, terms change, missing original nonce or lost attempt state prevents retry, offer an explicit new attempt with current terms acknowledgment and explain that a browser-created credential may never have been enrolled; no automatic restart after ambiguous failure. Do not automatically start a new registration after network error. Multiple independently completed attempts may create distinct Accounts; no claim that this deduplicates a natural person.

Discoverable login wire: POST /api/v2/auth/passkey/login/start {} ->200 LoginStart with the same full public_key_options wrapper and a separate five-minute __Host-console_account_login nonce cookie. Existing authentication ceremony_kind is retained; account_browser_flow=ACCOUNT_LOGIN selects v2 binding. Store only nonce hash, configured origin and challenge, with no client Account/Company selector. POST /api/v2/auth/passkey/login/finish {ceremony_id,assertion} ->200 SessionEstablished only after current verified primary WebAuthn assertion, matching login nonce/origin/RP/challenge, Account ACTIVE and AS1 guard/counter/family checks. Eligible historical consent must be a complete owner-verified required set for the exact manifest/version originally accepted (all item digests/times and same-Account TERMS_ACCEPTED evidence reconstructable); current head advancement alone does not erase that consent or force reacceptance. Unknown/missing evidence ->403 terms_acceptance_required only after valid primary proof, no new session/key/counter/ceremony-consumption mutation, and no Account recreation. Existing-account reacceptance is a separate HOLD; UI preserves Account and states that enrollment cannot repair it. Storage/consent resolver unavailable503, never eligibility by omission. Login reads immutable evidence under Account guard, not current terms head; no Company audit or client assertion substitutes. Clear login nonce on success. Wrong/expired/consumed attempt401 authentication_invalid; no credential issued. Login can intentionally replace browser cookies only through fresh primary proof, never through current-cookie identity or an employer invitation; it does not merge Accounts. No automatic original-key/new-Account recreation after failed registration response.

4. Session cookies, parsers and errors
Cookie names are __Host-console_account_session (ACCOUNT_V1 access JWT, SameSite=Lax), __Host-console_account_refresh (opaque refresh, SameSite=Strict), __Host-console_account_enrollment (random nonce, SameSite=Strict), and __Host-console_account_login (separate login nonce, SameSite=Strict). All Secure; HttpOnly; Path=/; no Domain. Cookie input is parsed exactly once; duplicate recognized names reject400 ambiguous_credentials, not first/last wins. Legacy console_refresh never authenticates v2. Clearing uses empty value; Max-Age=0 and same attributes/path. No session/refresh token appears in JSON, SSR HTML/hydration, URL, logs, browser storage or messages. Set-Cookie, Cookie, Authorization and X-Console-CSRF headers (including fetch marker) are suppressed before logging/tracing/export. csrf_proof response field and enrollment/login nonce representations are suppressed from body/header capture as well. Auth route request/response bodies and dependency auth debug/trace values use a no-capture boundary; only bounded allowlisted error/trace metadata leaves it. Cache headers do not establish observability redaction.
Session cookie Max-Age=floor(exp-now), access exp<=now+15minutes and existing stricter configured/absolute lifetime. Refresh cookie age never exceeds stored token/family expiry. Enrollment Max-Age300, server expiry authoritative. SessionEstablished is {account:AccountProjection}; AccountProjection exactly matches GET /api/v2/accounts/me (200). Registration assurance is PASSKEY_PRIMARY after required verified ceremony; assurance is an owner result, never a requested boolean. Expired/invalid Account access ->401 on /me; live ACTIVE/generation/family/protocol/revocation/absolute limits required every time. No refresh fallback on business, me,contexts or SSR protected reads. Current security suspension denies even unexpired JWTs.
Every private/auth proof/POST response is Cache-Control:no-store, Pragma:no-cache and Vary:Cookie,Origin as applicable. Auth errors use {error:{code,message}} with closed fields; no IDs, raw inputs, secret fragments or authority internals. codes/statuses enumerated in routes.json. Unsupported storage/authority returns503, not empty success or old parser fallback. Error receipt logging uses bounded code/trace IDs only. Clear expired cookies only for exact validated browser flow; invalid/foreign-origin requests must not mutate identity/session state.

5. Signed request proof (CSRF)
Choose signed request proofs over a stored synchronizer-token set. Existing PEM-backed ES256 signing/verifying material is reused; no JWKS or already-implemented rotation mechanism is claimed. All serving replicas must share one exact configured issuer and public-key fingerprint; readiness refuses mismatched key identity. Rolling key changes are prohibited in this single-key slice. Planned replacement requires maintenance stop/drain of all auth traffic and in-flight requests, revoke existing Account families under AS1 locks, replace all sign/verify keys together, discard old in-memory proofs, verify homogeneous identity before restart and require fresh primary sign-in. Rollback also revokes families; never restore pre-revocation DB/key state or reactivate retired keys. Emergency compromise uses the same closed boundary and separate authorized operator response. Local compatibility tests must prove wrong-key refusal, mixed-key readiness failure, revocation and post-restart fresh login; zero-downtime rollover is not claimed. Verify exact issuer, aud=console.account.csrf.v1 and token_kind=account_csrf_v1. Claims sub,sid,security_generation,iat,nbf,exp bind to independently cookie-authenticated current Account and family. Proof TTL<=5minutes and absolute family lifetime; no assurance upgrade or new session. Reject future iat/nbf and expired proof using server time; no unbounded library leeway. Proof is never accepted by ACCOUNT_V1 or legacy authentication parsers and an access JWT is never a request proof. CSRF cannot prevent same-origin script compromise.
GET /api/v2/auth/csrf requires X-Console-CSRF: fetch, same-origin Sec-Fetch-Site if supplied, and no cross-origin CORS. If Origin is supplied it must match; missing Origin on a same-origin GET is allowed because the non-simple header and no CORS prevent cross-origin browser reading. Access cookie is preferred if fully valid. If absent or expired only, refresh credential may identify a current session through the same auth-owner validation used for refresh, without consumption,rotation,extension or token issuance. Invalid signature/kind/generation/state never triggers parser downgrade. If two successfully validated supplied credentials name different Account/family, reject400 ambiguous_credentials. Refresh validation includes Account ACTIVE, exact generation/protocol/family, unrevoked family, unused/unexpired token and absolute lifetime. No speculative Account/family writes or CompanyActor creation on this GET. Response200 {csrf_proof,expires_at}; no account/access/refresh projection. Missing/invalid credentials401; signing or live authority unavailable503. No credential-bearing redirects.
Client keeps proof only in memory. Every authenticated browser mutation requires X-Console-CSRF equal to a validated proof and exact configured Origin; absence/mismatch403 csrf_invalid. Compare proof sub/sid/generation exactly with that mutation's independently verified credential context. Registration start/finish and discoverable login are pre-auth ceremonies protected by exact Origin and their own nonce/challenge binding, not by an invented pre-existing session proof. No selected Company/header/GUC grants identity authority.
Refresh uses refresh cookie as its credential and exact bound proof; no body token. Same-family rotation preserves primary age/assurance and CSRF binding until proof expires or security/family changes. Current proof can be reacquired after expiry/reload without extending authentication. Per-tab proofs do not revoke each other. Actual simultaneous refresh-token use retains approved reuse detection; no unreviewed grace/replay-success exception. Cross-tab refresh coordination and fallback must pass its separate compatibility tests before automatic background refresh is enabled.
POST /api/v2/auth/logout {} requires session-bound proof and current live session from valid access or refresh-only flow; revoke exact own family and return200 {outcome:COMMITTED}, clear both credential cookies. Retry with already revoked family returns401 without further state mutation or Set-Cookie; do not revive or inspect other sessions. Invalid-cookie recovery uses fresh sign-in which replaces browser cookies. Client must serialize auth-cookie-changing operations; late responses/concurrent logout/login require their explicit compatibility proof and cannot be declared safe from this prose alone. Security-revoked/expired sessions cannot recover business access by logout. Browser can return to public sign-in; server invalidity remains authoritative. Local cookie removal is not proof server revocation succeeded.
External object-link navigation: Lax access enables authorized SSR while access is valid. If expired, Strict refresh may be absent on the initial external GET. Serve a neutral no-data bootstrap shell, then same-origin proof fetch + refresh + freshly authorized target retry. Do not immediately force login, leak target labels, put credentials in return URLs or auto-execute any action. Return destination is a same-origin relative read target validated against mounted routes; choosing it grants no access. JS-unavailable/authority-unavailable path offers explicit retry/sign-in while keeping protected data omitted. This is a required compatibility acceptance, not claimed implementation.

6. Account self-actions and context projection
AccountActionRef is {action_key,registration_revision}; each pair binds an immutable release-owned Account action registration. It is not Company ActionRef or GroupActionRef and never contains a sentinel org. The initial registration manifest admits account.session.logout revision1 mapped to identity/auth's existing own-session logout use case. Other actions appear only after their actual owner and current checks are enrolled; no reflection over route strings. Displaying the reference grants nothing and no role/title preset is needed.
GET /api/v2/accounts/me/contexts?page_size=1..100&cursor=opaque uses GN16. Default25; reject duplicate/unknown query params or malformed page_size422. Fixed first-wire query is ALL including authorized historical contexts; no caller-supplied Account/group enumeration. Response200 {contexts:[...],next_cursor?:opaque}; empty list omits next_cursor, never null. No total/hidden count. COMPANY items use context_ref:{org_id}; GROUP use {group_id}; label is optional: include only a currently permitted string. If context identity is disclosed but the label field is denied, retain usable context without label; UI renders a local generic workspace label with no denied-derived initials, sort key or tooltip. entry_ref:{kind:WORKSPACE} is the existing safe repair destination semantics for the enclosing disclosed context, not an arbitrary URL and not an action grant. Any request for target data/action re-resolves current scope and Cedar.
No CompanyActor is created on GET. GN16 completeness, candidate freshness including denied->allowed, temporal changes, limits32Groups/256Companies, current policy and cursor5minute lifetime remain mandatory. Context hints alone never authorize a label. Valid Account with no contexts receives an actual empty result and Account settings; unavailable authority503 navigation_unavailable, never silently empty. Invalid current auth401; stale/expired/foreign cursor409 stale_cursor with no hidden ownership distinction. A known undiscoverable context target404. Populated context owner fixtures remain a separate acceptance family; first empty-context test does not fabricate Companies/assignments.

7. Operational bounds and acceptance limits
Registration start body<=4KiB; finish<=64KiB; WebAuthn parsing depth<=32; Account wrapper/terms manifest<=16KiB; up to8terms items each<=64KiB; proof header<=4KiB; cookie header<=16KiB; contexts response<=128KiB and100items; label<=256UTF-8 bytes; action list<=16. Unsupported/unserviceable bound ->explicit413/422/503, never truncation. Historical artifact and ceremony retention follow storage-refinement.json; missing terms closes enrollment only, not unrelated eligible Account operations. Initial deployment requires measured per-route concurrency/pending-attempt cap/rate limits and cleanup recovery evidence before activation; this packet does not manufacture50k/1M capacity claims. It does fix bounded payload work and avoids per-request remote content fetch or per-Company signup scans.
Success,origin/nonce swap,replay,lost-response recovery,stale/ABAterms,artifact outage,publication-vs-finish race,cookie ambiguity,CSRF parser confusion/family mismatch/expiry,zero-context-vs-unavailable and noCompanyActor are required executable candidates after approval. Fixture/hash/schema verification in verify.py is document consistency only. Full Account tests, implementation admission, production exposure and legal content authority remain HOLD.
