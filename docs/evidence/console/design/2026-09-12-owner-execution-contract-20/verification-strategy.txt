FV20 — Verus considered explicitly after owner suggestion
Decision: include Verus as the preferred candidate for a bounded proof of existing pure Rust monetary primitives and their caller-range obligations. Adoption is CONDITIONAL on source/build integration and maintenance proof, not a new mandatory whole-repository framework or a claim any function has been proved. No Verus/dependency install, source annotation, Rust/toolchain/CI change, proof execution or product test has occurred in20.
Evidence: official verus-lang/verus revision38f659b0e97a003d4fed73e083c71e786c6a3523 and pinned document URLs/excerpts/digests in verus-sources.json. Official docs describe a Rust subset, Cargo per-crate verification, checked arithmetic specifications, interaction with unverified code, safe API checks, ghost erasure and limited exec termination checking. This is a focused source-grounded assessment, not a claim of online consensus or production maturity from stars/publication counts.
Repository fit: console-payroll-domain currently depends on console-kernel-core and time, with pure i64/i128 arithmetic and existing golden cases. Existing trunc10/round10, national_pension_standard_income and checked conversions are candidate boundaries; storage, SQLx, web/Leptos and Cedar integration do not need to move into a proof language. Verify the actual production exec implementation with ghost/spec annotations erased for the ordinary executable; do not keep a parallel proof-only calculator that production can bypass or drift from. If annotations require a small ownership-preserving helper extraction, that remains later reviewed implementation, not permission to rewrite the kernel. The unverified facade must establish every precondition at runtime or expose an API whose verified guarantees cover all accepted inputs; a private module name alone is not proof of caller-range correctness.
First finite proof slice: existing monetary rounding/conversion primitives plus their reachable input bounds. State mathematical behavior independently before annotation: for nonnegative i128 x, trunc10 returns10*floor(x/10), result<=x, x-result<10, result divisible by10 and no overflow. Existing round10=(x+5)/10*10 requires proven x<=i128::MAX-5 at every reached caller or a checked-error public boundary; do not silently assume every i128 fits. Verify exact i128->i64 conversion returns the same integer iff in range and otherwise a typed failure. Extend to bounded sum/deduction conservation and rate scaling only after the first slice's maintenance/compatibility result warrants it. These properties do not establish that a specific Korean legal rounding rule or source edition applies. Preserve national_pension_standard_income's compare-before-truncate semantics; a simpler composed clamp must not be substituted merely because current bounds happen to align.
Next candidate targets: half-open interval clipping/partition with no double counting across prior/current anchored days; revision/terminal transition functions and manifest membership/conservation. Verus also has concurrent-code/state-machine support; it is not inherently limited to arithmetic. However a proved abstract commit/work/receipt transition is only a model until every concrete SQL/alias/trigger path is mapped to that transition with justified refinement and environment assumptions. Do not label PostgreSQL transaction atomicity, actual RLS, current Cedar operand loading, Account recovery or exact-version provider behavior as proved merely by assuming an external function's contract.

Proof boundary and acceptance
A proof is conditional on its specification and trusted components. Independent review must assess what was proved, input domain/nonvacuity, explicit assumptions and omitted error branches, not only verified:function_count. No assume(false), admitted goal, external_body around the target algorithm, or body-versus-build cfg(verus_only) divergence may make the selected goal pass. Keep a reviewed inventory of every external_body/assume_specification/trusted dependency boundary and corresponding runtime proof/test owner. The Verus verifier/solver/compiler/vstd and correctly specified environment are part of the trusted computing base, not all mathematically reverified by this exercise. Existing legal/source authority stays separate.
Unverified public callers must either have a total checked facade with no unchecked requires or a proved construction path for invariant-carrying values; run the applicable -V check-safe-api check on the selected verified crate/API, retaining limitations as explicit failures. No weakening existing tests or business validation to obtain a proof. A deliberately wrong postcondition or wrong rounding/overflow variant must be rejected by the verifier, and the accepted input set must have valid concrete witnesses including supported boundary cases. These are future independently reviewed proof/test acceptance candidates, not executed negative tests today.
Capture exact Verus/vstd/solver/compiler versions, source/features/target/dependency/lock hashes, fully checked functions and public entries, assumptions, excluded functions/crates, normal build and proof artifacts, verification duration/memory plus a small real change's proof-maintenance delta. Official cargo verus focus skips dependency re-verification and is not the acceptance invocation; normal cargo build also does not prove code. Candidate acceptance uses full selected cargo verus verify or build with exact dependencies, applicable safe-API check and the existing product tests against the same exec path. A green result with0 verified targets is unavailable coverage, not success.
