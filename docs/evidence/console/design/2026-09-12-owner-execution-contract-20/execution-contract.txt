OE20 — One owning execution boundary
OE20.1 Choice and trust
Extend the existing domain-owned transaction and existing Rust pure kernels. Native/source commands run an async owner adapter executor on one borrowed SQLx PostgreSQL connection, composed in console-app through consumer-declared participants. No new payroll application crate, adapter-to-adapter dependency, arbitrary callback registry, nested PgPayRunPort::write, block_on or pool-owning participant. Existing generic-instance transaction machinery is reused where its owner invariants fit. Legacy compatibility wrappers keep their current behavior only on nonenrolled targets.
The current console_ontology_cmd LOGIN has no direct DML on the needed governance/source/audit tables. Therefore a borrowed Rust function that executes raw INSERT is not a usable privileged participant. Select a fixed SQL owner commit entrypoint, called once after trusted Rust validation in the SAME already-open transaction. That entrypoint invokes restricted owner SQL participants and validates/writes the complete registered mutation set: domain rows, source generation/head, governance consumption if required, source/domain pins and adoption, common attempt/work/capacity finalization, audit and sole Company command receipt. It does not COMMIT; the domain Rust executor alone commits. Existing owner SQL/Rust transformations remain in their responsible crates/migration-owned routines; app only forwards. Cross-owner private SQL participants are not independently callable by the LOGIN credential.
Reuse console_ontology_cmd as the enrolled common/source/native command credential; propose one NOLOGIN console_owner_commit_writer for these new fixed entrypoints and their confined persistence authority. Do not repurpose the existing console_ontology_writer generic capability as source authority. No new login per source kind/reason/role/persona. Credential provisioning/rotation and real-role catalog proof still precede enrollment. The API execution process, authenticated identity derivation, Cedar evaluation, source decoder and Rust kernel are trusted. SQL independently enforces declared structure, scope, state, identity, CAS, bounds, exact command/gate binding and immutable membership, NOT the truth of a Rust-calculated amount, external credential or Cedar verdict. Compromise of this trusted process/command credential can authorize false facts; this design does not hide that trust boundary behind an allowed=true parameter, a signature made by the same process, a GUC or a marker row.
Reject three alternatives here: wrapping existing pool-owning methods would create split commits; broad runtime DML would reopen generic source/receipt/money append bypasses; duplicating the Rust payroll kernel in SQL would create two monetary authorities. A fully isolated execution service could reduce API compromise reach but is not required to pretend this same-process boundary is stronger. Separate service selection is a later explicit threat/deployment decision, not an unstated property of20.

OE20.2 Phases and replay
P0 authenticate current Account/session, Company selection, CSRF where applicable and registered action discovery. Request never chooses effective actor, SQL owner, protocol, credential, fixture clock or policy result. Decode bounded transport; resolve immutable registry/type/owner/codec. Discover candidate control/attempt/work/source/retained IDs without treating absence or preview as authority. Do not read external source bytes, create staging artifacts or require current source availability before receipt/provenance resolution; public input values do not become trusted prepared output.
P1 owner acquires command pool and starts transaction. Acquire only applicable earlier Group/Account/Company-authority/routing/work/attempt/command resources in LO20 order, initially gathering facts without rejecting solely on lost new-effect permission. Under the exact Company command fence recheck server-owned attempt provenance and receipt. If earlier control/attempt resources are newly discovered, rollback/replan from the start; no late lock. Historical matching success is returned under current disclosure, without requiring current source validity/assignment/execute grant or repeating any effect. An undisclosable outcome is unavailable, never proof of no effect. A binding conflict is disclosed only when permitted. This preserves14/18 rather than introducing a new replay algorithm.
P1a if immutable external bytes are needed after authoritative receipt absence and eligible direct/READY provenance, end the probe transaction without mutations and release all its locks. Fetch bounded exact existing immutable versions outside a transaction; this phase creates no new staging artifact and grants no effect authority. Replan and begin a fresh owner transaction, repeating P1 including all applicable earlier fences and the authoritative receipt/provenance probe. A concurrent success returns its currently disclosed receipt; concurrent unknown/conflicting state reconciles or refuses. If an external read fails, repeat that receipt/provenance probe before surfacing a new-effect storage blocker, so a meanwhile committed success is not mislabeled as absent. The unlocked prior absence is never reused as authority.
P2 only authoritative receipt absence and an eligible direct registration or exact READY attempt in the final fenced transaction allow new-effect checks. Acquire all period/source/retention/domain locks from a predeclared bounded plan; source reads and absence/ambiguity queries occur under guards. Current Account/Company/field/action/source/expiry/SoD and exact gate readiness are evaluated. Pure Rust source decoding/calculation uses the exact locked facts and preloaded immutable bytes, no network or second pool. No SQL mutation occurs through an unfenced public helper. Global rule/issuer/codec admission remains pinned and deployment-fenced.
P3 invoke exactly the selected fixed owner SQL commit entrypoint with canonical command, exact source/expected references and bounded typed prepared rows. SQL rechecks authoritative command/attempt/protocol/current pointers, normalized immutable envelope binding and structural prepared-row consistency; it consumes the exact gate and invokes already-locked owner participants. Native results bind actual input unit custody_digest and closed input/batch membership from18. A marker saying validated or a caller-supplied count cannot replace these checks. An entrypoint cannot change owner/action/type or create a second receipt namespace. If deferred checks cannot pass, the transaction rolls back.
P4 before commit, evaluate current authoritative expiry/disclosure/effect deadlines again within the fenced authority/source window; an expiry failure rolls back all provisional writes. Commit once. A lost commit acknowledgment is UNKNOWN; keep exact command/attempt/pins and reconcile, not new command/cancel/successor. Same-binding conflict retries only after established no effect, max3; changed source/schema/policy needs user-visible revalidation through the owning draft. Mutation SQL entrypoint invocation is not itself proof commit succeeded.
Preflight uses same decoders/current owner checks and nonconsuming gate check without changing source, draft, work, pins or approval. It may hold bounded read locks; it cannot issue upload/adoption jobs or build a task from GET. Preparation of staged bytes is a separately explicit registered action, not preflight side effect.

OE20.3 Registration and result ownership
Object ownership and action dispatch are independent from user permission. A registry-bound type selects exactly one payload owner; actions for that type must match its immutable owner binding and compiled decoder/result profile. Missing/unsupported registration refuses enrolled mutation. A source-specific action remains an ordinary registered Action using the same draft/review/receipt protocol; reasons do not select an executor or create a workflow taxonomy.
Owner source reads return current typed facts plus exact selected/candidate refs and complete bounded dependency/expiry observations. They never return allowed=true as lasting authority. Internal execution facts may include hidden subjects for deterministic completeness, but presentation returns only currently authorized owner projections. Generic data returned from a receipt, source count, error, link, day package, SSR/data-* or hydration must pass current resource/field/derived/history disclosure before serialization. Read-only users cannot invoke mutation by copying a linked object or action request. Required reviewer evidence must be viewable by that reviewer; hidden competitor identities/counts are not exposed to ordinary requesters.
No domain class is mislabeled PayRun merely to fit0223. New receipt owner/target/action rosters are enrollment dependencies, with Account attribution13 and exact CCF1 binding14. Current users.actor FKs do not accept Account IDs by coincidence. Closed source input/read/write mappings in owner-interfaces.json and caller-census.csv identify ownership; they are proposed interfaces, not claimed compiled methods or deployed roles.
