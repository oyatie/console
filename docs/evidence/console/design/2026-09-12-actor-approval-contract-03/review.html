검토 후보 03 · 사용자 요구와 설계 제안 · 구현/전체 설계 승인 아님

한 계정, 회사가 정의하는 업무,
객체마다 정확한 권한

지원자·재직자·퇴직자·외부업체 인원은 서로 다른 계정 유형이 아닙니다. 계정은 회사나 고용관계 없이도 존재하며 퇴사 후에도 유지됩니다. 같은 계정과 Cedar 정책 평가를 통해 현재 허용된 화면·정보·액션을 제공합니다.

인사담당자·임원·현장관리자는 인터뷰의 예시입니다. 직급·직책·직업별 권한이나 화면을 미리 만들지 않습니다. 회사마다 업무와 책임을 정의할 수 있고, 같은 직함이어도 권한이 다르거나 서로 다른 직함의 권한이 같을 수 있습니다.

추천하는 구성

구성의미
지속되는 Account본인 인증·개인 보안·복구. 회사·고용·업무 역할이 없어도 로그인합니다.
회사별 권한 묶음기존 액션을 재사용해 회사가 필요에 맞게 정의합니다. 한 사람이 여러 묶음을 가질 수 있습니다. 직급 enum이나 강제 직업역할이 아닙니다.
범위가 있는 배정누가 어떤 행위를 어느 법인·부서·사업장·객체에서 언제까지 수행할 수 있는지 함께 기록합니다. 서로 다른 배정의 행위와 대상을 무제한으로 합치지 않습니다.
객체·필드 제한직원 정보를 볼 수 있어도 금액·의료 증빙·특정 보호대상 정보는 별도입니다. 읽기·수정·결정·내보내기·위임을 구분합니다.
현재 정책 평가정확한 대상·행위·관계·유효기간을 서버가 확인합니다. 일치하는 명시적 금지는 다른 권한 묶음이나 관리자 명칭으로 우회하지 못합니다.

사용자가 제시한 두 사례

급여 담당 A: 허용된 직원들의 급여를 준비하되 보호대상의 금액은 볼 수 없습니다. 보호는 “임원”이라는 직함의 내장 효과가 아니라 해당 객체·필드에 적용된 정책입니다. 합계·다운로드·시트 수식으로도 숨겨진 금액을 복원할 수 없어야 합니다.

현장 업무 담당 B: 배정된 법인·사업장 또는 부서의 인원과 허용된 근태 정보만 봅니다. 하위 조직 포함 여부도 명시하며, 같은 장소를 사용하는 다른 법인까지 열리지 않습니다.

일부 급여를 볼 수 없는 사람이 숨겨진 금액까지 승인해서는 안 됩니다. 허용된 작업은 진행하고 남은 작업은 적격 담당자에게 이어지거나 막힌 상태를 명확히 표시해야 합니다. 부분 준비·검토를 전체 급여안 완료와 연결하는 정확한 계약은 B02/B07의 남은 설계입니다.

객체는 보이지만 일부 정보는 제한될 수 있습니다

임원 인사카드 자체는 볼 수 있으면서 보수·계좌·주민등록정보는 각각 허용된 항목만 보일 수 있습니다. 객체 조회가 모든 필드 조회를 뜻하지 않습니다. 같은 객체와 화면 구조를 쓰고 서버가 허용된 정보만 반환합니다.

필드의 존재를 보여도 되는 경우에는 제한·미입력·조회 오류를 구분합니다. 존재조차 비공개라면 필드와 제한 표시도 숨깁니다. 연결된 계약·대화·첨부·과거 변경이력에도 현재 권한이 적용됩니다. 허용된 연락처를 수정할 때 숨겨진 급여값이 빈값으로 덮어써지지 않도록 부분 수정 액션을 사용합니다.

Discord와 게임에서 가져올 점

여러 권한 묶음, 범위별 공간, 권한의 출처를 확인하는 화면, 짧은 단계별 설정과 명확한 업무 소유권을 참고합니다. Discord의 권한 충돌 규칙이나 Administrator 우회는 가져오지 않습니다. 공식 문서상 Cedar의 명시적 forbid는 permit보다 우선하지만 오류 정책은 건너뛰므로, 콘솔은 관련 정책·필수 사실 오류가 있는 요청을 별도로 차단해야 합니다. 확인한 사실과 설계 제안을 구분했습니다.

입력 화면과 실제 업무 경험

권한을 설정할 수 있는 사용자는 사람/집단 선택 → 권한 묶음 → 대상 범위 → 필드·제한 → 기간·위임 한도 → 영향 확인 → 제출/게시 흐름을 사용합니다. 기존 객체를 선택하고 실제 허용·제한이 어떻게 바뀌는지 확인합니다. 일상 업무에 Cedar 코드 작성이나 자유서술 해석을 요구하지 않습니다.

실제 담당자는 공통 객체 화면에서 자신의 업무, 이미 채워진 입력, 허용된 근거, 저장·처리 상태와 다음 행동을 봅니다. 권한 설정용 복잡성은 업무 화면에 떠넘기지 않습니다. 미리보기는 대상자의 계정으로 가장하거나 민감정보를 열어보는 기능이 아닙니다.

메뉴를 숨기는 것만으로 보안을 구현하지 않습니다. 직접 URL·API·검색·알림·첨부·내보내기·캐시·시트 파생값에도 같은 자원 정책이 필요합니다. 권한이 남아 있는 작업은 유지하고, 회수된 정보는 서버 응답과 열린 화면에서 제거합니다.

채팅 링크와 읽기 화면의 권한 경계

대화방을 읽는 권한은 링크된 기밀문서를 보는 권한이 아닙니다. 같은 메시지에서도 수신자마다 허용된 카드만 표시하고, 권한 없는 수신자에게 제목·미리보기·첨부 URL을 복사하지 않습니다. 인용·전달·검색·알림·외부메일에도 적용합니다. 외부 공유는 별도의 허용된 Action과 필요한 결재를 거쳐 대상·정보·기간을 한정합니다.

화면을 열 수 있어도 수정·결재·공유를 실행할 권한은 별도입니다. 직접 API·단축키·서버 함수·sheet write-back·자동화도 같은 owner 검사와 현재 권한을 통과해야 합니다. GET·미리보기·prefetch는 업무 상태를 바꾸지 않습니다. prepare 뒤 권한이 회수되면 execute는 실패해야 합니다.

16개 입력·노출 경로의 검증 표에 정상·거부·회수 동작과 소유 경계, 향후 구현 범위를 기록했습니다. 이미 읽거나 반출한 평문까지 소급 회수할 수 있다고 주장하지 않습니다.

SSR에서 제공 정보 자체를 통제합니다

현재 권한을 확인하고 허용된 owner projection만으로 화면을 렌더링합니다. 기밀정보는 DOM뿐 아니라 원본 HTML·data 속성·hydration payload·inline JSON·streaming chunk에도 포함하지 않습니다. 인증된 민감 응답은 검증된 별도 캐시 설계가 없으면 private/no-store로 다룹니다. 최초 렌더 이후 API·검색·미리보기·실시간 업데이트도 같은 기준입니다.

검증은 스크린샷만 보지 않고 실제 HTTP·HTML·초기 데이터에 금지된 값이 없는지 확인해야 합니다. SSR은 정보 전달 경계이며 상태 변경은 별도의 현재 Action 권한으로 통제합니다.

고용 전후에도 이어지는 경로

지원자: 채용 공고 → 같은 Account로 가입/로그인 → 자기 지원서 입력·제출 → 허용된 상태·보완·면접·제안 응답. 직원이나 회사 업무 역할을 만들지 않습니다. 기존 recruiting owner를 확장하며 내부 평가나 직접 채용 권한을 주지 않습니다.

퇴직자: 같은 Account로 로그인 → 나의 기록 → 과거 근로관계 → 적격 증명서 신청·발급·조회. 개인 인증수단을 회사가 초기화하거나 회사 삭제로 없앨 수 없습니다. 사실이 충분하면 정책에 따라 자동 발급하고, 보완이 필요하면 현재 적격 담당자에게 이어집니다.

향후 외부업체: 동일 계정의 한정된 업무 관계와 수신자·목적·기간이 정해진 초대. 초대받은 업무를 끝내기 위해 내부 조직을 배우거나 별도 영업 가입을 할 필요가 없습니다. 이 모듈은 향후 구현입니다.

결재·정정과 실제 저장 경계

한 Account의 원래 UUID로 법인별 실행 이력을 남깁니다. CompanyActor는 기록의 연결점이며 권한이 아닙니다. Company는 계속 법적 단위와 RLS 경계이고 Group은 법인별 권한 내에서 전사 업무를 조합합니다.

급여 제출자와 결정자는 서로 다른 검증된 자연인입니다. 선택적 실행허가와 급여안 결정은 별도 액션·기록입니다. 승인안의 오류는 원 승인이력을 보존하며 새 초안을 연결합니다. 오래된 생성/재시도도 이미 대체된 원안의 원천·계산·이력을 바꾸면 안 됩니다.

검토 상태와 남은 공백

56개 비실행 검증 시나리오, 28개 기준 소스 신원, 이전 범위별 검토와 현재 적용 여부를 기록했습니다. 과거 SHA의 수용은 바뀐 Account·정책 모델의 승인이 아닙니다. 새 독립 검토 receipt에서 계정·권한 설계와 정정 보완의 범위별 수용을 확인할 수 있습니다. 전체 설계 승인은 아직 없습니다.

남은 설계: 부분 열람에 따른 급여 준비·결정 범위, 전사 실행의 영속성, 자동 인계와 결과 미확정 복구, 서버 입력 초안 수명주기, 전체 화면 상태표, 직원 금액 명세 공개·이의제기. 계정 이전·정책 편집/평가 표면·증명서 서명/발급의 세부 운영 증거도 해당 검토가 필요합니다.
