업무 배정·인계 설계 후보09
범위: 첫 급여 준비·검토 업무의 자동 배정과 업무 연속성. 전체 설계/구현 승인은 별도입니다.

1. 사용자가 겪는 흐름
병가·부재가 기록되면, 시스템이 업무별 권한·필요 정보·적합성·가용성·업무량을 확인해 배정합니다. 새 담당자는 내 업무에서 저장된 입력과 필요한 근거를 바로 확인합니다. 대체자를 찾지 못하면 권한 있는 사람의 예외 업무로 남기며, 휴가를 불허하는 근거가 되지 않습니다.

2. 법인과 담당자 소속은 별개
법인에 현지 인사담당자가 없어도, 다른 법인의 사업장/부서 또는 특정 Account가 업무를 맡을 수 있습니다. 담당 서비스 관계와 Cedar 권한은 각각 확인합니다. 대표이사보다 권한이 넓은 직원도 같은 방식으로 처리하며 직급은 권한의 상하관계가 아닙니다.

3. 업무 단위마다 한 담당자
일부를 나누려면 실제로 분리 가능한 업무를 나눕니다. 한 업무를 여러 사람이 불분명하게 일부 분담하도록 만들지 않습니다. 임시 인계와 영구 이전은 책임의 기간을 뜻하며, 각각의 업무 배정과 구분합니다.

4. 전사 업무량은 원자적으로 확정
같은 PostgreSQL 안에서 공통 업무량과 한 법인의 담당·초안 변경을 함께 확정합니다. 여섯 법인이 같은 사람을 동시에 여유 있다고 판단해 초과 배정하는 일을 막습니다. 별도 분산 예약과 만료 타이머는 도입하지 않습니다. 업무량 단위는 설정된 작업별 예산이며 인간의 생산성을 정확히 계산한다는 주장은 하지 않습니다.

5. 업무는 이어받고 결재자는 바꾸지 않음
초안 ID·작성 이력은 유지하고 현재 담당과 편집 세대가 바뀝니다. 개인 초안은 자동 이전하지 않습니다. 이미 성공한 실행은 원 영수증을 확인하며, 결과가 미확정이면 확인하기 전 새 명령으로 다시 실행하지 않습니다. 전사 준비에 묶인 업무는 정해진 중지 권한과 확인 절차를 거칩니다.

6. 복귀는 진행 중인 일의 강탈이 아님
복귀 이후 새 업무는 원래 책임 관계를 따릅니다. 이미 다른 사람이 맡은 업무는 기존 유효기간 안에서 이어가며, 되돌릴 필요가 있으면 새 세대의 안전한 인계를 수행합니다. 임시 기간을 몰래 늘리거나 오래된 탭의 권한을 되살리지 않습니다.

7. 자동화가 못 하는 상황의 입력 경로
업무 예외 → 실제 업무 선택 → 적격 후보 또는 특정인 지정 → 기간/책임 변경 확인 → 현재 상태 재검증 → 확정. 권한 없는 강제 배정이나 과부하 우회는 없습니다. 비공개 사유는 노출하지 않지만 허용된 복구 경로를 제공합니다.

8. 착수 전 남은 구현 계약
현재 workflow는 legacy 권한을 적용하며 Cedar는 shadow 상태입니다. 새 경로에 실제 Cedar·현재 정책 검증을 연결해야 합니다. 정확한 API/SQL/ACL, 모든 claim/decide/finalize 경로의 잠금과 회계 일치, 마이그레이션·복구·성능 증명은 통합 계약과 승인 테스트에 연결합니다. 64개 사례는 아직 실행 테스트가 아닙니다.
전체 기술 계약
WA1 — A single accountable task, continuous work context, independently evaluated authority
Proposed bounded B04 contract. Builds on AI1/AM1, PC1, FD1, candidate06 recovery and GO1. Applies to explicit payroll preparation/review task definitions and their native draft/calculate participation first. It does not implement all absence/HR processes, general optimization, cross-tenant staffing, communications or autonomous payroll decisions.

WA1.1 Evidence, owner and simpler architecture choice
At product base05200e43, workflow/domain NewWaitingTask and NodeStepCommit, workflow/runtime and workflow/adapter-postgres own Company waiting tasks, transitions and outbox. claim_waiting_task serializes OPEN→CLAIMED using a row lock and replays same-user claims; it has no assignment epoch/capacity protocol. Inbox role-key filtering is existing behavior, not the required account/resource/property policy design. workflow/runtime/authz_guard.rs pins LegacyOnly and CedarEvaluation::NotConfigured; completion.rs explicitly relies on that boundary. Enabling a new routing path requires real Cedar evaluation and current policy guards, not relabeling the shadow guard. Source findings are scoped to inspected owners; no claim that the repository contains no scheduling logic anywhere.
Extend workflow's existing domain/runtime/adapter owner, with task assignment as part of its lifecycle; no new parallel task service/database. Ontology exposes the governed task projection and revision links; workflow remains the single assignment writer. Draft revision history remains common ontology-owned under FD1. Company task/domain facts remain one Company per transaction. Group control remains platform/group-owned through narrow participating helpers, never app.current_org=Group.
Selected pilot design: same PostgreSQL transaction for Group capacity accounting + ONE target Company's assignment/draft/receipt. This fits AI1's existing single PostgreSQL boundary and GO1's narrow cross-scope control access. No second connection, network RPC, separately expiring reservation or second Company's business table participates. A Group helper may mutate protected routing counters/charges, not payroll values or another Company's tasks. Runtime has no raw access to those Group tables.
Alternatives: (a) independently reserved distributed slots require fences and unknown-commit reconciliation that this deployment does not need; (b) preallocated Company quotas prevent some overbooking but strand shared capacity and complicate borrowing; (c) stale aggregate reads alone violate the six-Company invariant. Use atomic Group accounting now. A future split-database topology must design an equivalent protocol before routing migrates; current design does not promise transparent distributed operation.

WA1.2 Typed objects, relations and single ownership
WorkItem identifies one existing Company workflow waiting task: (company_id,task_id). Bind immutable task definition ID/revision, target object/action family and exact completion criterion. A WorkDefinition is a governed typed configuration object, not an enum of occupations: supported action/target types, required review/input field set, qualification requirements, routing scope, fixed capacity_units, priority class, default due/assignment interval rules and coverage policy. Business definition changes create a revision; open task changes require explicit owner replan with expected task version, never dynamic reinterpretation.
Workflow-owned current assignment: assignee_account_id nullable, assignment_epoch monotonic, state UNASSIGNED/ACTIVE/PAUSED/TERMINAL, task definition revision, coverage ref/revision, target/provisioning membership incarnations relied on, routing-rule revision, validity [from,until), obligation interval, capacity units/charge reference, relied-on current proof versions, original responsibility ref, handover plan ref if any. Task business status and assignment state are different: assigned does not mean approved/completed; PAUSED never satisfies completion. One ACTIVE or PAUSED assignment per WorkItem. UNASSIGNED has no accountable worker, with a separate governed queue-supervision route; it must not display the queue as a fictitious worker.
WorkCoverage is workflow-owned target-Company typed relation: target scope/object set and supported WorkDefinition refs -> explicit provider Account OR (provider_company_id,provider_orgunit_id), active interval, precedence, allowed temporary/permanent responsibility changes, supervisor route and policy-approved routing principal reference. Composite references preserve provider's own Company tree. Provider unit membership is resolved through canonical org/relationship owners; titles and unit membership alone do not grant target permissions. No fake target Employment/user/OrgUnit is created.
HandoverPlan is workflow-owned governed object with initiator/source event, exact WorkItem IDs and expected assignment epochs, temporary or permanent responsibility intent, optional explicit recipients, effective interval, reason_code, linked evidence and preserved original attribution. Partial distribution is expressed by separate task IDs. No PARTIAL_SHARING mode. Active tasks with separable required outputs may use the definition's explicit split action: cancel/fence original no-effect work, create children with disjoint exact coverage and a parent completion predicate. Arbitrary splitting of an indivisible final decision is refused. This slice reuses PC1's review units, not an open-ended user-authored workflow graph.
Group-owned RoutingAccountControl keyed(group_id,account_id): version, accepted capacity profile revision/limit, enabled state, availability projection revision and authority provenance, used_units and fairness sequence. Group-owned WorkCharge uniquely keyed(group_id,target_company_id,task_id), assignment epoch and account, positive integer units, active/released lifecycle. It contains opaque work key/epoch and units only, no task label, salary, employee subject or medical reason. Workflow owner passes verified bindings through a restricted helper; a draft save never edits a charge. Append a minimal assignment receipt referencing old/new epochs, source, exact authorized plan, effective time and proof/rule refs; do not copy full linked content into the audit log.

WA1.3 Authority and bootstrapping
Authorization concepts, to be bound to exact Cedar schema/ActionDefinition identifiers in W04: read task metadata; read linked object/field/history; manage scoped coverage; nominate/transfer exact work; manage capacity profile; routing workload eligibility probe/assign; reconcile task result; stop Group operation; execute/decide business action. These are separate grants. Existing GROUP_ADMIN/FINANCE, job title, chief executive status or provider department do not confer them. Preserve correlated action/target/field/validity/delegation tuples; no cross-product union. Account-only external personnel may qualify through an authorized engagement; active Employment is not a universal precondition.
Routing uses a provisioned workload principal with a versioned, target-Company-specific routing mandate. It can evaluate typed eligibility through a narrow policy-owner probe and mutate assigned task metadata through workflow; it cannot impersonate the human recipient, read required salary values, approve a decision, seal a human draft or inherit a human session. Candidate eligibility probe evaluates the candidate Account against exact action/target/required field set with current owner facts, returning only authorized feasibility/proof refs. It does not export a human credential or unrestricted 'evaluate as anyone' endpoint. A real human action still requires their current enabled Account/session and all AI1/owner/SoD guards.
Policies may intentionally authorize work only when assigned to the actor. Avoid a circular 'must already own the task to become owner': the policy owner may evaluate a trusted proposed assignment fact for the exact candidate, task, epoch, interval and action. Only pre-existing policy explicitly delegating that assignment-conditioned entitlement can permit this. The workflow assignment action itself must be authorized to establish that relation for that scope. Evaluate final actual-assignment policy again within the same transaction before commit. Other required rights, qualifications and SoD must already hold; proposed assignment is not a blanket grant or caller-supplied Cedar fact.
Routing configuration activation requires a governed manifest with target coverage, capacity profiles, routing mandate, exception supervisor and an authorized configuration-recovery route. Console provisioning under AI1's supervised tenant bootstrap records named initial configuration custodians and scoped grants in an immutable receipt; it creates neither salary authority nor title roles automatically. Thereafter policy-owner actions govern grants, with applicable independent approval. Last recovery-route removal fails activation checks or marks routing unavailable; do not invent a SUPER_ADMIN. Console support may receive a restricted operational configuration alarm under its existing operator authority, never business payload or implicit permission to repair grants. Actual initial identities/production provisioning authority remain operational inputs.

WA1.4 Capacity, availability and bounded meaning
Capacity is an admission budget for currently assigned work, not a claim to know human productivity or working hours. WorkDefinition supplies positive integer effort units; CapacityProfile supplies a positive integer limit for an Account within this Group, with validity/revision and governing actor. Defaults are typed configuration populated during setup, not repeated subjective prompts per task. Missing/expired profile or effort units => CONFIGURATION_REQUIRED, never infinite/zero capacity. Existing assigned work remains charged while PAUSED or awaiting external evidence; release only on proven task terminal state or atomic transfer to a different current worker. No TTL releases active or unknown work. One Account's total active units across all six Companies is enforced by the single locked Group control row.
Assignments require a bounded intended obligation interval and validity window supplied by the definition/planned task; qualification/coverage/availability must cover the interval. This is conservative eligibility, not a future scheduling optimizer or promise of deadline completion. Recurring duties generate distinct bounded WorkItems. Unbounded/unknown intervals require replan rather than silently treating leave as irrelevant. Availability facts use typed AVAILABLE/UNAVAILABLE/UNKNOWN intervals and current policy-approved source references; UNAVAILABLE dominates overlap, UNKNOWN is not AVAILABLE. Data source conflicts are an exception requiring owner correction. No holiday/timezone/free-text parsing by LLM.
The originating HR/availability owner preserves medical reasons and leave/attendance decisions. It publishes a minimal versioned routing projection (Account, Group, interval, availability, source_ref/projection version) through an owning same-DB port/outbox; latest accepted projection is the routing truth only if its source watermark/freshness is valid. For known scheduled absences, routing reads the interval immediately; delayed UI notification does not defer it. Source changes that invalidate eligibility must advance the shared RoutingAccountControl availability version synchronously in the source transaction before new effects can rely on old availability. If an owner cannot participate or freshness cannot be established, pause affected new assignment/effects rather than rely on an eventually delivered event. Background events schedule reassessment; they are not the revocation fence.
Calling in sick, leave extension/cancellation, termination of a relied-on engagement and return emit distinct typed changes. A missed clock event does not automatically become unauthorized absence or discipline. Staffing exceptions never reject a leave request or alter its legal/domain decision. This packet defines the integration seam, not substantive leave law or all source owner implementations. Manual authorized availability updates through the same owner provide a typed fallback when the external/source system is unavailable, with precedence/expiry/provenance and a conflict queue.
Capacity reductions never erase or secretly reassign charges. If new limit < used_units, mark OVER_CAPACITY and reject additional positive net load; permit proven release and transfers out. Raising a limit is a separate authorized profile change, not an override hidden inside assign. No forced over-capacity button. External commitments may lower the explicit profile, but untracked personal or other-tenant work is not inferred or exposed; cross-tenant capacity coordination is outside this pilot.

WA1.5 Deterministic candidate matching and reevaluation
Process due routing events by typed priority, due_at, created_at and stable task ID with bounded per-Company queues. Within one task, enumerate all applicable authorized coverage candidates at the pinned coverage/provider membership versions. Filter conjunctively by target relationship/incarnation, required candidate task metadata and field permissions, explicit assignment-conditioned policy if used, natural-person independence of the exact decision, typed qualification and evidence validity, availability interval, valid capacity profile and available units. UNKNOWN source/identity does not prove qualification. The workload probe may compute confidential constraints; users receive only permitted explanations.
Selection among feasible candidates: explicitly authorized nominated recipient if still feasible; then coverage precedence; then smallest projected utilization (used_units+task_units)/limit using checked integer cross-multiplication; then oldest last-assignment sequence; then Account ID. For an existing assignment to the same Account, do not add its own charge twice. Qualification is a hard supported predicate; no subjective LLM score. Stable sequence breaks ties, not a guarantee of globally optimal distribution. Skip incumbent for absence-driven replacement while they remain unavailable. No automatic reassignment solely because another person's load becomes lower; keep work stable.
Candidate enumeration uses a version-bound keyset cursor, max100 candidates/page. Pilot evaluation budget max2,000 candidate Accounts/task and max6 target Companies; these are explicit supported routing bounds, not employee quotas. Reaching a bound or detecting membership drift means MATCHING_INCOMPLETE, never NO_ELIGIBLE. NO_ELIGIBLE is valid only after a complete stable scan. Intermediate candidates/rank/capacity values stay protected. Commit the chosen candidate in a short transaction with all current guards, task epoch and capacity rechecked; scans are advisory. Contention/changed versions resume a new scan generation, max3 automatic commit retries before a durable exception, no endless reshuffle.
A deterministic scan may miss a later newly eligible candidate until the next event; the successful assignment need only be currently feasible, not provably globally minimum-load at commit. Source/version changes, capacity releases, qualification/policy changes and manual retry schedule deduplicated reevaluation of affected pending tasks. Persist cursor/checkpoint and event watermark; periodic bounded sweeps recover lost notifications. Work item routing generation and event source version deduplicate overlapping sick/leave events. After automatic retry budget exhaustion, a new relevant source version or explicit authorized retry starts a fresh bounded generation, not an immediate self-triggering loop.

WA1.6 Atomic assignment and total lock order
For enrolled task paths, extend GO1's order: (1) Group identity/topology guard; (2) involved Account/security guards sorted by Account ID, plus current human session when there is a human effect; (3) target and relied-on provider membership/policy/qualification guard references in canonical sorted order; (4) involved RoutingAccountControl rows sorted by Account ID; (5) target Company coverage/definition guards, then WorkItem assignment guards sorted by task ID; (6) applicable Group operation parent SHARE fence; (7) Company draft/child/attempt guards sorted by stable key; (8) workflow run/node guards needed for task transition, then existing domain period/run/source/governance order. Paths acquiring only a subset must respect the same relative order. Discover refs before locking, then validate their versions under locks; changed refs cause rollback/restart, not acquisition of an earlier lock while holding later locks.
Availability/capacity changes lock their relevant earlier guards/control row, commit version/update and durable event without taking Company task locks. Coverage/provider/qualification/policy writers change the relevant guard and emit events without synchronous task traversal. Business execute takes routing control SHARE when it does not change capacity; assignment, release and task-terminal transitions take relevant routing control EXCLUSIVE from the start. No SHARE→EXCLUSIVE upgrades after a task lock. Domain effect that atomically completes a task takes capacity write locks up front. Unsupported owner paths remain disabled on enrolled tasks until they participate. Ordinary unrelated payroll writes do not acquire task/capacity locks merely because workflow exists.
Workflow assignment transaction: current caller/workload mandate + candidate proof -> old/new account controls -> exact task epoch/definition/coverage + current assignment -> parent fence if linked -> exact linked draft/attempt set -> validate no unresolved conflicting effect -> owner cancels old READY no-effect intent where permitted -> workflow updates one assignment epoch and common draft owner updates custody/editing epochs -> Group helper releases old charge and creates/updates new charge -> immutable assignment receipt and transactional notification outbox. All commit or none do. Group helper validates group membership, exact target Company armed context, receipt/charge uniqueness, nonnegative used_units and new load<=limit for positive net admission. It cannot mutate arbitrary charges by raw client IDs. Existing same-account unchanged binding is a receipt replay/no-op; changed payload under same command ID conflicts.
Every charge mutation and task lifecycle transition joins the owning protocol. Active WorkCharge unique by WorkItem and assignment epoch binds precisely to its current assignment; used_units equals active charge sum for that Account. Increment/decrement and actual charge mutation occur together. Charge audit and task receipt share command binding so retry cannot debit twice. Crash/response loss: query exact assignment receipt under current disclosure before proposing another transfer; an ambiguous client timeout never releases capacity. Bounded periodic consistency checks use the privileged owner to compare controlled charge refs with authorized per-Company task state; mismatch pauses new admission and opens repair, never overwrites task truth from a counter.
Historical charge retirement after Company/Account relationship removal is a separate release-only operation, not new admission. Current membership validation applies to new assignment/positive load; it must not strand an already recorded charge when a Company leaves this Group or is reminted into a Group-of-one. Keep the original Group/Company/task/assignment-epoch charge binding and immutable attribution. An explicitly authorized reconciliation principal may resolve that exact historical task through its Company owner and, in the same transaction, release only proven terminal or safely unassigned no-effect work from the original Group charge. The helper validates the existing historical binding and release-only authority rather than requiring new membership in the old Group. It cannot assign a successor, increase capacity usage, copy task data into the old Group, or grant access to the removed Company. Both original Group control and current Company owner recovery permissions are required; if either proof or effect outcome is unavailable, retain/quarantine the charge and expose a restricted recovery case. No transfer of the charge to the new Group or re-admission on remove/readd is automatic. A new active assignment in a new Group requires a new currently authorized plan after old unresolved work is fenced/reconciled.
No cross-Company business transaction occurs: the Group helper touches only Group control data, while app.current_org remains the one target Company. No Group-wide mutex serializes unrelated Accounts; two Companies assigning the same Account deliberately serialize. Helper ACL, fixed search_path, server context binding, no raw runtime grants, parameter validation and catalog ownership proof are required before activation. Exact migration SQL and mechanical lock instrumentation integrate in W04.

WA1.7 Temporary coverage, permanent transfer and return
Responsibility continuity and atomic task assignment are distinct. A temporary HandoverPlan leaves the original responsibility relation in place with a bounded coverage interval; a permanent transfer changes the future responsibility relation through its owner with expected revision and effective time. Neither changes legal Employment/OrgUnit or creates permission. Each selected existing task is transferred independently through WA1.6; a plan shows truthful per-task outcomes and never claims a multi-Company atomic success. A fixed selection does not capture newly created tasks; temporary/permanent future-task coverage is explicit in the separate relation.
Return ends temporary coverage for NEW work at its governed effective time. Already transferred ACTIVE tasks stay with their current assignee until completion or an explicit guarded return/transfer, within their existing assignment validity. Returning does not steal a colleague's started/sealed work. Temporary assignments are not silently extended: reaching their validity limit prevents new human effects; reconcile outstanding outcomes, then renew through the same current eligibility/assignment action or transfer safely. Automated renewal is allowed only inside the already authorized plan's interval and scope; otherwise require an authorized new plan. No automatic approval inheritance.
A planned handback may automatically transfer EDITABLE/no-effect tasks to the original worker if the exact plan permits it and they remain currently feasible; it creates a new epoch. If no longer feasible, keep a truthful paused/assigned state as permitted by validity and open exception. Multiple sequential delegations retain original/current attribution without nested permission inheritance. A→B→A always has new assignment/custody epoch; A's first tab never regains authority. Permanent change and temporary return race via responsibility revision/task epochs; later stale plans cannot pull tasks back to the previous worker.

WA1.8 Drafts, decisions and outcome-unknown handover
Eligibility requires the mandatory field/read/review set for the exact atomic task, not all information on the entity. A preparer may edit one explicitly separate input unit; a decider must see the evidence their decision contract requires. Preserve linked inputs the successor cannot see; never clear them on a partial patch. Hidden optional links use nondisclosing placeholders only when link existence itself is allowed. Required hidden evidence makes this candidate ineligible for that decision, with an authorized exception route.
On transfer, workflow enumerates the complete work-bound draft slot set under the task guard. Definition supplies a bounded maximum (pilot32 slots/task); over-bound means definition/configuration exception, never first32-only handover. New slot creation, draft save/seal/discard/restore and task changes use the same assignment guard. All EDITABLE drafts keep object IDs/revisions/creator history and obtain new custody/editing epochs through the common owner in the transaction. Sealed payloads are not edited. Account-private drafts are excluded; work assignment, departure and administrator request do not authorize copying them.
Attempt outcomes: SUCCEEDED -> preserve original actor/decision/receipt and continue from the actual domain result; no resubmission. READY proven under the common owner fence -> terminal CANCELLED_NO_EFFECT and new editable successor intent, with a new recipient-authored seal/command later. Terminal no-effect -> authorized reuse of saved permitted inputs, never resurrect old command. Running lock or inaccessible/uncertain outcome -> RECONCILIATION_REQUIRED and retain old charge/attribution, no new recipient business effect. Assignment may be PAUSED only once the owner can safely record that state; the current eligibility/source guard already blocks new stale effects meanwhile. An empty mirrored receipt is not proof of rollback.
Already admitted transactions may commit before an absence/revocation fence wins; the result remains historical. After the fence commits, no newly admitted task effect may use old eligibility. Definitive outcome is established by participating owner locks, attempt/receipt and domain state, not elapsed time. Completed approvals remain with the original verified human and exact approved inputs. Transfer never changes submitter/decider or bypasses natural-person separation. A workflow finalize-author step cannot be completed by merely replacing initiated_by: use an explicitly authorized owner continuation/successor that preserves original business decision; if the existing task definition has no such continuation, show an unsupported transfer exception until that specific owner contract is admitted.

WA1.9 Group operation fences and manual recovery
An enrolled Group-prepared child is immutable from Company preparation commit even before ACK under GO1. Automatic assignment authority alone does not grant Group cancellation. On affected unresolved/READY Group work, emit HANDOVER_REQUIRES_GROUP_STOP. If a preauthorized routing mandate explicitly includes stopping that exact operation scope, workload may invoke the bounded control action; otherwise request action from a currently authorized controller. Preserve unaffected data and explain only the currently permitted affected scope. Do not silently stop other Company's work because a local supervisor can reassign one task.
Stop happens in a separate control transaction: AI1 caller/workload control guards -> parent EXCLUSIVE -> STOPPED/control epoch and receipt -> commit; it does not hold Company assignment/attempt/domain locks. Then process each target Company separately under WA1.6 (assignment before parent SHARE before attempt) and require parent STOPPED plus owner-confirmed no-effect cleanup for that child. Already executing children held parent SHARE and must finish before STOPPED commits. A lost preparation ACK does not weaken the fence; exact frozen slot/Company receipt identifies the prepared child. Unknown Company states stay unresolved; parent stop alone is not cancellation proof.
Deadlock trace: executor holds earlier assignment then parent SHARE then attempt/domain; stopper waits at parent EXCLUSIVE without holding assignment/child; executor completes, stopper commits; handover then takes assignment→parent SHARE(STOPPED)→attempt. Forbidden trace: handover holds task/attempt and asks another connection to stop parent. Assignment code must roll back/release locks before calling the stop action. A revoked Group control right means no stop; work remains paused/exception until an authorized controller resolves it. No title fallback.
After cleanup, transfer editable work to currently eligible successor and let that human explicitly inspect/seal a new command. For Group execution create a successor operation over the explicit affected subset under GO1; other successful children remain historical with their own receipt. Do not combine different actor/payload generations into old operation success. Same original Account may use GO1's explicit session renewal for unchanged pending intent; different Account needs successor intent. All manual select/transfer/retry paths use the same guards and exact command bindings as automation.

WA1.10 Input paths, disclosure and everyday experience
Normal user: submit the typed absence/leave event through its owning form; relevant work is already linked to duties/tasks. The result shows coverage status for authorized tasks, saved progress and exceptions; finding a substitute is not a required leave field. Workload routes feasible work and the recipient's '내 업무' shows the next step, due time, relevant permitted objects, the needed saved input and surfaced decision notes. A delivery acknowledgement/read marker is not task acceptance or business completion.
