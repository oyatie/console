MP1.2 Migration and rollback invariants
Inventory every wage/line/calculation reader, direct/Action/background writer and source guard before activation. Run resumable bounded backfill with stable high-water key and counts; each batch idempotent, writes append-only mappings and checks original row hash/identity. Unmapped Account attribution, missing source guard or bad legacy provenance blocks only the affected enrollment; never manufacture a fake employee or silently discard a line.
Compatibility sequence: expand -> backfill/validate -> all correction-aware readers and guarded adapters deployed -> prove old write paths rejected for enrolled targets -> server-owned enrollment. Old binary must either refuse enrolled data or use corrected reads; disabling the new button is insufficient. After first correction/Account-only/task-transfer record, rollback uses a known compatible binary with new writes paused or forward repair. Preserve heads/history/receipt/dispute/unknown pins. Do not drop tables or reset head revisions to make old code accept data.
Restore one consistent DB point, then apply candidate06 independent erasure/recovery journal and current policy/identity/membership/source guards before readmission. Unknown effects stay quarantined/charged until reconciliation. These are required future proofs, not evidence of an actual restore drill.

MP1.4 Bounded performance decision
Retain existing single-Company atomic calculation for first implementation. Do not introduce chunked durable arithmetic or a new queue engine without measured failure of that boundary. Replace per-line source lookups with bounded set-oriented source/manifest reads inside the same owner contract where possible, and validate allocations/body bounds. This is a design recommendation, not a completed optimization.
Pilot fixture has exactly6Companies/2,000 people total: skew1800+40+40+40+40+40 and balanced334+334+333+333+333+333. Test normal and blocked units, no hidden totals, and unrelated interactive requests. Retain GO1 max2Company executions/Group,1perCompany,30s statement/execution cap,60s claim lease/20s heartbeat as provisional harness bounds. The300s whole-Group target includes queueing/reconciliation and does not enlarge a Company's transaction budget. These values are not logically contradictory, but compatibility and capacity are unmeasured. Lease expiry/30s timeout never proves rollback; same child fence and receipt determine outcome.
Measure per-run input-resolution/lock-wait/kernel/persist/commit duration, rows/query count, memory and interactive latency, with versions and dataset digest. Benchmark harness records DB/runtime/hardware resources before comparison; current evidence does not select a deployment VM or promise SLA. If1800unit Company cannot satisfy30s after bounded data access, stop enrollment and return to reviewed design: (a) change validated deadline/lease/resource budget, or(b) immutable staged calculation with an atomic current-head publish and explicit cancellation fence. Do not silently split a receipt or increase timeouts. Numeric oracle, correctness and policy isolation remain unchanged in either option. The complete per-request/UI/perf acceptance thresholds and deployment resource envelope are W04b/PILOT pending.
