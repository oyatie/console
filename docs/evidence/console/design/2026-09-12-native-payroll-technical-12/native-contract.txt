NP1 — Native payroll input and calculation technical contract (proposed W04a)

NP1.1 Facts and responsible ownership
At product05200, payroll/adapter-postgres owns employee_contract_wages and payroll_draft_runs/lines/calculations. payslip_draft::contract_wage_in_force_in_tx selects the greatest base effective_from <= pay_date; REST get_payslip_draft calls the pure insurance kernel without writing a run. roster::materialise_roster_in_tx now exists: old comments saying no production roster writer are stale. lifecycle::calculate_run_in_tx still derives gross/tax from data_import_rows and checks text VERIFIED_SOURCE_ROW. Existing native wage entry therefore is not a native run input path.
Keep console-payroll-domain the only arithmetic owner and payroll/adapter-postgres the only payroll SQL writer. Extend its payslip_draft.rs, roster.rs, lifecycle.rs and pay_run.rs; introduce focused inputs.rs and source_evidence.rs modules in the same adapter when implemented. There is no existing payroll application crate. A new crate is not required merely to share a command between REST and canonical Action. Pure eligibility/arithmetic rules belong in payroll/domain; wire DTOs belong in console-contracts; database-dependent preparation/guard/receipt orchestration belongs in the payroll adapter. Leptos UI consumes filtered contracts and never reaches SQL or an adapter.
No fake import record, duplicated wage ledger, alternate Foundry payroll calculator, or new LLM classifier. Native and imported evidence resolve into the same immutable typed input manifest; old imported calculations retain LEGACY_IMPORT lineage until explicit preparation. General objects/actions/drafts remain shared engine concerns; native payroll facts are domain-owned projections, not JSON owned by an arbitrary generic instance mutation.

NP1.2 Identity, period and canonical scalar decisions
Company is the sole org_id/RLS cell. Request scope is resolved from authenticated server context; body Company/reference must match it. Account/CompanyActor attribution follows AI1; employment is an operand, not permission. Group may select Company operations but cannot arm app.current_org or become employer.
DraftRunId is the existing payroll_draft_runs.id; caller correlation_run_id is distinct. New native run gets server source_label native:<correlation UUID>; the natural key and owner command receipt prevent duplicate creates. A successor has a new correlation/source_label and an explicit predecessor relation through AC1. Do not reuse a caller correlation UUID as an existing business run ID.
Period wire stays inclusive YYYY-MM-DD start/end. Initial profile accepts one full calendar month. Internal temporal intersections use [period_start, next_month_start). pay_date remains a separate explicit date, defaulted and shown before sealing. Do not silently replace historical pay_date or select wage solely at pay_date. Native profile requires the same effective wage throughout the month AND on pay_date; a new wage inserted in either relevant span invalidates eligibility. Employment need cover the earning month, not continue until pay_date; a full-month worker may be paid after exit. Account survival and historical result entitlement do not depend on this narrow calculation eligibility.
KR_MONTHLY_FULL_V1 fixes earning-calendar timezone to Asia/Seoul. Convert inclusive Date bounds to local midnight instants [start00:00, next-month00:00) in that zone before comparing Employment TIMESTAMPTZ; never use server/browser timezone or UTC midnight by assumption. Record the zone and rule identity in the manifest. A changed zone requires a new profile/input revision. Wage identity must remain the same throughout [period_start, max(next_month_start, pay_date+1day)); a newly effective base in that span requires supported-profile reassessment even if its displayed amount happens to match.
UUIDs are canonical lower-case hyphenated values, never nil. All new wire won values use canonical decimal strings (no exponent, plus sign, leading zeros except 0, fraction, separators or whitespace); server parses checked i64. Revisions/epochs use decimal strings parsed to positive i64; initial absent head uses explicit null, not a fabricated row. Amounts and revisions never round through JavaScript Number. Hours is a bounded integer1..400; timestamps RFC3339 UTC, temporal comparisons on parsed instants, dates on parsed Date. Old numeric wire fields keep their existing contract; conversion is explicit at the compatibility adapter.

NP1.3 Supported profile is a typed, versioned rule object
Profile key KR_MONTHLY_FULL_V1 references exact kernel source/build and approved rule-source identities. It is a calculation coverage declaration, not a universal legal status or hardcoded occupation. The positive case requires: exactly one Employment covering the whole earning month; one MONTHLY contract wage across the required intervals; immutable approved applicability/basis facts; complete owner-derived attendance and a valid covering close; no prorated earning, overtime/night/holiday premium, unpaid reduction, retro adjustment, competing Employment or unknown obligation; explicit pension basis; exact admitted and verified tax selection. Unknown applicability is not zero or true. A worker can have access and submit a request even if this calculation profile cannot calculate them.
Native preparation receives a versioned scope_basis_ref, not a caller-filtered employee list. The payroll owner derives the required population from that authorized scope selection (Company/site/department with explicit descendant semantics), effective facts and the source-scope generation. It includes undiscoverable employees and records typed exclusions/unsupported cases. A scoped run is labeled as that scope, never all-Company completion. Visible employee refs in a preview are only witnesses, not the population authority. NP1 prepare resolves the entire selected scope; narrower work requires an independently authorized versioned scope, not deleting hidden rows from the payload. PC1 common obligations and current REGULAR coverage reservations remain required: reserve the full derived population atomically, detect overlapping periods/runs and transfer predecessor reservations only through AC1; legacy overlap ambiguity blocks enrollment.
Represent each required employee as PopulationSlot(input_revision, employee_id, employment_resolution). Resolution is tagged Resolved(exact Employment revision) or Blocked(typed code, immutable candidate-ref/absence-scope evidence). A missing/multiple/non-full-period Employment has a Blocked slot; preserve candidate history without choosing or fabricating one qualifying Employment. Candidate refs remain internal evidence and are separately disclosure-filtered. Only Resolved slots that pass all other source/profile checks yield a CalculationUnit with exactly one Employment and PC1 coverage key. Any required Blocked slot prevents complete calculation/review coverage. Never sum multiple employments or silently pick the first. Organizational selection and required membership are frozen with the input revision, not rerun as a mutable department query at calculation.
Eligibility facts bind Company/Employment, earning interval, pay_date applicability, exact pension_standard_monthly_income_won, insurance coverage for each computed deduction, taxable basis and its definition, no-adjustment evidence, working-calendar revision and source/evidence references. They are an immutable payroll-owned assessment created by a separately authorized typed action, with current source references and independent verification required before use. A client checkbox alone cannot assert absence of overtime or statutory coverage. Derived attendance comes from current owning attendance/calendar facts; missing attestable coverage blocks the unit. Assessment revocation/supersession is append-only. Its full physical action/storage contract is a W04b source-owner dependency; do not claim a positive production workflow until that dependency is implemented and proved.
The pure LineCalculationInput is arithmetic input, not proof of eligibility. Its internal insurance call passes hours=None, missing pension basis defaults to gross, and it does not carry insurance-applicability switches. Native caller must therefore pass explicit basis and check the profile, including the existing minimum-wage comparator with declared hours, before calculation. A comparator failure is this profile's blocker with evidence, not a newly asserted legal conclusion. Nonnegative tax and checked arithmetic are required; net<0 is a typed UNSUPPORTED_NEGATIVE_NET blocker in this profile, not clamped to zero. Other profiles may later model receivables/adjustments separately.

NP1.4 Wage correction and temporal source changes
A genuinely new effective date uses the existing append-only employee_contract_wages base row. Same-date correction uses an append-only chain (base_wage_id, correction_revision, predecessor_revision) plus a current-head CAS. Base identity, Company, employee and effective_from cannot change in that correction. New amount/kind/hours and relied-on evidence/reason form an immutable revision; source_note retains its500-character bound. A correction is not a fictional raise on the following day.
The one resolver returns WageFactRef(base_wage_id, correction_revision=0 for base) and values. Both insurance-only payslip-draft and native preparation must call it. Effective selection tests all relevant base dates; correction overlay changes values at the same original date. Before enabling correction writes, update every wage reader and prove old/base-only paths cannot be served. Existing ON CONFLICT/append-only triggers remain; never UPDATE original wage rows. Reject stale predecessor without writes. Same command+payload recovers exact receipt.
Relevant-source freshness must detect insertion, deletion where lawful, and newly effective/superseding rows, not just changes to selected IDs. Proposed enrollment requirement: each relied-on source owner participates in a monotonically versioned source-scope guard for Company/subject/period (or a coarser safe scope). Every relevant write obtains that scope's EXCLUSIVE guard and increments its generation in the SAME write transaction. Prepare/close/calculate/review read SHARE guards then re-resolve all facts, including absence predicates. Do not generate those versions only in a background job or trust an outer preview timestamp. Exact guard table/key range and complete writer enrollment inventory are W04b blocking work; affected native commands stay disabled until it exists.

NP1.5 Tax evidence admission, verification and revocation
Use payroll source-evidence owner actions, not nts_tax_row_status text or request verified=true. Admission stores an immutable artifact reference+content hash, approved source/rule reference, table version, exact row locator, source units, date applicability, exact income band/definition, household/dependent/withholding selection, Company/employee/Employment/earning period/pay_date, exact income/local tax amounts and relied-on evidence. URL alone is not custody. Typed row-selection facts belong in the manifest and must match normalized input.
Verification is a separate deliberate action by a different verified natural person from admission, under current exact scope/field authority. It binds the complete admission digest and approved source reference; unknown/missing/revoked source qualification refuses verification. Revocation is an append-only owner action; it is not erasure of prior calculations. Correction admits a new immutable evidence row; never mutates the verified row's amounts or subject. Governed source qualification proves custody/version and a qualified-review artifact, and does not itself grant legal compliance authority.
Preflight and execute recheck verification, validity, revocation and applicability on prepare, close, calculate and PC1 progression. Imported VERIFIED_SOURCE_ROW cannot satisfy this contract. Tax evidence for a3m income band cannot be reused after a3.4m wage correction; a newly matching row and verification are required.
Synthetic fixture sources are provisioned only by disposable test-harness composition, before requests, with explicit NONPRODUCTION_FIXTURE classification. There is no request/query/tenant flag enabling them, and tenant production source qualification must reject them. The normal admit/verify/prepare/calculate actions must still be exercised; raw fixture INSERT of a verified boolean is not the positive test. Artifact storage/custody and source-qualification owner APIs are W04b dependencies, not permission to fabricate qualification.

NP1.6 Immutable manifests and persistence
Proposed payroll_input_revisions key(org_id,run_id,input_revision) includes schema/profile/kernel identities, inclusive period, pay_date, complete selected membership, ordered typed source refs, normalized inputs, blockers, actor attribution and manifest digest. payroll_input_units key(org_id,run_id,input_revision,employee_id) stores the PopulationSlot tagged resolution and slot digest. A Resolved slot has exactly one same-Company Employment revision; a Blocked slot stores typed candidate/absence evidence with no fabricated qualifying ref. A calculation row can reference only a Resolved eligible slot; SQL checks/FKs or equivalent owner constraints must enforce that distinction. The manifest includes scope_basis_ref and frozen owner-derived membership/effective-query proof, including all blocked slots. payroll_input_source_refs bind relied-on facts/absence-scope generations and evidence digests. Entries are immutable; monetary typed columns use BIGINT. Extensible annotations may be JSON but cannot replace required typed fields or become executable meaning.
Prepare acquires the complete protocol lock set, verifies expected run/input heads, resolves sources and writes one complete input revision with active membership; advances head and audit/receipt atomically. NP1 create must separate header allocation from legacy stage_draft_run_inner import-roster materialization: do not call the legacy materializer on new native header or replay. It starts without copied import lines and receives active membership only via explicit prepare. Existing import staging callers keep their existing owned branch and regression tests. No import rows are created. Preparation can preserve a blocked unit; it cannot make an empty roster closeable. A new run starts with protocol_version=NP1, current_input_revision=null and run_revision=1; every accepted run-changing command advances run_revision once. Replay does not advance it. A wage or evidence source change does not rewrite a run revision behind the user's back: current-source validity changes and explicit prepare/revise creates the successor snapshot.
Keep existing payroll_draft_lines as stable per-run employee identity/readiness projections, with UNIQUE Company/run/employee. Their mutable status is not historical calculation input. payroll_line_calculations remains the arithmetic-result owner; extend it with exact input_revision/unit_digest and use a monotonic per-run calculation revision allocated under run lock, including all-blocked runs. Add an immutable calculation-batch header with selected membership/counts/outcome so MAX(existing success rows) is not the only version allocator. Foreign keys include Company/run/input/employee or equivalent proven composite references. A calculation cannot point to another Company's or another run's line. Old rows retain LEGACY_INPUT_UNKNOWN rather than invented input provenance.
Calculation uses only the manifest's normalized facts plus current validity checks. It must never query import gross for an NP1 unit. It writes all successful results and typed per-unit blockers in one Company transaction plus batch/current-head/receipt; payable remains false and runtime cannot flip it. Unresolved rounding is a blocked unit, not a retryable infrastructure error. Partial results expose only authorized scope totals and never a whole-run total. An all-blocked completed calculation still has a durable batch receipt and actionable blockers.

NP1.7 Lifecycle integration, preserving later reviewed contracts
New native preparation is STAGED/BLOCKED_LEGAL_GATE/READY_FOR_REVIEW -> STAGED; close requires exact current prepared input, nonempty complete attendance and owner period-close proof -> ATTENDANCE_CLOSED. Calculate only exact closed current inputs -> CALCULATED. Reprepare a calculated or closed run requires explicit reopen_inputs with reason/expected revisions; reopen invalidates active close/calculation pointers while retaining history, and does not globally unlock the period. Reclose rechecks evidence even when reusing a still-valid period lock.
PC1 supersedes candidate02's single SUBMITTED review path for enrolled runs. CALCULATED -> explicit open_review_cycle -> REVIEWING with Unit/Common proposals. Do not map submit_run blindly onto global approval or skip proposal submission. During REVIEWING, committed source correction feeds revise_review_cycle with affected proposal CAS and selective recalculation; unaffected approvals survive only full dependency equality. Generic reopen_inputs is forbidden while REVIEWING; explicit cancel_review_cycle is its guarded preparation return. Last-decision completion races share the same run fence; once APPROVED, source correction requires AC1 successor, not ordinary reopen/revise. Approved predecessor may have revoked sources: creating its safe successor must not require those old sources to become valid again.
Exception generation is revision-bound. Existing unique live exception(run,line,kind) and broad HELD carry-forward are not proof of current coverage; new calculation references exact exception revision and status. Supporting new NP1 exception kinds requires explicit owner schema expansion and readers, not reusing an unrelated kind or confirming a blocker to create money. Restoring a form draft is input only; source corrections, reopened inputs and recalculation each require an explicit governed action and receipt.

NP1.8 Scope and closure
This packet settles proposed native owner, normalization, source-evidence semantics, temporal/correction, calculator boundary and positive arithmetic expectations. It does not complete W04 physical identity/Cedar/source-guard/draft/workflow/publication SQL/ACL, the full37-command transport surface, real migrations or executable tests. Those dependencies remain explicit in remaining-work.csv. No production legality, payable issuance or full HR profile coverage is inferred.
