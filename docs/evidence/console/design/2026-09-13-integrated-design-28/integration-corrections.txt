IC28 — Integrated review corrections and constructive paths
This specification supersedes contradictory28 descriptions and the explicitly listed inherited projections below. Historical evidence is preserved. It does not approve this design or alter current authority.

1. Gate construction, no future dependency
ReviewDecide contains business request/basis/decision/reason only. Its optional execution gate lives outside that business body. REQUEST_GATE accepts editable draft identity/revision/editing epoch and the selected gate policy/evidence/validity. In one Company transaction the common seal owner reserves the actual governance request UUID, registers its immutable EXECUTION_GATE purpose, seals the business attempt with that request identity in the envelope, computes its unchanged fingerprint, then fills the request binding with that exact attempt/command/fingerprint. The request UUID has no digest of a future decision; its initial payload revision is fixed. Deferred constraints forbid committing an unbound request or an unbound sealed attempt. A distinct gate-request command receipt reports this request and the sealed attempt. DraftSeal with gate_request_intent delegates this same owning protocol rather than creating a second request.
Positive path: D edits ReviewDecide -> REQUEST_GATE seals C with stable request G -> independent permitted human decides G against C -> D explicitly executes C -> executor loads GateExpectation from G and verifies current policy, decision validity, exact command and unused consumption -> business decision plus consumption/receipt commit once. Hash(C) before gate decision equals Hash(C) at execute. Gate approval does not execute C. Gate refusal leaves C unexecuted; cancel through conclusive receipt-first path. A newly mandatory/different gate after sealing blocks C; cancel/reseal new intent, never insert a future gate or decision digest into C. Source24 preparation/seal ordering and25 one-way adoption remain unchanged.

2. Scoped review and public/internal boundaries
ReviewBasis exposes Company, basis identity/revision/digest, obligation and permitted evidence contract; no cycle membership digest or global cycle revision. ReviewSubmit/Decide/Withdraw/Revise operate on those exact bases. The payroll owner resolves cycle membership and unchanged-basis applicability internally as04. An unrelated hidden unit correction cannot invalidate an unchanged basis solely because the global cycle head advanced. Whole-cycle cancellation and completion still require their separate broad authority. ReviewResult is INTERNAL and can contain global cycle/Completion; it is not a public response.
All *Result owner structs, internal receipt payloads, PreparedNative* and retained witnesses are internal. Public action responses use PublicOutcome and AuthorizedScreen; only currently permitted fields/links/actions populate AuthorizedObjectView. Global counts, membership digests, hidden result refs and Completion are absent unless independently authorized. Public partial Group progress includes individually permitted Company child outcomes with no hidden child placeholders, global counts or percentages. A scoped reviewer can receive their basis card and submit/decide without receiving the global cycle. AuthorizedObjectView.snapshot_revision is a random256-bit server-stored projection handle, never the whole object's revision counter.
CONTROL_REFERENCE is a random256-bit handle for an exact server-owned typed reference the form may use without disclosing its internal bytes, for example a Group control expectation. Handle storage binds Account, session/context generations, Company or Group, action/field/schema identity, exact private reference, and expiry; fixed lifetime15minutes refreshed only by a fresh authorized render. Possessing it grants no read or execute authority. Resolve before complete typed validation and fingerprinting; receipts seal exact private refs, never expiring browser handles. Client cannot edit server-owned expectation fields. Existing public scoped basis refs stay scoped; opaque handles do not restore global equality as their validity condition. Expired/stale handles preserve visible input and request fresh validation. ErrorProjection addresses field_id plus stable parent_item_ids; forbidden error locations are omitted. No private Result derives public serialization.

3. Native preparation has an owning producer
The existing POST payroll.prepare_inputs takes NativePrepare: staged run expectation, versioned scope/profile, membership expectation and bounded source/evidence witnesses. The trusted payroll owner derives COMPLETE population from authoritative scope and source selection; supplied refs cannot filter hidden employees. Public payload is a request, not an internal manifest. payroll.calculate_run similarly takes RunCalculate and derives its prepared calculation from the actual complete sealed input. No new user preparation action or alternate payroll writer is introduced.
Each command first reserves its original Company command ID/fingerprint under receipt-first admission and creates an owner-private native_preparations row and append-only preparation event. That committed BUILDING record is a preparation effect, not an activated payroll input, monetary batch or terminal business success. Its preparation event namespace is distinct from the final command receipt. The same command returns PENDING with ReconciliationSubject.COMPANY_COMMAND (or its existing attempt), not UNKNOWN while known active. A fixed payroll worker consumes that owner row; it cannot change Account attribution, sealed body or source/profile selection. Stage membership outside final transaction in bounded chunks under exact immutable preparation plan; every chunk has stable ordinal and receipt, is protected, and retrying a chunk cannot duplicate members. Native unit/build bounds from18/26 and CP28 apply; BUILDING never means current input.
On complete staging, record SEALED exact manifest digest. The native owner finalizer loads that manifest by command-bound preparation ID and checks exact fingerprint/build/header/member/source fences under current authority, then activates whole input or whole calculation batch, creates all result/custody memberships, consumes any gate, finishes the same original attempt and appends the final business receipt in one Company transaction. It is never a second user command adopting another person's prepared results. Worker runs only with currently admitted dispatch identity and original session/work/Account context; expired authority blocks new activation and exposes repair, not autonomous impersonation. Stale sources conclude no business effect after definitive finalizer reconciliation; a new explicit intent is required to recompute a changed basis. Incomplete staging cannot be silently truncated to fit.
Recovery uses original command receipt then preparation state; response loss returns UNKNOWN only when outcome is not known. Cancellation serializes with activation on original command/preparation state: terminal business receipt wins, otherwise cancel prevents any later activation and appends CANCELLED preparation event. Active/unknown retained dependencies stay pinned until conclusive cancellation and retention evaluation; do not pretend preparation never existed. BUILDING/SEALED/ACTIVATED/CANCELLED are preparation states, separate from actual STAGED/ATTENDANCE_CLOSED/etc run states.

4. Constructible nested editor and coupled validation
CREATE_CONTAINER is an editor operation, not a NULL business value. For a registered singular RECORD/LIST field item_id and after_item_id must be null. For a RECORD/LIST item in a registered repeated field, item_id is a fresh stable UUID and after_item_id is null or an existing sibling. container_kind must equal the compiled schema node; each child starts Unset. Parent path resolves exact registered fields/items at depth<=8. INSERT_ITEM remains for scalar items. Removing a container removes its draft subtree only; receipts retain prior revision. No arbitrary field/path can be created.
Calendar example: CREATE_CONTAINER(duties,new item D,RECORD); SET weekday at [D]; SET start/end at [D]; CREATE_CONTAINER breaks LIST at [D]; CREATE_CONTAINER break record B at [D]; SET start/end at [D,B]. Exact field registry determines each source19 path. Case example: CREATE_CONTAINER issues record I; SET I's registered issue enum and source reference; SET narrative; CREATE_CONTAINER/INSERT_ITEM evidence using its admitted element schema. Required members may be Unset in editable revisions; complete submission rejects every unresolved container/value. An atomic save containing coupled start/end patches validates the coupled result, not an invalid intermediate patch order. Per-row errors carry [D,B] or [I], so two equal field IDs do not collide. Read authority is checked before diff/error projection; unauthorized child values never return through an invalid-patch echo.

5. Unknown direct and Group commands
ResultObservation.UNKNOWN holds ReconciliationSubject: COMPANY_COMMAND(org_id,command_id), GROUP_COMMAND(group_id,command_id), or existing ATTEMPT. A lost Group-create response requires neither operation ID nor fabricated FD1 attempt. SafeRepair.RECONCILE reads the corresponding owner receipt/status route with current Account/context and original-command visibility. Company receipt lookup uses Company connection; Group lookup uses Group owner and never arms app.current_org. Stable read routes are /api/v1/commands/{command_id} in bound Company context, /api/v1/groups/{group_id}/commands/{command_id}, and existing attempt detail in bound Company context. Reconciliation never creates new effect, new command ID or retries under a new actor. Group PREPARING receipt stores GroupActionRef and GroupControlResultRef; child action/receipts remain Company typed. Internal GroupResult means committed success only; UNKNOWN/PENDING use observations outside it.

6. Publication size and manual correction fallback
Retain the accepted one-Company, up-to2,000-selected-subject atomic publication. PublicationRelease.targets and internal PublicationResult explicitly permit2,000; the usual256 array limit does not apply to these two fields. The command/draft sealed body has an explicit8MiB encoded cap and2,000 target bound; ordinary patch requests remain64KiB/256 and can accumulate a2,000-target draft over acknowledged saves. No per-subject partial commit and no assumption that UI can authorize hidden subjects by selecting all. Current registered broad publication authority and complete exact target validation are mandatory. Public outcome is paged AuthorizedScreen, at most256 permitted objects per page, with no unpermitted counts. If measured atomic2,000-person publication cannot meet the required envelope, revisit design before implementation acceptance; do not silently split it.
OUTSIDE_SUPPORTED_PROCESS carries subject-readable explanation content, accountable follow_up_task and exact owning_process reference. It leaves the issue unresolved and case pending. Unsupported overtime, paid/issued or off-profile corrections cannot be marked CORRECTED by creating a task. If no eligible assignee exists, preserve the task as visible UNASSIGNED exception under common routing; the requesting subject can see permitted pending/explanation status. Actual owner follow-up and eventual resolution evidence are required.

ObjectRef.object_id resolves by registered object_type_id to the domain-owned projected ID or common instance ID. CREATE allocates real object ID once and carries an exact permitted scope_ref. The action registration maps type UUID to canonical14 object_kind; normalized CCF1 target uses Create/object_kind/allocated_object_id/scope_ref or existing exact target according to14. Company equality is checked across every nested reference. Never replace a canonical ID with a generated common instance ID. Historic14 vectors remain exact byte-format witnesses, not evidence that a changed action body retains its old semantic fingerprint.
WageCreate preserves12 employee target and historical Employment correlation: effective_from, wage_kind, amount_won, monthly_standard_hours integer1..400, source_note<=500, evidence_refs and expected subject_source_generation. Employee and Employment in28 are explicit target/correlation witnesses checked equal to the enrolled owner; they do not alter wage arithmetic. HOURLY storage is valid but NP1 calculation remains unsupported. No ordinary_weekly_hours substitution.
NATIVE_CALCULATION_UNIT identity is NativeBatchRef plus employee_id. Successful monetary ResultRef is separately correlated through18 outcome; BLOCKED has no monetary result and still has complete retained unit identity. Entirely blocked batches can therefore be retained without fabricated money or IDs.

Persistent Account survives employment end. Former-worker historical own publication/case access is in this vertical. 10. Complete readback and Group control projection
ProjectedFieldNode identifies registered field_id, stable parent_item_ids, optional current item_id and previous_visible_item_id. Its closed state distinguishes VALUE, UNSET, INCOMPLETE exact preserved editor text, and RECORD/LIST CONTAINER, including empty containers. AuthorizedDraftView binds exact draft/revision/schema and optional current editing token; it supplies ProjectedFields(nodes<=256,continuation). HistoryEntry and AuthorizedObjectView reuse this representation. A page may include permitted ancestor containers needed to interpret child paths; identity deduplicates them on the client. No global ordinal/count or hidden sibling ID is emitted. If parent existence is denied, omit descendants rather than leaking the parent path. Read-only historical views have no editing token and no state-changing action.
Continuation is opaque server-held projection state bound to exact immutable revision or result snapshot, Account, context/policy generations, permitted query and last visible position. Each page reauthorizes. Authority change invalidates remaining cursor and requests a fresh projection; it never resumes under old disclosure. Within unchanged authority, traverse every permitted node/subject exactly once apart from repeated ancestor context, preserving order and incomplete text. AuthorizedScreen.continuation pages top-level object/Group results; ProjectedFields.continuation pages nodes inside a specific object/draft. Neither is permission, an exposed global total, nor a request to materialize all hidden objects. This closes calendar D1/D2 and break readback and2,000-publication result browsing.
AuthorizedScreen.groups uses Group-native AuthorizedGroupView. GroupViewRef is Group+operation UUID without private epochs/digest. GroupControlAction carries exact GroupActionRef, optional operation identity and opaque action-bound expectation; the Group owner resolves private control refs and revalidates current policy. Group root create has null operation; PREPARING create response renders the actual operation card and independently permitted activate/stop controls. Active operation can show authorized resume/stop. SafeRepair OPEN_GROUP_OPERATION/OPEN_GROUP_ACTION uses the Group route, never Company ObjectRef or app.current_org. Company child results remain individually projected Company objects; hidden children do not leak through totals or blank slots.

11. Exact size exception and generic retained intent
FieldDefinition can represent max_items up to2,000 solely so compiled payroll.review.release PublicationRelease.targets can register its accepted2,000 bound; fixed registry admission rejects any unrelated field exceeding its previous256/narrower bound. The exception covers exact registered accumulated draft body, sealed command body and OWNER_SUBMISSION snapshot storage/codec at8MiB; ordinary patches remain64KiB and256 operations, and source24 stays64KiB unchanged. Common row storage validates its exact action/schema-specific byte cap, not an unconditional64KiB cap inherited from source commands. No8MiB object can pass a source24 decoder. UI results remain bounded pages. All retained-byte/expansion budgets still count the full snapshot, including larger publication intent; a cap failure preserves input and never partially publishes.
The common owner publishes non-source sealed input through common.publish_owner_submission; its final EvidenceRef identifies actual immutable OWNER_SUBMISSION unit/bytes/hash, not SourcePayloadRef24. SOURCE_SUBMISSION retains its exact24 format and source-effect binding. Native/common result adoption accepts exact final EvidenceRef and verifies origin command/retention/correlation without requiring a source ordinal. Only source effects require25 reciprocal slot1. This is shared common custody with a closed source specialization, not separate competing domain writers.
