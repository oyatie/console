UX1.3 What a work screen must surface
Every screen answers: what is this work; what is already known; what needs my action; what happens after it; what prevents it now. Relevant source objects, current-versus-proposed values, meaningful comparable history, due/assignment state and unresolved case narratives appear near the action requiring them. Information indispensable to a decision is in the primary review path, with concise summaries and immediately available detail. Collapsing lengthy secondary history is allowed; hiding a mandatory warning/evidence requirement behind an unopened tab is not.
Use task checklist/progress patterns to show actual satisfied prerequisites and remaining actions, not decorative progress percentages. Filled states derive from owner facts, not client clicks/read markers. Defaults use existing Company/Employment/contract/source/time references and domain rules; user corrects a typed control instead of describing a relationship in prose. Field types, units and evidence provenance are visible where needed to avoid ambiguity, while technical command IDs/schema hashes stay in authorized diagnostic detail rather than routine inputs.
Human decisions preserve necessary information density: keyboard-friendly tables and focused detail, stable row identity, pinned scope/period summary, explicit partial-coverage labels and source differences. A decision over hidden evidence stays blocked for that actor; expose the authorized path to the exact task/eligible handler. No blanket 'approve all' over undisclosed items. '내 검토 완료', '선택 범위 계산 완료', '급여안 승인', '본인 검토본 공개' and '지급 완료' are distinct; payment/issuance remain out of this slice.
Primary action follows current owner state and capability. Unknown/denied actions are omitted if their existence is confidential. A known permitted action blocked by incomplete inputs may be disabled with a specific inline reason and reachable repair action. Do not show every possible action to every user or turn all errors into '관리자에게 문의'. At least the permitted back/refresh/own request/exception route remains accessible; a configuration/security recovery path exposes only its authorized metadata.

UX1.4 Input stages and commands
Common action surface stages: (a) open/resume typed intent; (b) complete/validate inputs; (c) review exact current effect; (d) confirm/execute; (e) show durable result and next owning action. This is a reusable form/action pattern, not a forced wizard or five user clicks. Small actions fit one form with review context; complex multi-subject commands use explicit scope preview. Opening a screen or GET does not create a business action or mark a task read/completed. Draft creation occurs only on explicit start/edit intention through FD1.
One final deliberate confirmation may authorize the exact reviewed input through FD1 seal then owner execute, provided both stages keep their separate durable states/receipts and the confirmed payload matches the sealed digest. A sealed-but-unexecuted response must never appear submitted. After connection loss or changed authority, first reconcile the same attempt; do not resume a different intent automatically. Where earlier contracts require a later explicit gesture (e.g. D after optional gate approval, GO1 same-Account session renewal), retain that gesture. Approval does not silently launch the human decision.
Every command binds server-derived actor, Company/resource, permitted typed patch/input, expected revision/editing context and stable command/attempt IDs. CSRF/origin/session protections apply to browser mutations; no mutation via GET or querystring. Client validation accelerates feedback, server owner remains authoritative. Submit buttons prevent accidental duplicate gestures but server idempotency is mandatory. An exact response identifies whether a change is saved input, a sealed intent, accepted work, completed business effect, rejected-no-effect or outcome unknown.
Screen-map input schemas describe domain meaning and value sources; they do not allow UI code to reinterpret i64 won as floating point or an end-inclusive pay period as half-open date range. Money uses exact integer/string decimal representation per final wire contract; UI formatting never changes stored units. UTC instants display in known business/user timezone with label at ambiguous boundaries; effective dates stay dates, not browser-timezone conversion. W04 fixes final supported profile and calendar rules before executable tests. Unsupported employment/calculation input has a truthful owner-supported alternative/manual exception path, never silent conversion to monthly employee.

UX1.5 Durable draft, offline and field revocation overlays
All mutable action-input screens use one FD1 draft store and editing context. Overlay states are EDITING_UNSAVED, SAVING, SAVED, OFFLINE_UNACKNOWLEDGED, SEALED_READY, CUSTODY_CHANGED, EXPIRED/INTEGRITY_HOLD; input-overlays.json defines exact transition/controls/focus. These are orthogonal to the business screen matrix. Only ACK of all current local edits means '저장됨'. Keep at most one in-flight save/tab with bounded coalescing and no-op suppression. Loss of server ACK does not imply data loss or durable success; read back exact save receipt/revision before new patch.
Navigation with unsaved input offers stay/save or explicit leave/discard, with the last acknowledged server revision identified. Do not block unrelated browsing forever; a deliberate leave is allowed with truthful loss warning. Private salary/case text is not automatically stored in localStorage/IndexedDB or exported to clipboard. Offline RAM input can survive an in-app pause while still authorized but not a guaranteed crash/reload. Loss of authentication/current field permission or Company/custody context clears managed sensitive props and forbids stale writeback; server may retain protected saved content. Do not promise recovery of unsaved fields after a security-clearing event.
Draft history S06 uses exact permitted revision/schema and keyset paging over retained history; no20-revision cutoff or fallback to live values when old history is unavailable. Restoring selected authorized fields appends a new revision and does not execute a business action, approve work or reveal denied old fields. Dirty local changes must first be saved/reconciled or explicitly discarded before applying restore. Full-chain existence/progress permission governs timeline exposure; authorized pinned versions do not imply visible hidden-version counts. Optional hidden input is preserved by patch semantics; it is not silently nulled.
Handover due to workload, instruction, absence or responsibility change uses WA1/WA2. Old tabs cannot regain authority in A→B→A; assignment and lifecycle epochs matter independently of Account ID. Readable work-bound saved input follows current task custody; Account-private request drafts remain private until submission. The successor sees necessary allowed narrative/evidence and explicitly makes their own business decision; no old actor/gate identity transplantation.

UX1.6 State matrix and error composition
state-matrix.csv has an explicit row for each of16 surfaces in10 review families: LOADING, EMPTY, DENIED, READY, INCOMPLETE, PARTIAL, STALE, FAILED, UNKNOWN, SUCCESS. Fields specify condition, visible information, permitted logical actions, preserved state, return/next focus and proof binding. A row marks NOT_APPLICABLE with an explanation where a view has no mutation outcome; it must not fabricate an action result merely to fill a table. Input overlays and flow traces add dirty/offline/sealed/history/assignment specifics. Counts are inventory coverage, not executed tests or exhaustive product correctness.
Precedence: whole-page/object or identity disclosure denial removes its sensitive content first. Optional-field denial preserves the permitted PARTIAL object view; action-only denial removes/blocks that action without blanking an otherwise permitted page. Mandatory denied decision evidence blocks that decision while keeping other authorized information. Successful read completion resolves to READY usability, retaining actions such as own correction-request entry. A mutation SUCCESS shows its immutable receipt and separately recomputes next actions from CURRENT owner state, never replaying the previous action because a success flag is set; outstanding uncertain effects still exist server-side but are not exposed to an unauthorized observer. If disclosure later returns, reconcile original command/receipt before new action. Among authorized data, UNKNOWN effect inhibits retry-as-new; STALE input blocks old execute; INCOMPLETE required evidence blocks only dependent action; PARTIAL permits only explicitly authorized and actually independent subset work. Read failures never change known business state. Empty means authorized empty data, not denied, hidden or failed loading.
Logical errors are not HTTP codes: UNAVAILABLE_TARGET, AUTHENTICATION_REQUIRED, FIELD_OR_ACTION_DENIED, INPUT_INVALID, SOURCE_INCOMPLETE, INPUT_OR_POLICY_STALE, REVISION_CONFLICT, DEFINITIVE_NO_EFFECT_FAILURE, EFFECT_OUTCOME_UNKNOWN, RETRY_BUDGET_PAUSED and DEPENDENCY_UNAVAILABLE map to current owner facts. W04 will bind exact wire variants/status codes. A409 cannot be blanket retried; it may mean stale intent, state conflict or completed receipt. A timeout/503 alone is not verified rollback. No-effect retry must be proven by owner outcome; otherwise route to original receipt reconciliation. All recovery actions recheck current rights.
Errors preserve allowed user intent and identify the responsible owning repair route/linked task. Inline field errors focus the first invalid authorized input after a summary; server policy failures do not expose forbidden names/fields/source values. A browser notification/toast is supplementary: durable result/exception stays visible in the owning screen and '내 업무' even if notification delivery fails. Repeated polling uses bounded server hints/backoff and an actionable paused state, not busy infinite retry or false completion.

UX1.7 Group, review and publication composition
V02/V09 GO1 supports an explicit selected calculation manifest, maxone target per selected Company and max6Companies. It does not silently enable Group creation, decisions, review publication or handover with the same dispatch. V03 creates one Company run per command; multiple Company UI work uses explicit per-Company intents/receipts and actual partial outcomes. No claim that GO1 calculation is a universal Action runner yet. V02 consolidates authorized observations, not immutable approval evidence; each action freezes its own source/target manifest.
S05 handover plans and S02 PR1 publications similarly use their own one-Company command contracts. Multi-Company UI may link separate plans/results with truthful partial acceptance/cancellation; selecting Group does not make their commits/cancel global atomic. GO1 parent cancellation prevents future Group child effects but preserves prior effects and unknown outcomes; WA2 plan cancellation uses its own Company plan fence. No generic 'undo batch' hides these distinctions.
V07 offers explicit OPEN_REVIEW_CYCLE after complete supported calculation, creating current R/C and DRAFT Unit/Common proposals with a separate owner receipt (CALCULATED -> REVIEWING). V08 then offers SUBMIT_REVIEW for the exact inspected proposal before DECIDE_REVIEW. These are separate business transitions even when a UI presents adjacent next-step actions. V08 payroll decision review uses PC1 exact permitted unit coverage and AC1 S/D separation. S01 optional execution gate concerns D's exact command; gate permit alone leaves payroll undecided, and D explicitly executes afterward. Blind final sign-off on hidden wage data is not introduced. While still REVIEWING with no Completion, rejected/stale Unit/Common work opens its source owner form and then REVISE_REVIEW_CYCLE using committed correction refs and affected proposal CAS. It selectively recalculates dependencies, preserves unchanged calculations/approvals only on complete dependency equality, and activates a new immutable current cycle. Scoped users do not supply hidden roster/head tokens. V04/V07/V08 expose this route; it is not legacy whole-run withdraw/recalculate. An authorized explicit WITHDRAW_REVIEW_DECISION before Completion preserves the old receipt and creates the required unsubmitted replacement; role expiry alone does not withdraw a decision. CANCEL_REVIEW_CYCLE is the explicit control-authorized fallback when valid prerequisites cannot be retained; it preserves history and does not unlock periods. If a racing last decision already made the run APPROVED, same-run revision/withdraw is refused and AC1 successor is required. Approved-run correction uses AC1 supersession and required new review while preserving old results. S02 publishes exact approved nonpayable own-review snapshots under PR1; it does not imply paid/issued or bypass legal gates. Publication-only projection correction retains source amounts and replaces one current publication slot; source monetary changes use the payroll correction lineage.
V10/S03/S04 distinguish published own result, private request draft, submitted case, assigned handler, pending domain correction and resolved response. Case completion requires exact item response coverage and actual corrected publication for a corrected outcome, not merely reassignment or a saved wage change. Same Account remains usable after employment end with current historical own-record authorization. Internal preparedness is not leaked when no own result has been published.

UX1.8 Accessibility, keyboard, responsive and SSR fallback
Semantic headings/landmarks, labelled typed controls/units, table header associations, text+icon states and visible keyboard focus are required. Status is never color-only. WCAG2.2 AA is the acceptance target; no compliance claim until checked. Complex tables retain a reading/table mode and explicit row-detail links; editable grids, if used later, need their own keyboard contract rather than adding spreadsheet shortcuts to every table. Large tables use bounded pages with focusable navigation and announced count only for permitted rows; virtualization cannot drop focused rows or invisible mandatory errors.
Desktop can show source context beside input; narrow screens stack the same required content before action without hiding it. Actions remain reachable at200% zoom/reflow, with adequate target size and without a sticky bar covering focused input/error. Dialogs are only for bounded preview/confirmation: focus enters heading/first appropriate control, remains contained, Escape closes non-committing dialog, close returns to opener. A full-page fallback exists for deep-linked action forms. Back restores the caller's authorized context; login return targets are server-allowlisted local paths, never arbitrary URLs.
Hydration improves autosave/inline preview/filtering, not authority. If JS/WASM fails, SSR provides current authorized content, normal links and explicit save/submit forms calling the same server use case with CSRF/current policy/idempotency. Autosave is labelled unavailable and manual save remains. A transport adapter not yet implemented for this fallback is a W04/W06 obligation, not permission to remove safe input routes. Disabled JS cannot expose a hidden payload, bypass validation, or falsely claim an automatic save.
On route/context change, sensitive panes show a loading boundary, not old Company values. Background updates use polite status announcements without moving focus; explicit navigation/result completion focuses the destination heading. Unknown execution status uses an accessible persistent status region and a '결과 확인' action. Confirmation requires no timed interaction; work validity expiry warns when permitted and rechecks on action. Reduced-motion preference is respected; animation never substitutes for a durable state.

UX1.9 Surface assurance and implementation handoff
Current policy applies to HTML, island props/data-*, API/SSR forms, object/link previews, option search/autocomplete, pagination/filter counts, totals/deltas, notifications, browser caching/back-forward restored pages, draft history and error/log outputs. URLs contain only approved opaque refs and non-sensitive filters, not wage values, narrative or bearer tokens; server logs use route templates/redacted identifiers, sensitive pages use appropriate Referrer-Policy and cache control. Back-forward/focus reentry revalidates policy and clears stale managed content; already seen/copied information is not remotely erasable.
Actions and input templates are configured by real typed ActionDefinition/domain schema, not inferred from job titles or user prose. Reuse existing Leptos SSR and domain owners; do not generate16 independent CRUD applications. W04 supplies exact UI route handlers, input schema validators/DTO projection types, server command adapters, transport/error mapping, source/period numeric oracle and migration/transaction participation. First implementation is blocked until these interfaces are concrete and DELIVERY design/test approvals exist. This packet makes the user-facing behavior determinate but is not the final integrated technical candidate.
Required executable proof later: supported native end-to-end case with real persisted results, field/tenant denial and derived leaks, current revocation after SSR, same command response loss, saved draft conflict and transfer ABA, source correction and preserved prior publication, extra-gate separation, partial Group results, no-JS/manual-save path, keyboard/focus/reflow and regression checks for existing routes. Task traces in journeys.json name the expected receipts and failed alternatives; they are design walkthroughs, not test runs. No tests skipped/weakened and no product behavior implemented by this packet.
